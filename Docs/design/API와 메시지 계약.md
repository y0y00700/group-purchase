# API와 메시지 계약

작성 기준: 2026-10-28 대화 내용 반영

상태: 외부 API 요청 멱등성·JSON 메시지 형식·Kafka 전달 및 소비 방식을 초기 MVP 방향으로 합의했다. 구체적인 경로·DTO·설정값은 구현 설계에서 정한다.

## 1. 외부 API와 요청 멱등성

변경 요청에는 `Idempotency-Key`를 적용하고 사용자·작업 종류·키의 조합으로 요청 내용과 접수 결과를 영속화한다. 같은 키·같은 내용이면 기존 접수 결과·업무 ID·조회 경로를 반환하고, 같은 키·다른 내용이면 `409 Conflict`로 거절한다. 대상 리소스도 내용 비교에 포함하며 인증과 현재 조회 권한의 확인을 생략하지 않는다.

키 기록·해당 업무 변경·필요한 Outbox는 같은 로컬 트랜잭션으로 저장한다. 동시 요청에서도 중복 접수가 생기지 않도록 DB 유일 제약과 트랜잭션으로 제어한다. 커밋되지 않은 접수를 성공으로 반환하지 않는다.

결제 접수는 기존 합의대로 영속화 후 `202 Accepted`와 결제 시도 ID·조회 경로를 반환한다. 202는 실제 승인 성공·공동구매 성사를 뜻하지 않는다. 응답 유실로 재전송할 때 같은 키를 사용하고, 실패 확정·업무 반영·확보 해제 후 업무 조건이 유효해 새 시도를 시작할 때 새 키를 사용한다. 새 키만으로 미완료 시도를 우회하거나 중복 승인을 시작할 수 없다.

조회는 저장된 진행·확인 결과·필요한 환불 진행을 구분해 반환한다. 같은 요청의 접수 응답 재현과 현재 진행 조회를 구분한다. 공통 오류 형식에는 오류 코드·메시지·추적 정보를 포함하는 방향으로 상세 구현 시 정리하며, 정확한 경로·메서드·키 적용 대상·내용 정규화·보관 기간·다른 업무 거절 및 오류의 HTTP 매핑·조회 주기는 아직 미정이다.

## 2. 명령·결과의 JSON 형식

공통 정보와 업무별 본문을 구분한 JSON을 사용한다. 초기에는 별도 스키마 관리 서버 없이 계약 문서와 직렬화·호환성 테스트로 관리한다.

| 구분 | 관리할 정보 |
|---|---|
| 메시지 식별 | 메시지 ID·종류·형식 버전·생성 시각 |
| 업무 연결 | 메시지에 필요한 공동구매·참여·결제 시도 ID와 환불 ID |
| 추적·순서 | 흐름 추적 ID·원인 메시지 ID·기존 합의의 시도별 및 전달 방향별 순번 |
| 본문 | 수량·금액·적용 기한 또는 확인한 승인·환불 결과 등 해당 업무 정보 |

각 메시지에서 필요한 식별자를 정하며 모든 메시지에 의미 없는 필드를 강제로 채우지 않는다. 구체적인 필드명·필수 여부·ID 형식·금액 단위·시각 표현과 정밀도·버전 호환 규칙은 상세 계약에서 정한다. 생성·수신 시각을 PG의 실제 승인 완료 시각 대신 사용하지 않는다.

Outbox 재발행은 기존 메시지 ID·순번을 유지한다. 결과 확인 중·승인 성공 등 서로 다른 결과 통지는 각 메시지 ID를 가지며 같은 업무 ID에 연결한다. 상태·결과 종류도 확인해 새로운 유효 결과를 중복으로 버리거나 이전 상태로 되돌리지 않는다. 같은 업무 식별자의 금액·대상 불일치는 충돌로 기록한다.

지원하지 않는 버전·해석할 수 없는 원본은 기존 오류 분류·DLT 보관·파티션 보류 원칙을 따른다. JSON 사용만으로 호환성·순서·중복 방지가 보장된다고 가정하지 않는다.

## 3. Kafka 토픽·키·발행 및 소비 완료

| 목적 | 합의한 토픽 구분과 키 |
|---|---|
| 결제 명령 | 승인·중단·환불 의뢰를 결제 명령 토픽으로 전달. 키는 원승인 결제 시도 ID |
| 결제 결과 | 결제 결과 토픽으로 전달. 환불 결과도 원승인 결제 시도 ID를 키로 사용 |
| 알림 의뢰 | 별도 알림 의뢰 토픽으로 전달. 키는 공동구매 ID |

명령·결과·알림 목적별로 토픽을 분리한다. 업무 종류는 메시지 종류와 본문으로 구분하고 환불 업무 자체의 환불 ID도 유지한다. 같은 키라도 서로 다른 토픽 사이의 순서가 보장된다고 가정하지 않으며, 같은 시도·방향의 Outbox 순번과 상태 검증을 계속 적용한다. 서로 다른 결제 시도의 공동구매 경합은 공동구매 DB의 잠금 경계로 판단한다.

발행에는 `acks=all`과 프로듀서 멱등성을 사용하고, Kafka 성공 확인 후 현재 선점 ID에 따라 Outbox 발행 완료를 기록한다. 성공 확인 또는 완료 저장이 불명확하면 기존 메시지를 추적·재발행한다. 프로듀서 멱등성이 애플리케이션 Outbox 재발행에 의한 업무 중복까지 제거한다고 가정하지 않는다. 복제 수·최소 동기 복제본 수에 따른 내구성 조건은 실행 환경 설계에서 정한다.

소비는 자동 오프셋 커밋을 끄고 DB의 처리 기록·업무·필요한 Outbox 커밋 후 완료 위치를 반영한다. 같은 파티션에서 앞선 미처리·실패 원본을 넘기는 커밋을 하지 않는다. 병렬 처리가 있더라도 연속으로 처리 완료한 범위만 반영한다. DB 커밋 후 오프셋 반영 전 중단은 재전달과 기존 처리 기록으로 복구한다. DLT 보관만으로 실패 원본을 넘기지 않는 기존 원칙과 운영 종결 예외를 유지한다.

구체적인 토픽명·소비 그룹명·파티션 수·소비 병렬도·DLT 경로·클라이언트 버전·커밋 API·세부 설정값은 아직 미정이다. 같은 파티션의 실패가 다른 시도를 대기시킬 수 있는 비용과 조정 후보는 MVP 설계 재검토 목록에 기록한다.

## 4. 검증할 시나리오

- 같은 키·내용의 동시 및 반복 요청, 응답 유실 후 재요청에서 접수·시도·확보·Outbox가 중복 생성되지 않는지 확인한다.
- 같은 키의 대상·내용 변경은 409이며, 새 키로도 기존 미완료 시도와 업무 한도를 우회하지 못하는지 확인한다.
- 요청 키 저장·업무·Outbox 중 하나의 저장 실패 시 함께 롤백되는지 확인한다.
- JSON 직렬화·역직렬화와 버전 호환·필수 정보 검증, 금액·대상 불일치와 지원하지 않는 버전의 격리·보류를 확인한다.
- 같은 원승인 시도의 명령·결과·환불 연결과 Outbox 재발행 시 식별자·순번 유지를 확인한다.
- 발행 성공 후 완료 기록 전 중단, DB 소비 반영 후 오프셋 커밋 전 중단과 재전달에서 업무 중복을 막는지 확인한다.
- 앞선 레코드의 실패와 뒤 레코드의 처리 완료가 경합해도 앞선 실패를 건너뛰는 오프셋을 커밋하지 않는지 확인한다.

위 항목은 구현 후 검증할 후보이며 실행 결과가 아니다. 이후 합의한 인증·세션·권한은 [인증과 권한 설계](%EC%9D%B8%EC%A6%9D%EA%B3%BC%20%EA%B6%8C%ED%95%9C%20%EC%84%A4%EA%B3%84.md)를 따른다.
