# 도메인 책임과 서비스 경계

작성 기준: 2026-10-28 대화 내용 반영

관련 문서: [프로젝트 개요](../%ED%94%84%EB%A1%9C%EC%A0%9D%ED%8A%B8%20%EA%B0%9C%EC%9A%94.md), [MVP 요구사항](MVP%20%EC%9A%94%EA%B5%AC%EC%82%AC%ED%95%AD.md), [개별 참여 상태 설계](%EA%B0%9C%EB%B3%84%20%EC%B0%B8%EC%97%AC%20%EC%83%81%ED%83%9C%20%EC%84%A4%EA%B3%84.md), [기술 범위](%EA%B8%B0%EC%88%A0%20%EB%B2%94%EC%9C%84.md)

## 1. 합의한 초기 경계

- **공동구매와 참여는 하나의 공동구매 서비스에 둔다.**
- **결제는 공동구매와 분리한 독립 서비스로 둔다.** 결제 서비스는 승인·환불 실행과 결과 확인을 담당한다.
- **회원 정보·인증·역할 관리는 하나의 독립 회원 서비스에 둔다.** 회원 서비스가 로그인·로그아웃을 맡고, 대상 공동구매·참여 건에 대한 업무 권한은 공동구매 서비스가 판단한다.
- **알림은 독립 서비스로 둔다.** 공동구매 서비스가 안내 시점·대상·기한을 결정하고, 알림 서비스가 메시지 구성·전달과 전달 결과 관리를 맡는다.
- **상품 정보는 공동구매 서비스가 공동구매별로 관리한다.** MVP에서는 별도 상품 서비스를 두지 않는다.

공동구매 서비스 내부에서는 상품 정보·공동구매·참여의 책임을 구분한다. 각 영역의 데이터는 공동구매 서비스가 소유하고 변경한다. 클래스·테이블·애그리거트 구성과 구체적인 트랜잭션 범위는 후속 설계에서 정한다.

## 2. 공동구매 서비스 내부 책임

| 책임 | 담당 업무와 데이터 |
|---|---|
| 상품 정보 | 해당 공동구매의 상품명·설명·단가 관리, 공동구매별 상품 정보와 판매 조건 보관 |
| 공동구매 | 기준 수량·모집 목표·기한·공동구매 상태 관리, 모집·결제 접수·재모집, 성사·무산 판정 |
| 참여 | 참여 건의 구매자·수량·금액·상태 관리, 구매자별 유효 참여금액 10% 상한 검증, 취소·재참여, 확인된 결제·환불 결과의 참여 상태 반영 |

공동구매 서비스는 결제·환불 결과를 확인해 참여 상태에 반영한다. 실제 승인·환불 실행과 그 결과 확인·기록은 독립된 결제 서비스가 맡는다.

## 3. 함께 두는 이유와 비용

두 책임은 다음 규칙을 함께 지켜야 한다.

- 참여 신청 시 모집 상태·잔여 모집 수량과 구매자의 기존 유효 참여금액 합계를 확인한다.
- 결제 결과를 반영할 때 기준 수량 초과 여부를 확인하고, 정확히 기준 수량에 도달하면 공동구매의 구매를 확정한다.
- 구매자 취소 시 공동구매의 확정 여부를 확인한다. 결제 후 취소가 받아들여지면 해당 참여의 수량을 성립 판단에서 즉시 제외한다.
- 구매 확정·결제 기한 종료·최종 마감에 따라 관련 참여의 상태를 변경한다.

같은 서비스에 두면 이 규칙을 위한 데이터 확인과 변경을 로컬 트랜잭션으로 묶기 쉽고, 두 서비스 사이의 상태 전달 지연과 조율 부담을 줄일 수 있다.

대신 공동구매와 참여를 함께 배포·확장하게 된다. 동시 참여·결제·취소·마감의 경합을 제어하는 방법은 별도로 설계해야 하며, 외부 결제·환불 처리까지 로컬 트랜잭션으로 원자성을 보장하는 것은 아니다.

## 4. 결제 서비스와의 책임 경계

| 구분 | 공동구매 서비스 | 결제 서비스 |
|---|---|---|
| 결제 허용 | 참여 상태·기한·접수 상태·수량 상한에 따라 결제 허용 여부와 결제할 금액 판단 | 결제 요청을 처리하고 승인 결과 확인·기록 |
| 결제 결과 반영 | 확인된 결과를 참여 상태와 결제 완료 수량에 반영하고 성사 여부 판단 | 승인 성공·실패 또는 결과 불명을 추적하고 확인한 결과 전달 |
| 취소·환불 | 참여 취소 허용 여부와 환불 필요성 판단, 취소 수량 제외, 결제 후 취소 시 환불 대기로 전환 | 환불 실행, 실제 환불 결과 확인·기록·전달 |
| 환불 완료 반영 | 환불 완료가 확인되면 참여 상태에 반영 | 환불이 실제 완료되었는지 확인 |
| 소유 데이터 | 공동구매·참여의 업무 상태, 수량·금액·기한 | 결제 시도·승인 내역·실제 결제 결과, 환불 내역·결과 |

각 서비스가 자신이 소유한 데이터를 변경한다. 결제 서비스가 공동구매·참여 데이터를 직접 변경하거나 공동구매 성사 여부를 판정하지 않는다. 결제 승인과 공동구매의 구매 확정은 서로 다른 업무 사실이다.

분리하면 결제 연동·결과 확인·재시도를 공동구매의 모집·성사 판정과 별도 책임으로 관리할 수 있다. 두 서비스 사이에는 결제·환불 요청과 결과 전달이 필요하며, 중복·지연·결과 불명 및 후속 반영 실패에 대한 복구를 설계해야 한다.

후속 합의로 공동구매 서비스 내부의 조정 로직이 결제 흐름의 Saga Orchestration을 맡기로 했다. 공동구매 서비스가 승인 요청·업무 결과 반영·필요한 환불 요청과 전체 진행을 관리하고, 결제 서비스는 실제 승인·환불 실행과 결과 확인·기록·전달을 맡는다. 상세 책임과 선택 이유는 [핵심 결제 흐름 설계](%ED%95%B5%EC%8B%AC%20%EA%B2%B0%EC%A0%9C%20%ED%9D%90%EB%A6%84%20%EC%84%A4%EA%B3%84.md)의 1.1절을 따른다.

공동구매 서비스가 승인 전 사전 수량 확보를 맡고 확보 기록을 소유하기로 했다. 결제 완료 수량과 확보 수량의 합이 기준 수량을 넘지 않도록 원자적으로 처리한다. 결과별 전환·해제와 결과 불명 시 유지 기준은 [핵심 결제 흐름 설계](%ED%95%B5%EC%8B%AC%20%EA%B2%B0%EC%A0%9C%20%ED%9D%90%EB%A6%84%20%EC%84%A4%EA%B3%84.md)의 3절을 따른다.

메시지 발행 신뢰성을 위해 Transactional Outbox 도입·각 서비스의 업무 RDB 내 테이블 저장·초기 폴링 발행을 합의했다. 공동구매 서비스는 수량 확보·시도와 승인 의뢰, 취소·환불 후속 의뢰를 자신의 업무 RDB에 함께 원자적으로 저장한다. 결제 서비스는 확인한 승인·중단·환불 결과와 결과 전달 Outbox를 자신의 업무 RDB에 함께 저장한다. 각 서비스 내부의 폴링 발행기는 커밋한 메시지를 주기적으로 조회해 Kafka로 전달하고 발행 결과를 기록하며, 장애 후 전달을 재개한다. 폴링의 구체적인 간격·상세 동작·소비 멱등성의 상세 구현과 복구 구현은 후속 설계에서 정한다. 상세 원칙은 [핵심 결제 흐름 설계](%ED%95%B5%EC%8B%AC%20%EA%B2%B0%EC%A0%9C%20%ED%9D%90%EB%A6%84%20%EC%84%A4%EA%B3%84.md)의 8절을 따른다.

Outbox는 각 서비스가 자신의 업무 데이터와 같은 RDB에 저장한다. 서비스 간 테이블 공유·교차 접근을 추가하지 않으며, DB 서버의 물리적 공유 여부는 별도로 정한다. Kafka 브로커는 전달받은 메시지를 자체 저장소로 관리한다.

각 내부 발행기는 자신의 Outbox에 처리 중 상태·선점 ID·선점 기한을 원자적으로 기록해 대상을 선점하고 커밋 후 Kafka로 전송한다. 현재 처리 중인 선점 ID에만 결과 갱신을 허용하고, 기한 만료 후 새 ID로 재선점해 중단된 전달을 재개한다. 이전 발행기의 늦은 전송에 따른 중복은 소비 멱등성으로 다루며, 선점 만료로 결제 수량 확보를 해제하지 않는다. 구체적인 DB 제어·설정값은 후속 설계에서 정한다.

같은 결제 시도·같은 전달 방향의 메시지는 발행 순서를 관리하고 서로 다른 시도는 병렬 전달할 수 있도록 합의했다. 발행 순서가 공동구매 수량·취소·구매 확정에 대한 원자적인 업무 판단을 대신하지 않는다. 선점 만료 후 늦은 전송에 따른 중복·역순 도착에도 취소 기록·승인 차단·필요한 환불과 상태 전이 규칙을 유지한다. 상세 원칙은 [핵심 결제 흐름 설계](%ED%95%B5%EC%8B%AC%20%EA%B2%B0%EC%A0%9C%20%ED%9D%90%EB%A6%84%20%EC%84%A4%EA%B3%84.md)의 8.6절을 따른다.

각 발행 서비스는 같은 시도·전달 방향의 순번 갱신·업무 변경·Outbox 저장을 같은 로컬 트랜잭션으로 묶고, 가장 앞선 미완료 메시지만 선점한다. 앞 메시지의 Kafka 전송 성공 확인과 현재 선점 ID에 따른 Outbox 완료 기록 후 다음 메시지를 허용하며 실제 결제 업무 완료를 기다리지 않는다. 재시도 시 메시지 ID·순번을 유지하고 재선점 시 새 선점 ID를 부여한다. 앞 메시지의 실패·발행 여부 불명 중에는 후속 메시지를 건너뛰지 않는다. 구체적인 DB·Kafka·소비 계약은 후속 설계에서 정하며, 상세 원칙은 핵심 결제 흐름 설계의 8.7절을 따른다.

일시 발행 장애와 발행 여부 불명은 미완료 기록을 유지하고 간격을 점차 늘려 재시도한다. 간격에는 상한과 작은 무작위 차이를 두고 재시도 횟수·마지막 오류·다음 재시도 시각을 영속화한다. 장기 일시 장애는 운영 알림과 상한 간격의 자동 재시도를 병행한다. 직렬화·데이터·권한 문제처럼 원인 수정이 필요한 오류는 자동 재시도 중단을 영속화하고 원인 해결 후 재개한다. 재시작·선점 만료만으로 대기 시각이나 중단 기록을 무시하지 않으며, 앞 메시지를 건너뛰지 않는다. 발행 장애만으로 결제 미승인·확보 해제·기한 연장을 판단하지 않는다. 상세 원칙은 [핵심 결제 흐름 설계](%ED%95%B5%EC%8B%AC%20%EA%B2%B0%EC%A0%9C%20%ED%9D%90%EB%A6%84%20%EC%84%A4%EA%B3%84.md)의 8.8절을 따른다.

자동 재시도 상태와 운영 확인 상태를 구분한다. 원인 수정이 필요한 오류는 중단 기록 저장 후 즉시 알리고, 장기 일시 장애는 최초 실패 이후 경과 시간으로 판단해 알림과 자동 재시도를 병행한다. 최초 실패 시각은 재시도마다 덮어쓰지 않는다. 같은 서비스·원인의 장애는 묶어 알리고 재알림 간격을 두며 Kafka 장애 중에도 동작할 감시·전달 경로를 구성한다. 수동 재개는 원인 수정과 현재 중단 상태를 확인해 같은 메시지를 정상 선점 대상으로 돌리고 사람·시각·사유를 기록한다. 메시지 ID·순번·오류 이력은 유지한다. 알림 확인·재개 요청만으로 발행 완료나 문제 해결로 처리하지 않는다. 상세 원칙은 [핵심 결제 흐름 설계](%ED%95%B5%EC%8B%AC%20%EA%B2%B0%EC%A0%9C%20%ED%9D%90%EB%A6%84%20%EC%84%A4%EA%B3%84.md)의 8.9절을 따른다.

소비 멱등성과 업무 중복 방지의 다섯 원칙을 합의했다. 각 소비 서비스는 처리한 메시지 ID와 업무 식별자·현재 상태를 함께 확인하고, DB의 중복 처리 기록·해당 단계 업무 변경·필요한 후속 Outbox를 같은 로컬 트랜잭션으로 저장한다. 동시 중복도 한 번만 반영하도록 제어한다. 외부 승인·환불은 같은 업무의 재요청에 같은 멱등성 키를 사용하고 결과 불명 시 기존 작업을 확인한다. 미완료 작업의 복구와 새 결제 시도를 구분하며 중복·늦은 결과로 현재 상태를 되돌리지 않는다. 알림은 같은 안내의 전송 작업 중복 생성을 막고 실제 전달은 채널 연동에서 별도 확인한다. 식별자의 구성·수명·충돌 처리 원칙은 8.11절을 따르며, 구체적인 ID 형식·알림 대상 단위·상세 저장 모델·보관 기간·DB·API·외부 연동 계약은 미정이다. 상세 원칙은 [핵심 결제 흐름 설계](%ED%95%B5%EC%8B%AC%20%EA%B2%B0%EC%A0%9C%20%ED%9D%90%EB%A6%84%20%EC%84%A4%EA%B3%84.md)의 8.10절을 따른다.

메시지는 Outbox 최초 저장 시 ID를 부여하고 재발행 시 유지하며, 승인 요청·결과 등 서로 다른 메시지는 새 ID를 갖는다. 소비 중복 기록은 소비 처리 역할 + 메시지 ID로 관리하고 같은 역할의 여러 인스턴스가 공유한다. 승인·중단 업무는 결제 시도 ID와 업무 종류로 구분한다. 원승인 시도당 하나의 전액 환불 업무와 환불 ID를 재사용한다. 안내는 공동구매·회차·대상·안내 종류로 구분하되 대상 단위·채널은 미정이다. 결과는 업무 식별자·결과 종류·현재 상태를 함께 확인하며, 같은 업무 식별자의 금액·대상 불일치는 충돌로 기록한다. 외부 멱등성 키는 승인·환불 업무별로 고정한다. 상세 원칙은 [핵심 결제 흐름 설계](%ED%95%B5%EC%8B%AC%20%EA%B2%B0%EC%A0%9C%20%ED%9D%90%EB%A6%84%20%EC%84%A4%EA%B3%84.md)의 8.11절을 따른다.

공동구매·결제·알림 등 각 소비 서비스의 업무 RDB에 별도 소비 처리 기록 테이블을 두기로 합의했다. 소비 처리 역할 + 메시지 ID 조합에 DB의 중복 저장 방지 제약을 두고, 기본 정보는 처리 역할·메시지 ID·처리 시각으로 시작한다. 처리 기록·해당 단계 업무 변경·필요한 후속 Outbox를 한 로컬 트랜잭션으로 커밋하거나 롤백한다. DB 커밋 후 Kafka에 소비 완료를 알리고, 그 사이 중단되면 재수신 시 커밋된 기록으로 중복 반영을 막는다. 처리 기록과 실제 외부 승인 완료를 구분하며 이미 접수한 미완료 작업은 영속 진행 기록으로 계속 복구한다. 테이블명·상세 컬럼·DB 제품·보관 기간·구체적인 오프셋 설정은 미정이다. 상세 원칙은 [핵심 결제 흐름 설계](%ED%95%B5%EC%8B%AC%20%EA%B2%B0%EC%A0%9C%20%ED%9D%90%EB%A6%84%20%EC%84%A4%EA%B3%84.md)의 8.12절을 따른다.

소비 실패는 정상적인 중복·업무 거절, 일시 오류, 처리 불가·한도 초과 메시지, 공통 장애를 구분하기로 합의했다. 일시 오류는 같은 메시지를 간격을 두어 한도 내 재시도하고, 처리 불가·한도 초과 메시지는 원본·Kafka 위치·소비 역할·오류 이력과 해석 가능한 식별자를 DLT에 보존해 운영 알림과 재처리 대상으로 관리한다. 공통 DB 장애는 영향받는 소비를 일시 중단하고 복구를 확인한다. DLT 저장 확인 전 원본 소비 위치를 넘기지 않으며 보관을 업무 완료·결제 실패 확정으로 취급하지 않는다. 원인 해결 후 기존 식별자와 현재 상태를 확인해 재처리한다. 보관 후 후속 소비의 파티션 보류·재개 원칙은 8.14절을 따르며 실제 오프셋 설정·중단 기록 모델·운영 API는 미정이다. 상세 원칙은 [핵심 결제 흐름 설계](%ED%95%B5%EC%8B%AC%20%EA%B2%B0%EC%A0%9C%20%ED%9D%90%EB%A6%84%20%EC%84%A4%EA%B3%84.md)의 8.13절을 따른다.

DLT 보관 후 해당 소비 그룹의 실패 토픽·파티션과 이미 읽은 후속 메시지의 업무 처리를 보류한다. 다른 파티션은 자신의 조건을 만족하면 진행할 수 있다. 중단 사유·원본 위치를 영속 기록해 재시작·재할당 시 다시 적용하고, 같은 식별자로 실패 건을 정상 재처리해 해당 소비 단계의 DB 반영을 확인한 뒤 재개한다. 정상 재처리나 아래 종결 예외를 확인하기 전에는 실패 원본을 넘기는 오프셋을 커밋하지 않는다. 같은 파티션의 다른 업무도 대기한다. 상세 원칙은 [핵심 결제 흐름 설계](%ED%95%B5%EC%8B%AC%20%EA%B2%B0%EC%A0%9C%20%ED%9D%90%EB%A6%84%20%EC%84%A4%EA%B3%84.md)의 8.14절을 따른다.

정상 재처리가 어려운 원본은 무효라는 근거와 필요한 업무가 누락되지 않는다는 확인을 갖춘 경우에만 운영 종결할 수 있다. 승인·환불 결과나 업무 영향이 불명확하면 보류를 유지한다. 원본 위치·사람·시각·사유·확인 근거를 별도 종결 기록으로 커밋한 뒤 해당 원본만 넘기며, 원본·오류 이력을 보존한다. 종결을 정상 처리 성공·결제 실패·환불 완료로 취급하거나 수량을 임의 해제하지 않는다. 기록 커밋 후 통지 전 중단은 같은 원본의 종결 적용을 이어간다. 운영 요청의 접수·실행과 동시 조작 제어는 8.16절을 따른다. 실제 저장·오프셋·권한·API는 미정이다. 상세 원칙은 [핵심 결제 흐름 설계](%ED%95%B5%EC%8B%AC%20%EA%B2%B0%EC%A0%9C%20%ED%9D%90%EB%A6%84%20%EC%84%A4%EA%B3%84.md)의 8.15절을 따른다.

실패 파티션의 운영 요청을 해당 소비 서비스 DB에 영속 접수하고 현재 담당 소비자가 실행한다. 요청 ID·작업 종류·소비 그룹과 역할·실패 원본 위치·보류 상태 버전을 연결하며, 같은 요청은 기존 진행을 반환하고 내용이 다르면 충돌로 처리한다. 같은 그룹·토픽·파티션의 충돌 작업은 동시에 실행하지 않는다. 접수·실행 중·완료·실패를 구분하고 접수만으로 완료를 표시하지 않는다. 실행권은 실행 ID·기한으로 관리하며 안전한 해제 또는 만료를 확인한 현재 파티션 담당자만 새 실행 ID로 원자적으로 인수한다. 요청 ID·원본 식별자는 유지한다. 실행권 확인과 업무·진행 기록은 같은 짧은 DB 트랜잭션에서 경합을 제어한다. 재시작·재할당 후에는 업무·종결 기록과 Kafka 커밋 위치를 확인해 남은 단계부터 이어가고 이전 담당자의 늦은 갱신을 차단한다. 실행권 만료로 결제 결과·원본 종결·확보 해제를 확정하지 않는다. 운영 실행권의 시간은 해당 서비스 DB를 기준으로 판단하고, 단계 경계에서 현재 담당 여부·실행 ID·보류 버전과 미만료 조건을 확인해 필요한 경우에만 갱신한다. 업무·진행 반영 때에도 권한을 다시 검사하며, 이전 실행자의 늦은 실패·완료 표시도 제한한다. 갱신 실패·불명 시 새 단계를 중단하고 저장된 권한·진행을 확인한다. 운영 요청별 한도 내에서 자동 복구하고 데이터 충돌·원인 수정 필요·반복 실패·장시간 무진행이면 영속 중단과 운영 알림으로 전환한다. 공통 장애는 영향받는 작업을 일시 중단하고 복구 후 재개한다. 재시도·무진행 이력은 요청 ID에 연결해 재시작·실행권 인수로 초기화하지 않는다. 자동 중단을 결제 실패·원본 종결·확보 해제로 해석하지 않으며 원본·진행을 보존한다. 원인 수정 후 같은 요청을 수동 재개하고 사람·시각·사유를 기록한다. 수동 재개는 같은 요청 안에 새 복구 회차와 한도·수정 근거를 기록하고 전체 이력을 보존한다. 재개 중복은 같은 회차를 반환하며 재시작·실행권 인수는 같은 회차의 한도를 이어간다. 기존 반영 근거를 확인해 남은 단계만 수행한다. 정확한 기한·제한시간·횟수·간격·DB 제어·권한·API는 해당 구현 설계에서 구체화한다. 상세 원칙은 [핵심 결제 흐름 설계](%ED%95%B5%EC%8B%AC%20%EA%B2%B0%EC%A0%9C%20%ED%9D%90%EB%A6%84%20%EC%84%A4%EA%B3%84.md)의 8.16~8.20절을 따른다.

구현 범위 3개를 합의했다. 결제 서비스는 HTTP로 별도 PG Mock 서버를 호출하고 승인·환불·결과 조회·멱등성·통신 장애를 검증한다. 초기 알림은 테스트 대역을 사용하고 실제 업체 연동은 후속으로 둔다. 알림 대역의 구체적인 구성·채널은 구현 설계에서 정한다. 미완료 Saga·승인·환불은 각 서비스 내부의 주기적인 작업으로 자신의 DB 진행을 확인해 기존 식별자로 이어간다. 초기 사용자·운영 수단은 API와 테스트 클라이언트로 구성하고 화면·대시보드는 후속으로 둔다. 이번 세션은 합의 반영과 인계로 마무리하며 다음 세션에서 데이터와 동시성 3개 항목을 검토한다. 상세 결정은 [핵심 결제 흐름 설계](%ED%95%B5%EC%8B%AC%20%EA%B2%B0%EC%A0%9C%20%ED%9D%90%EB%A6%84%20%EC%84%A4%EA%B3%84.md)의 10절을 따른다.

별도 HTTP PG Mock과 초기 알림 테스트 대역을 채택했다. 메시지 계약, DB 제품·물리 구성과 수량 확보의 구체적인 동시성 제어 방식은 후속 설계에서 정한다.

## 5. 회원 서비스와의 책임 경계

| 담당 | 업무와 소유 데이터 |
|---|---|
| 회원 서비스 | 회원 ID·계정·인증 정보·역할 관리, 로그인·로그아웃, JDBC 세션 소유와 내부 인증 확인 |
| 공동구매 서비스 | 공동구매 등록자·참여자 소유 관계 관리, 대상 건의 수정·취소 권한과 업무 조건 판단 |

회원 서비스가 사용자 신원과 역할 정보의 기준을 관리한다. 공동구매 서비스는 신뢰할 수 있는 사용자 정보를 바탕으로 요청자의 역할, 대상 건의 소유 관계와 현재 업무 상태를 확인해 해당 행동을 허용할지 판단한다.

예를 들어 로그인한 구매자라도 다른 구매자의 참여를 취소할 수 없다. 본인의 참여라도 공동구매가 이미 구매 확정 상태라면 기존 취소 규칙에 따라 취소를 허용하지 않는다. 참여 소유 관계와 공동구매 상태를 관리하는 공동구매 서비스가 이 조건을 확인한다.

분리하면 계정·인증 변경을 공동구매 업무와 독립적으로 관리할 수 있다. 다른 서비스가 인증 결과와 역할 정보를 신뢰하는 방법, 회원 서비스 장애의 영향은 상세 설계에서 검토한다.

인증 방식은 세션 + 쿠키이며 초기 구현은 Spring Security + Spring Session JDBC로 회원 서비스 PostgreSQL에 세션을 저장·공유한다. Gateway는 보호된 요청마다 회원 서비스 내부 API로 세션·현재 역할·계정 상태를 확인하고 검증된 회원 ID·역할을 전달한다. 외부 신원 헤더를 제거하고 내부 호출자는 서비스별 자격 증명으로 확인한다. 소유 서비스는 역할·소유 관계·현재 업무 상태를 최종 검사한다. 인증 확인 장애 시 보호된 요청을 허용하지 않는다. 쿠키와 CSRF·운영 권한의 상세 합의는 [인증과 권한 설계](%EC%9D%B8%EC%A6%9D%EA%B3%BC%20%EA%B6%8C%ED%95%9C%20%EC%84%A4%EA%B3%84.md)를 따른다. Redis는 초기 도입하지 않고 후속 재검토 목록에 관리한다.

## 6. 알림 서비스와의 책임 경계

| 담당 | 업무와 소유 데이터 |
|---|---|
| 공동구매 서비스 | 결제 안내가 필요한 시점·대상 참여자·결제 기한 결정, 안내에 필요한 업무 정보 관리 |
| 알림 서비스 | 안내 정보로 메시지 구성, 전달, 전달 내역·성공·실패 기록, 재시도와 중복 전달 방지 처리 |

전달 흐름의 방향은 공동구매 서비스 → Kafka → 알림 서비스로 잡는다. 결제 개시 상태·개시 정보와 알림 의뢰 Outbox를 공동구매 서비스의 같은 업무 RDB와 로컬 트랜잭션으로 저장하고, 커밋한 메시지를 폴링 발행기가 전달한다. Outbox 도입과 각 서비스 내부의 초기 폴링 발행은 합의했고, 구체적인 메시지 종류·계약, 폴링의 구체적인 간격·상세 동작과 재시도·중복 전달 대응 방식은 후속 설계에서 정한다.

알림 서비스는 전달 상태를 관리한다. 공동구매의 업무 상태와 결제 기한을 변경할지 판단하는 책임은 공동구매 서비스에 둔다. 이메일·문자 등 전달 채널과 실제 외부 연동 여부는 아직 정하지 않았다.

분리하면 전달 장애와 재시도를 독립적으로 관리할 수 있다. 그 대가로 서비스 하나와 메시지 처리·운영 부담이 추가된다.

결제 안내 시점은 공동구매 서비스가 결제 개시와 개시 시각·기한을 확정해 저장한 회차 공통 결제 개시 시각이다. 기한은 이 시각부터 168시간과 최종 마감 중 빠른 시각이며, 같은 회차 참여자에게 공통 적용한다. 알림의 지연·실패·재시도·실제 전달·읽음 확인으로 개시 시각이나 기한을 바꾸지 않는다. 새 회차를 열어도 이전 결제 시도의 기한은 유지한다. 상세 합의는 [핵심 결제 흐름 설계](%ED%95%B5%EC%8B%AC%20%EA%B2%B0%EC%A0%9C%20%ED%9D%90%EB%A6%84%20%EC%84%A4%EA%B3%84.md)의 7절을 따른다.

## 7. 상품 정보의 소유 범위

공동구매 서비스가 상품명·설명·단가를 해당 공동구매의 판매 조건과 함께 관리한다. 판매자는 상품과 공동구매의 초안을 함께 작성해 게시하며, 추가 판매 시 새 공동구매를 수동 등록하는 기존 흐름을 유지한다.

현재 합의한 요구사항에는 여러 공동구매에서 재사용하는 상품 카탈로그나 공통 재고 관리가 없다. MVP에서는 별도 상품 서비스를 두지 않고, 공동구매별로 상품 정보와 판매 조건을 보관한다.

단가는 참여금액·구매자별 10% 상한·결제금액 계산에 사용되므로 공동구매의 판매 조건과 함께 관리한다. 별도 상품 서비스와의 조회·동기화 부담을 줄이는 대신, 같은 상품으로 여러 공동구매를 등록하면 상품 정보가 중복될 수 있다. 독립 상품 관리가 필요한 요구사항이 생기면 경계를 재검토한다.

상품명·설명·단가·기준 수량·최종 마감은 임시 저장 중 등록 판매자만 수정할 수 있고, 최초 게시 후에는 고정한다. 게시 후 참여가 없거나 모든 참여가 취소되어도, 공동구매가 재모집으로 돌아와도 수정 권한을 다시 열지 않는다. 수정과 게시의 선후는 공동구매 서비스에서 원자적으로 판단한다. 상태·수량 집계·재모집 부족분·회차별 기한은 기존 업무 규칙에 따라 계속 변경한다. 상세 합의는 [상품 정보 수정 정책](%EC%83%81%ED%92%88%20%EC%A0%95%EB%B3%B4%20%EC%88%98%EC%A0%95%20%EC%A0%95%EC%B1%85.md)을 따른다.

## 8. 초기 업무 서비스 구성

| 서비스 | 주요 책임과 소유 데이터 |
|---|---|
| 공동구매 | 상품 정보·판매 조건·공동구매·참여, 수량·기한·성사·무산 판단, 참여 상태 반영 |
| 결제 | 결제 시도·승인·환불 실행, 실제 처리 결과 확인·기록·전달 |
| 회원 | 회원 정보·인증 정보·역할, 로그인·로그아웃 |
| 알림 | 메시지 구성·전달, 전달 내역·성공·실패 기록, 재시도·중복 전달 대응 |

MVP의 초기 업무 서비스는 위 4개로 정리한다. Gateway·Eureka·Config 등 공통 기반의 실행 구성은 기술 범위를 기준으로 별도 설계한다. 각 업무 서비스가 소유한 데이터를 변경하며, 데이터 모델·DB 제품·물리 구성은 미정이다.

## 9. 후속 설계

최신 진행: 데이터·동시성·PostgreSQL, API·메시지 계약, 인증·권한과 [실행 환경과 초기 설정](%EC%8B%A4%ED%96%89%20%ED%99%98%EA%B2%BD%EA%B3%BC%20%EC%B4%88%EA%B8%B0%20%EC%84%A4%EC%A0%95.md)에 이어 [관측과 검증 설계](%EA%B4%80%EC%B8%A1%EA%B3%BC%20%EA%B2%80%EC%A6%9D%20%EC%84%A4%EA%B3%84.md)도 합의했다. JSON 로그·Actuator/Micrometer·Prometheus/Grafana, Alertmanager와 로컬 운영 알림, 목적별 정합성·장애 검증과 k6 초기 부하·목표를 채택했다. 수치는 측정 전 목표이며 코드 구현·실행 검증은 아직 없다. 다음 검토는 구현 순서와 단계별 완료 기준이며 아래 이전 인계의 미정·다음 세션 표기보다 이 최신 합의와 프로젝트 개요의 진행 현황을 우선한다.

- 다음 세션 검토: RDB 구성·핵심 테이블과 트랜잭션·동시성 제어. 업무 RDB 내 Outbox·서비스 내부의 긴 간격 폴링·선점 ID와 기한에 따른 원자적 선점·커밋 후 전송·재선점·이전 발행기의 갱신 제한과 시도별·전달 방향별 순번 기록·앞 메시지 발행 완료 후 다음 선점과 8.8절의 재시도·8.9절의 운영 개입·8.10절의 멱등성 기본 원칙·8.11절의 식별자 구성·8.12절의 별도 소비 처리 기록 테이블·커밋 후 소비 완료 통지와 8.13절의 소비 실패 분류·한도 재시도·DLT 보관과 8.14절의 실패 파티션 후속 처리 보류·재개 흐름과 8.15절의 무효 원본 운영 종결 예외와 8.16절의 운영 요청 영속 접수·담당 소비자 실행·동시 조작 제어 원칙과 8.17절의 실행 ID·기한에 따른 인수·단계별 장애 복구와 8.18절의 운영 실행권 DB 시간 기준·단계 경계의 조건부 갱신·반영 시 권한 재검사와 8.19절의 운영 요청별 한도 내 자동 복구·반복 실패 시 개입과 8.20절의 같은 요청 수동 재개·복구 회차별 한도 관리는 합의했다. 이후 오류 분류·운영 임계값·권한·API·재시도 설정·정확한 폴링 간격·선점 기한·멱등성 상세 구현·복구와 구체적인 DB 제어·Kafka 설정을 관련 내용 3개씩 묶어 검토한다.
- 상품 정보 입력 검증과 수정·게시 경합에 대한 구체적인 데이터 모델·DB 제어·API 설계.
- 알림 전달 실패·지연에 대한 복구·재시도 종료·운영 기준과 상태 변경·안내 의뢰의 유실 방지 구현.
- 회원 서비스·Gateway·각 도메인 서비스 사이의 인증·인가 상세 설계.
- 결제 결과 불명·지연·중복과 동시 요청을 다룰 업무 흐름·복구 방식.
- 데이터 모델·API·이벤트 계약·DB 구성과 동시성 제어 방식.

관련 설계 항목은 사용자와 약 3개씩 묶어 검토하고, 세부 필드·쿼리·설정값은 해당 구현 설계에 포함한다. 상품 정보·공동구매·참여는 공동구매 서비스에 두고, 결제·회원·알림은 각각 독립 서비스로 분리하기로 했다. 초기 도메인 책임과 서비스 경계는 이 구성을 기준으로 정리했다.
