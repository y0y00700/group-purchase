## 서비스 경계

- **공동구매와 참여는 하나의 공동구매 서비스에 둔다.**
- **결제는 공동구매와 분리한 독립 서비스로 둔다.** 결제 서비스는 승인·환불 실행과 결과 확인을 담당한다.
- **회원 정보·인증·역할 관리는 하나의 독립 회원 서비스에 둔다.** 회원 서비스가 로그인·로그아웃을 맡고, 대상 공동구매·참여 건에 대한 업무 권한은 공동구매 서비스가 판단한다.
- **알림은 독립 서비스로 둔다.** 공동구매 서비스가 안내 시점·대상·기한을 결정하고, 알림 서비스가 메시지 구성·전달과 전달 결과 관리를 맡는다.
- **상품 정보는 공동구매 서비스가 공동구매별로 관리한다.** MVP에서는 별도 상품 서비스를 두지 않는다.

공동구매 서비스 내부에서는 상품 정보·공동구매·참여의 책임을 구분한다. 각 영역의 데이터는 공동구매 서비스가 소유하고 변경한다. 클래스·테이블·애그리거트 구성과 구체적인 트랜잭션 범위는 후속 설계에서 정한다.

<a id="purchase-responsibility"></a>

## 공동구매 내부 책임

| 책임 | 담당 업무와 데이터 |
|---|---|
| 상품 정보 | 해당 공동구매의 상품명·설명·단가 관리, 공동구매별 상품 정보와 판매 조건 보관 |
| 공동구매 | 기준 수량·모집 목표·기한·공동구매 상태 관리, 모집·결제 접수·재모집, 성사·무산 판정 |
| 참여 | 참여 건의 구매자·수량·금액·상태 관리, 구매자별 유효 참여금액 10% 상한 검증, 취소·재참여, 확인된 결제·환불 결과의 참여 상태 반영 |

공동구매 서비스는 결제·환불 결과를 확인해 참여 상태에 반영한다. 실제 승인·환불 실행과 그 결과 확인·기록은 독립된 결제 서비스가 맡는다.

<a id="boundary-rationale"></a>

## 책임을 함께 두는 근거

두 책임은 다음 규칙을 함께 지켜야 한다.

- 참여 신청 시 모집 상태·잔여 모집 수량과 구매자의 기존 유효 참여금액 합계를 확인한다.
- 결제 결과를 반영할 때 기준 수량 초과 여부를 확인하고, 정확히 기준 수량에 도달하면 공동구매의 구매를 확정한다.
- 구매자 취소 시 공동구매의 확정 여부를 확인한다. 결제 후 취소가 받아들여지면 해당 참여의 수량을 성립 판단에서 즉시 제외한다.
- 구매 확정·결제 기한 종료·최종 마감에 따라 관련 참여의 상태를 변경한다.

같은 서비스에 두면 이 규칙을 위한 데이터 확인과 변경을 로컬 트랜잭션으로 묶기 쉽고, 두 서비스 사이의 상태 전달 지연과 조율 부담을 줄일 수 있다.

대신 공동구매와 참여를 함께 배포·확장하게 된다. 동시 참여·결제·취소·마감의 경합을 제어하는 방법은 별도로 설계해야 하며, 외부 결제·환불 처리까지 로컬 트랜잭션으로 원자성을 보장하는 것은 아니다.

<a id="payment-responsibility"></a>

## 결제 서비스 책임

| 구분 | 공동구매 서비스 | 결제 서비스 |
|---|---|---|
| 결제 허용 | 참여 상태·기한·접수 상태·수량 상한에 따라 결제 허용 여부와 결제할 금액 판단 | 결제 요청을 처리하고 승인 결과 확인·기록 |
| 결제 결과 반영 | 확인된 결과를 참여 상태와 결제 완료 수량에 반영하고 성사 여부 판단 | 승인 성공·실패 또는 결과 불명을 추적하고 확인한 결과 전달 |
| 취소·환불 | 참여 취소 허용 여부와 환불 필요성 판단, 취소 수량 제외, 결제 후 취소 시 환불 대기로 전환 | 환불 실행, 실제 환불 결과 확인·기록·전달 |
| 환불 완료 반영 | 환불 완료가 확인되면 참여 상태에 반영 | 환불이 실제 완료되었는지 확인 |
| 소유 데이터 | 공동구매·참여의 업무 상태, 수량·금액·기한 | 결제 시도·승인 내역·실제 결제 결과, 환불 내역·결과 |

각 서비스가 자신이 소유한 데이터를 변경한다. 결제 서비스가 공동구매·참여 데이터를 직접 변경하거나 공동구매 성사 여부를 판정하지 않는다. 결제 승인과 공동구매의 구매 확정은 서로 다른 업무 사실이다.

분리하면 결제 연동·결과 확인·재시도를 공동구매의 모집·성사 판정과 별도 책임으로 관리할 수 있다. 두 서비스 사이에는 결제·환불 요청과 결과 전달이 필요하며, 중복·지연·결과 불명 및 후속 반영 실패에 대한 복구를 설계해야 한다.

Saga·수량 확보·Outbox·소비 처리·운영 복구의 상세 원칙은 [결제·메시지 처리](payment-and-messaging.md)를 따른다.

<a id="member-responsibility"></a>

## 회원 서비스 책임

| 담당 | 업무와 소유 데이터 |
|---|---|
| 회원 서비스 | 회원 ID·계정·인증 정보·역할 관리, 로그인·로그아웃, JDBC 세션 소유와 내부 인증 확인 |
| 공동구매 서비스 | 공동구매 등록자·참여자 소유 관계 관리, 대상 건의 수정·취소 권한과 업무 조건 판단 |

회원 서비스가 사용자 신원과 역할 정보의 기준을 관리한다. 공동구매 서비스는 신뢰할 수 있는 사용자 정보를 바탕으로 요청자의 역할, 대상 건의 소유 관계와 현재 업무 상태를 확인해 해당 행동을 허용할지 판단한다.

예를 들어 로그인한 구매자라도 다른 구매자의 참여를 취소할 수 없다. 본인의 참여라도 공동구매가 이미 구매 확정 상태라면 기존 취소 규칙에 따라 취소를 허용하지 않는다. 참여 소유 관계와 공동구매 상태를 관리하는 공동구매 서비스가 이 조건을 확인한다.

분리하면 계정·인증 변경을 공동구매 업무와 독립적으로 관리할 수 있다. 다른 서비스가 인증 결과와 역할 정보를 신뢰하는 방법, 회원 서비스 장애의 영향은 상세 설계에서 검토한다.

## 알림 서비스 책임

| 담당 | 업무와 소유 데이터 |
|---|---|
| 공동구매 서비스 | 결제 안내가 필요한 시점·대상 참여자·결제 기한 결정, 안내에 필요한 업무 정보 관리 |
| 알림 서비스 | 안내 정보로 메시지 구성, 전달, 전달 내역·성공·실패 기록, 재시도와 중복 전달 방지 처리 |

전달 흐름의 방향은 공동구매 서비스 → Kafka → 알림 서비스로 잡는다. 결제 개시 상태·개시 정보와 알림 의뢰 Outbox를 공동구매 서비스의 같은 업무 RDB와 로컬 트랜잭션으로 저장하고, 커밋한 메시지를 폴링 발행기가 전달한다. Outbox 도입과 각 서비스 내부의 초기 폴링 발행은 합의했고, 구체적인 메시지 종류·계약, 폴링의 구체적인 간격·상세 동작과 재시도·중복 전달 대응 방식은 후속 설계에서 정한다.

알림 서비스는 전달 상태를 관리한다. 공동구매의 업무 상태와 결제 기한을 변경할지 판단하는 책임은 공동구매 서비스에 둔다. 이메일·문자 등 전달 채널과 실제 외부 연동 여부는 아직 정하지 않았다.

분리하면 전달 장애와 재시도를 독립적으로 관리할 수 있다. 그 대가로 서비스 하나와 메시지 처리·운영 부담이 추가된다.

결제 안내 시점은 공동구매 서비스가 결제 개시와 개시 시각·기한을 확정해 저장한 회차 공통 결제 개시 시각이다. 기한은 이 시각부터 168시간과 최종 마감 중 빠른 시각이며, 같은 회차 참여자에게 공통 적용한다. 알림의 지연·실패·재시도·실제 전달·읽음 확인으로 개시 시각이나 기한을 바꾸지 않는다. 새 회차를 열어도 이전 결제 시도의 기한은 유지한다. 상세 합의는 [핵심 결제 흐름 설계](payment-and-messaging.md)의 7절을 따른다.

<a id="product-ownership"></a>

## 상품 정보 소유권

공동구매 서비스가 상품명·설명·단가를 해당 공동구매의 판매 조건과 함께 관리한다. 판매자는 상품과 공동구매의 초안을 함께 작성해 게시하며, 추가 판매 시 새 공동구매를 수동 등록하는 기존 흐름을 유지한다.

현재 합의한 요구사항에는 여러 공동구매에서 재사용하는 상품 카탈로그나 공통 재고 관리가 없다. MVP에서는 별도 상품 서비스를 두지 않고, 공동구매별로 상품 정보와 판매 조건을 보관한다.

단가는 참여금액·구매자별 10% 상한·결제금액 계산에 사용되므로 공동구매의 판매 조건과 함께 관리한다. 별도 상품 서비스와의 조회·동기화 부담을 줄이는 대신, 같은 상품으로 여러 공동구매를 등록하면 상품 정보가 중복될 수 있다. 독립 상품 관리가 필요한 요구사항이 생기면 경계를 재검토한다.

<a id="api-contract"></a>

## 외부 API와 요청 멱등성

변경 요청에는 `Idempotency-Key`를 적용하고 사용자·작업 종류·키의 조합으로 요청 내용과 접수 결과를 영속화한다. 같은 키·같은 내용이면 기존 접수 결과·업무 ID·조회 경로를 반환하고, 같은 키·다른 내용이면 `409 Conflict`로 거절한다. 대상 리소스도 내용 비교에 포함하며 인증과 현재 조회 권한의 확인을 생략하지 않는다.

키 기록·해당 업무 변경·필요한 Outbox는 같은 로컬 트랜잭션으로 저장한다. 동시 요청에서도 중복 접수가 생기지 않도록 DB 유일 제약과 트랜잭션으로 제어한다. 커밋되지 않은 접수를 성공으로 반환하지 않는다.

결제 접수는 기존 합의대로 영속화 후 `202 Accepted`와 결제 시도 ID·조회 경로를 반환한다. 202는 실제 승인 성공·공동구매 성사를 뜻하지 않는다. 응답 유실로 재전송할 때 같은 키를 사용하고, 실패 확정·업무 반영·확보 해제 후 업무 조건이 유효해 새 시도를 시작할 때 새 키를 사용한다. 새 키만으로 미완료 시도를 우회하거나 중복 승인을 시작할 수 없다.

조회는 저장된 진행·확인 결과·필요한 환불 진행을 구분해 반환한다. 같은 요청의 접수 응답 재현과 현재 진행 조회를 구분한다. 공통 오류 형식에는 오류 코드·메시지·추적 정보를 포함하는 방향으로 상세 구현 시 정리하며, 정확한 경로·메서드·키 적용 대상·내용 정규화·보관 기간·다른 업무 거절 및 오류의 HTTP 매핑·조회 주기는 아직 미정이다.

## 인증과 권한

### 세션 저장·공유·만료·로그아웃

- 회원 서비스가 세션을 소유하고 자신의 PostgreSQL에 Spring Session JDBC로 저장한다. 여러 회원 서비스 인스턴스는 같은 세션 저장소를 사용한다.
- 로그인 성공 시 세션 ID를 변경하고 로그아웃 시 현재 세션을 무효화한다. 유휴 만료의 초기값은 이후 실행 환경 합의에서 30분으로 정했다. 테이블·정리 주기·저장 설정은 구현 설계에서 구체화한다.
- Gateway와 다른 업무 서비스가 회원 DB의 세션 테이블을 직접 읽지 않는다. 인증 확인은 회원 서비스의 내부 API를 사용한다.
- 세션 조회·갱신은 DB 부하에 추가된다. 초기에는 기존 PostgreSQL을 활용해 별도 저장소의 실행·장애 대응 구성을 줄인다.
- Redis 도입은 아직 확정하지 않았다. 세션 접근 부하·업무 DB 자원 경합·인증 지연을 관측한 뒤 JDBC 최적화와 Redis 전환을 비교한다. Redis의 추가 운영·장애 대응 비용과 전환 시 기존 세션의 처리도 함께 검토한다. 상세 재검토 항목은 MVP 설계 재검토 목록 R-11을 따른다.

로그아웃·세션 만료는 이후 인증 확인에서 반영한다. 이미 인증을 마치고 실행 중인 요청이나 접수 완료한 결제·환불·Saga까지 자동 취소하는 의미가 아니다. 업무의 취소 가능 여부와 후속 처리에는 기존 업무 규칙을 적용한다.

### Gateway 인증 확인과 내부 신뢰

보호된 외부 요청은 Gateway가 회원 서비스의 내부 인증 확인 API를 호출해 세션 유효성·현재 역할·계정 상태를 확인한 뒤 전달한다. 로그인 등 공개적으로 접근해야 하는 경로는 보호된 업무 경로와 구분하고 구체적인 목록은 구현 설계에서 정한다.

Gateway는 외부에서 보낸 사용자 신원·역할 헤더를 제거하고 검증한 회원 ID·역할을 내부 요청 정보로 전달한다. 인증 정보가 없거나 유효하지 않으면 보호된 업무 요청을 허용하지 않는다. 인증 확인 장애를 유효한 세션으로 추정해 통과시키지 않으며 인증 거절과 확인 불가 장애를 구분해 응답 계약에 반영한다.

내부 API는 외부에 공개하지 않고 서비스별 호출 자격 증명으로 호출자를 확인한다. 업무 서비스는 임의의 외부 요청이 보낸 신원 헤더를 신뢰하지 않으며 허용된 내부 호출자를 확인한다. 호출 자격 증명 형식·전달 방식·교체·보관과 네트워크 구성은 관련 구현 설계에서 구체화한다. 세션 쿠키·내부 자격 증명을 로그에 기록하지 않는다.

이 방식은 회원 서비스에 인증 책임을 모으는 대신 보호된 요청마다 내부 호출과 세션·회원 조회가 추가된다. 인증 확인 실패가 보호된 요청에 영향을 주는 비용과 최적화 후보는 재검토 목록 R-12를 따른다. 인증 결과의 별도 캐시는 현재 합의에 포함하지 않는다.

### 쿠키와 CSRF

세션 쿠키는 HttpOnly·SameSite=Lax를 적용하고 HTTPS 환경에서는 Secure를 적용한다. 로컬 HTTP 개발 환경과 HTTPS 환경의 쿠키 설정을 구분해 관리하며 구체적인 이름·경로·도메인·교차 출처 정책은 구현 설계에서 정한다.

쿠키 인증의 변경 요청에는 로그인·로그아웃을 포함해 CSRF 토큰 검증을 적용한다. SameSite 설정만으로 CSRF 검증을 대체하지 않는다. 테스트 클라이언트와 k6도 토큰 발급·세션 쿠키 유지·변경 요청의 토큰 전달을 재현한다.

Gateway를 통과하는 업무 변경 요청도 실제 업무 실행 전에 검증한다. 회원 서비스가 소유한 세션과 토큰 확인을 Gateway의 인증 확인 흐름에 연결하고 로그인·로그아웃은 회원 서비스의 보안 처리와 연결한다. 발급 경로·전달 헤더·검증 배치·토큰 갱신과 내부 확인 API의 요청 계약은 구현 설계에서 구체화한다. API 요청 멱등성 키는 인증·CSRF·권한 검사를 대체하지 않는다.

### 역할과 업무 권한

Gateway는 공통 인증·역할 검사를 수행하고 데이터를 소유한 서비스가 역할·소유 관계·현재 업무 상태를 함께 확인해 최종 허용 여부를 판단한다. 회원 서비스의 인증 확인은 현재 역할·계정 상태를 확인해 다음 확인부터 변경을 반영한다. 권한 정보를 세션 생성 당시 값만으로 계속 허용하지 않는다.

| 역할 | 허용할 업무 범위 |
|---|---|
| 구매자 | 본인 참여·결제 시도 조회와 허용된 시점의 취소 |
| 판매자 | 본인 공동구매 등록·게시와 임시 저장 중 수정 |
| 운영자 | 복구 상태 조회·재처리·재개·근거를 갖춘 종결 |

운영자도 구매 확정·환불 완료 등 업무 상태를 임의로 덮어쓰지 않는다. 기존 운영 요청·실행권·복구 회차·이력·종결 근거 규칙을 적용한다. 운영자 권한은 초기 관리 절차로 부여하며 일반 회원이 스스로 운영자 권한을 설정하는 API는 두지 않는다. 정확한 역할 코드·여러 역할 보유·운영 권한 부여 절차는 구현 설계에서 정한다.

공동구매의 참여·결제 접수 등 기존 구매자 기능은 그대로 유지한다. 위 표는 인증·권한 경계를 정리한 것이며 기존 기능을 축소하지 않는다. 대상의 소유 관계와 상태 검사는 실제 업무를 변경하는 트랜잭션 안에서 기존 잠금·경합 규칙과 함께 적용한다.
