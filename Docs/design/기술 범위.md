# Spring MSA 개인 프로젝트 기술 범위

작성 기준: 2026-10-28 대화 내용 반영

프로젝트 주제는 **목표 달성형 공동구매**로 확정했다. 아래에서는 사용자 선택이 정해진 기술과 추가 설계·검토가 필요한 항목을 구분한다. 핵심 업무 규칙은 MVP 요구사항에 정리했으며, 최소 기능부터 완성하고 필요에 따라 확장한다.

관련 문서: [MVP 요구사항·업무 규칙](MVP%20%EC%9A%94%EA%B5%AC%EC%82%AC%ED%95%AD.md), [프로젝트 개요·다음 세션 인계](../%ED%94%84%EB%A1%9C%EC%A0%9D%ED%8A%B8%20%EA%B0%9C%EC%9A%94.md), 설계 방법 (로컬 전용: `Docs/process/설계 방법.md`), [추천 프로젝트 리스트](../decisions/%EC%B6%94%EC%B2%9C%20%ED%94%84%EB%A1%9C%EC%A0%9D%ED%8A%B8%20%EB%A6%AC%EC%8A%A4%ED%8A%B8.md)

## 1. 선택한 기술과 역할

| 영역 | 기술·방식 | 적용 목적 |
|---|---|---|
| 애플리케이션 | Spring Boot | 도메인 서비스 구현 |
| 언어·빌드 | Java 21, Maven Wrapper | 단일 저장소의 개별 실행 모듈과 재현 가능한 빌드 |
| MSA 기반 | Spring Cloud | 설정·서비스 발견·Gateway 등 구성 |
| 서비스 발견 | Eureka | 서비스 인스턴스 등록·발견 |
| 설정 관리 | Spring Cloud Config | 환경별 애플리케이션 설정 관리 |
| 외부 진입점 | Spring Cloud Gateway | 외부 요청 라우팅과 공통 필터 |
| 인증 | 세션 + 쿠키 | 서버 세션에 인증 상태를 유지하고 쿠키로 세션 식별 |
| 인증·세션 구현 | Spring Security + Spring Session JDBC | 회원 서비스의 PostgreSQL에 세션 저장·공유. Redis는 후속 검토 후보 |
| 비동기 통신 | Kafka | 서비스 간 명령·이벤트 전달 |
| 분산 업무 일관성 | Saga Orchestration 및 보상 처리 | 공동구매 서비스가 여러 로컬 트랜잭션의 진행·실패·보상을 조정 |
| 장애 대응 | Resilience4j | 필요한 원격 호출의 장애 대응 정책 |
| 실행 환경 | Docker / Docker Compose | 애플리케이션·인프라 실행 환경 구성 |
| 메트릭 노출·수집 | Actuator·Micrometer, Prometheus | 시스템·업무 메트릭 노출과 수집 |
| 대시보드 | Grafana | 메트릭 시각화·분석 |
| 운영 알림 | Alertmanager, 로컬 테스트 수신기 | Kafka를 거치지 않는 장애 알림의 묶음·중복 억제·전달 검증 |
| 부하·성능 테스트 | k6 | 부하 발생, 응답·업무 처리 성능 검증 |

Java 21·Maven Wrapper와 초기 실행 설정을 합의했다. Spring Boot 4.0.x + Spring Cloud 2025.1.x는 후보 조합이며 프로젝트 생성 때 Resilience4j 등 연동 호환을 확인한 뒤 패치 버전을 고정한다. 정확한 버전·구현 설정과 합의한 초기값은 아래 실행 환경 합의 및 별도 문서를 따른다.

## 2. 인증 설계 범위

확정한 인증 방식은 **세션 + 쿠키**다.

회원 정보·인증·구매자 및 판매자 역할 관리는 하나의 독립 회원 서비스가 맡으며, 로그인·로그아웃도 이 서비스의 책임이다. 대상 공동구매·참여 건의 소유 관계와 업무 조건에 따른 권한 판단은 공동구매 서비스가 맡는다.

2026-10-28 다음 초기 방향을 합의했다.

- Spring Security + Spring Session JDBC를 사용해 회원 서비스의 PostgreSQL에 세션을 저장·공유한다. 로그인 성공 시 세션 ID 변경, 현재 세션 로그아웃·유휴 만료를 적용한다.
- Gateway는 보호된 요청마다 회원 서비스 내부 API로 세션·현재 역할·계정 상태를 확인한다. 외부 신원 헤더를 제거하고 검증된 신원을 전달하며 확인 장애 시 보호된 요청을 통과시키지 않는다.
- 내부 API는 외부에 공개하지 않고 서비스별 호출 자격 증명으로 호출자를 확인한다. 소유 서비스가 역할·소유 관계·현재 업무 상태를 최종 검사한다.
- 세션 쿠키는 HttpOnly·SameSite=Lax, HTTPS 환경의 Secure를 적용한다. 쿠키 인증의 변경 요청에는 로그인·로그아웃을 포함해 CSRF 토큰을 검증한다.
- 운영자는 복구 조회·재처리·재개·근거를 갖춘 종결을 수행하며 업무 상태를 임의로 덮어쓰지 않는다. 운영자 권한은 초기 관리 절차로 부여한다.

Redis는 후속 검토 후보이며 현재 도입하지 않는다. JDBC 세션 접근 부하·업무 DB 경합·인증 지연을 관측하면 JDBC 최적화와 Redis 분리를 비교한다. 상세 합의와 검증 후보는 [인증과 권한 설계](%EC%9D%B8%EC%A6%9D%EA%B3%BC%20%EA%B6%8C%ED%95%9C%20%EC%84%A4%EA%B3%84.md), 재검토 조건과 비용은 MVP 설계 재검토 목록 R-11~R-13을 따른다.

정확한 만료 시간·정리 주기·쿠키 이름·CSRF 발급 및 전달 계약·내부 API와 자격 증명·역할 코드·권한 부여 절차·k6 로그인 시나리오는 실행 환경 및 해당 구현 설계에서 구체화한다.

## 3. Kafka·Saga 설계 범위

Kafka는 메시지를 전달하고, Saga는 분산된 업무의 진행과 보상을 관리한다. Kafka 도입만으로 여러 서비스의 DB와 외부 결제 시스템까지 원자적으로 처리되는 것은 아니다.

| 항목 | 설계·검증할 내용 | 현재 상태 |
|---|---|---|
| Saga 조정 방식 | 공동구매 서비스 내부에서 Orchestration 수행 | 합의 완료. DB·메시지·복구의 상세 구현은 별도 설계 |
| 사전 수량 확보 | 승인 전 전체 수량을 원자적으로 확보, 결과별 전환·해제, 결과 불명 시 유지 | 채택 합의. DB 잠금·조건부 갱신 등 구체적인 제어 방식은 미정 |
| Saga 상태 저장 | 시도별 진행 중·결과 확인 중·반영 완료와 승인 결과 구분, 환불 별도 추적 | 업무 구분 합의. 마감 결과 확인 중은 별도 공동구매 상태. DB 모델·복구 구현은 미정 |
| 접수·결과 조회 | 접수 영속화 후 202와 시도 ID·조회 경로 반환, 기존 시도의 결과 조회 | 방식 합의. 상세 API·오류 코드·멱등성·조회 주기는 미정 |
| 메시지 계약 | 명령·결과 이벤트, 식별자, 토픽, 파티션 키 | 8.11절의 메시지·업무 식별자 구성 합의. 실제 필드·ID 형식·알림 대상 단위·토픽·파티션 키는 미정 |
| 발행 신뢰성 | 업무 변경과 발행할 메시지를 같은 로컬 트랜잭션으로 영속화 | 업무 RDB에 Outbox 테이블 저장·초기 폴링 발행 합의. 상세 구현은 미정 |
| 소비 멱등성 | 중복 명령·이벤트의 업무 중복 반영 방지 | 8.10절의 메시지·업무 중복 판단, 원자적 저장·동시 중복 제어와 외부 업무 중복 방지 등 다섯 원칙 합의. 식별자 구성은 8.11절에 합의. 소비 기록의 별도 테이블과 커밋 후 소비 완료 통지는 8.12절에 합의. 실제 ID 형식·상세 저장 모델·보관·DB·API·연동 계약은 미정 |
| 재시도 | 일시 장애·업무 실패·결과 불명을 구분 | Outbox 발행은 8.8절, 소비 실패는 8.13절의 분류·한도 재시도 원칙 합의. 외부 연동과 구체적인 설정은 후속 설계 |
| 소비 실패 메시지 | DLT 저장, 조회, 재처리 | 8.13절의 DLT 보관·운영 알림·기존 식별자 재처리 원칙 합의. 보관 성공 전 원본 소비 위치를 넘기지 않음. 후속 소비는 8.14절의 파티션 보류·재개 흐름 합의. 8.15절의 무효 원본 운영 종결 예외 합의. 8.16절의 영속 운영 요청·담당 소비자 실행·동시 조작 제어 원칙 합의. 8.17절의 실행 ID·기한에 따른 인수·단계별 장애 복구 합의. 8.18절의 운영 실행권 DB 시간 기준·단계 경계 조건부 갱신·반영 시 권한 재검사 합의. 8.19절의 요청별 한도 내 자동 복구·반복 실패 시 영속 중단·알림·같은 요청의 수동 재개 원칙 합의. 8.20절의 같은 요청 수동 재개·복구 회차별 한도·이력 보존 합의. 정확한 기한·횟수·간격·DB 제어·토픽·보관·오프셋 세부는 구현 설계에서 구체화 |
| 보상 복구 | 보상 실패 재시도와 미완료 상태 추적 | 각 서비스 내부의 주기적인 복구 작업으로 자신의 미완료 업무를 이어가는 구성 합의. 주기·조회·경합 제어는 구현 설계에서 구체화 |

Transactional Outbox를 도입하기로 합의했다. 공동구매 서비스의 수량 확보·시도와 승인 의뢰, 취소·환불 후속 의뢰, 회차 결제 개시와 알림 의뢰, 결제 서비스의 결과 저장과 결과 전달에 적용한다. 각 서비스가 소유한 업무 데이터 변경과 발행할 메시지를 같은 로컬 트랜잭션으로 영속화하고, 발행기는 커밋된 메시지를 Kafka로 전달한다. 발행 성공과 실제 승인·환불 완료는 구분하며, 재발행에 따른 소비 멱등성은 8.10절의 기본 원칙을 따르며 구체적인 구현은 후속 설계에서 정한다.

Outbox는 각 서비스의 업무 데이터와 같은 영속 RDB에 테이블로 저장하고, 초기 발행기는 각 서비스 내부의 폴링 작업으로 구성하기로 합의했다. 주기적으로 미발행 기록을 조회하고 Kafka 전송 결과를 확인해 발행 진행을 기록한다. Kafka 자체의 메시지 저장소는 브로커가 관리한다. 서비스별 데이터 소유권을 유지하며, DB 서버의 물리적 공유 여부는 별도로 정한다.

CDC·Debezium은 필요가 확인될 때 비교할 후속 대안이다. 폴링 발행기의 구체적인 간격·조회 건수·선점의 구체적인 DB 제어·순서 제어 구현·재시도 설정·정리 정책과 구체적인 테이블명·컬럼·DB 제품은 미정이다. 자세한 합의 범위는 [핵심 결제 흐름 설계](%ED%95%B5%EC%8B%AC%20%EA%B2%B0%EC%A0%9C%20%ED%9D%90%EB%A6%84%20%EC%84%A4%EA%B3%84.md)의 8절을 따른다.

초기 폴링 발행기는 각 서비스의 애플리케이션 내부에 구성하기로 합의했다. 공동구매 서비스와 결제 서비스가 각각 자신의 Outbox를 주기적으로 조회해 메시지를 발행한다. 서비스와 자원을 공유하며 함께 중단·재시작되고, 재시작 후 영속 기록으로 전달을 재개한다. 구체적인 스케줄러·스레드 구성과 별도 워커 분리 시점은 미정이다.

발행 대상은 처리 중 상태·고유한 선점 ID·선점 기한을 짧은 로컬 트랜잭션으로 원자적으로 기록해 선점한다. 커밋한 뒤 DB 트랜잭션 밖에서 Kafka로 전송하며, 처리 중 상태이며 현재 선점 ID가 자신의 것과 같은 경우에만 완료·실패 상태를 갱신한다. 미완료 상태에서 기한이 지나면 새 선점 ID로 재선점해 복구한다. 이전 발행기의 늦은 전송·발행 결과 기록 전 장애에 따른 중복 전달은 가능하므로 8.10절의 소비 멱등성 원칙을 적용하며 구체적인 구현은 후속 설계에서 정한다. 선점 기한은 메시지 발행 권한에 적용하며 결제 수량 확보를 만료시키지 않는다. 구체적인 DB 잠금·조건부 갱신 방식과 선점 기한·연장 여부는 미정이다.

같은 결제 시도·같은 전달 방향의 메시지는 발행 순서를 관리하기로 합의했다. 서로 다른 시도는 병렬 전달할 수 있으며, 공동구매 수량·취소·구매 확정 경합은 원자적인 업무 상태 변경으로 제어한다. 개별 메시지의 선점이나 같은 Kafka 키만으로 업무상 생성 순서가 보장된다고 가정하지 않는다. 선점 만료 후 늦은 전송과 재발행으로 인한 중복·역순 도착에도 기존 취소 기록·상태 전이 규칙을 유지한다.

시도별·전달 방향별 순번 갱신·업무 변경·Outbox 저장을 같은 로컬 트랜잭션으로 묶고, 동시 생성에서도 순번 중복과 업무 선후 관계의 역전을 방지한다. 가장 앞선 미완료 메시지만 선점하며, 앞 메시지의 Kafka 전송 성공 확인과 현재 선점 ID에 따른 Outbox 완료 기록이 커밋된 뒤 다음 메시지를 허용한다. 실제 승인·환불 완료를 기다리지 않는다. 재시도 시 메시지 ID·순번은 유지하고 재선점 시 새 선점 ID를 부여한다. 앞 메시지의 실패·발행 여부 불명·재시도 대기 중에는 후속 메시지를 건너뛰지 않는다. 구체적인 DB·Kafka·소비 계약과 오류 분류·재시도 설정·운영 임계값·권한·API는 미정이다. 상세 원칙은 핵심 결제 흐름 설계의 8.7절을 따르며, 재시도 원칙은 다음 문단과 핵심 결제 흐름 설계의 8.8절을 따른다.

일시 발행 장애와 발행 여부 불명은 미완료 기록을 유지하고 간격을 점차 늘려 재시도한다. 간격에는 상한과 작은 무작위 차이를 두고 재시도 횟수·마지막 오류·다음 재시도 시각을 영속화한다. 장기 일시 장애는 운영 알림과 상한 간격의 자동 재시도를 병행한다. 직렬화·데이터·권한 문제처럼 원인 수정이 필요한 오류는 자동 재시도 중단을 영속화하고 원인 해결 후 재개한다. 재시작·선점 만료만으로 대기 시각이나 중단 기록을 무시하지 않으며, 앞 메시지를 건너뛰지 않는다. 발행 장애만으로 결제 미승인·확보 해제·기한 연장을 판단하지 않는다. 상세 원칙은 [핵심 결제 흐름 설계](%ED%95%B5%EC%8B%AC%20%EA%B2%B0%EC%A0%9C%20%ED%9D%90%EB%A6%84%20%EC%84%A4%EA%B3%84.md)의 8.8절을 따른다.

자동 재시도 상태와 운영 확인 상태를 구분한다. 원인 수정이 필요한 오류는 중단 기록 저장 후 즉시 알리고, 장기 일시 장애는 최초 실패 이후 경과 시간으로 판단해 알림과 자동 재시도를 병행한다. 최초 실패 시각은 재시도마다 덮어쓰지 않는다. 같은 서비스·원인의 장애는 묶어 알리고 재알림 간격을 두며 Kafka 장애 중에도 동작할 감시·전달 경로를 구성한다. 수동 재개는 원인 수정과 현재 중단 상태를 확인해 같은 메시지를 정상 선점 대상으로 돌리고 사람·시각·사유를 기록한다. 메시지 ID·순번·오류 이력은 유지한다. 알림 확인·재개 요청만으로 발행 완료나 문제 해결로 처리하지 않는다. 상세 원칙은 [핵심 결제 흐름 설계](%ED%95%B5%EC%8B%AC%20%EA%B2%B0%EC%A0%9C%20%ED%9D%90%EB%A6%84%20%EC%84%A4%EA%B3%84.md)의 8.9절을 따른다.

소비 멱등성과 업무 중복 방지의 다섯 원칙을 합의했다. 각 소비 서비스는 처리한 메시지 ID와 업무 식별자·현재 상태를 함께 확인하고, DB의 중복 처리 기록·해당 단계 업무 변경·필요한 후속 Outbox를 같은 로컬 트랜잭션으로 저장한다. 동시 중복도 한 번만 반영하도록 제어한다. 외부 승인·환불은 같은 업무의 재요청에 같은 멱등성 키를 사용하고 결과 불명 시 기존 작업을 확인한다. 미완료 작업의 복구와 새 결제 시도를 구분하며 중복·늦은 결과로 현재 상태를 되돌리지 않는다. 알림은 같은 안내의 전송 작업 중복 생성을 막고 실제 전달은 채널 연동에서 별도 확인한다. 식별자의 구성·수명·충돌 처리 원칙은 8.11절을 따르며, 구체적인 ID 형식·알림 대상 단위·상세 저장 모델·보관 기간·DB·API·외부 연동 계약은 미정이다. 상세 원칙은 [핵심 결제 흐름 설계](%ED%95%B5%EC%8B%AC%20%EA%B2%B0%EC%A0%9C%20%ED%9D%90%EB%A6%84%20%EC%84%A4%EA%B3%84.md)의 8.10절을 따른다.

메시지는 Outbox 최초 저장 시 ID를 부여하고 재발행 시 유지하며, 승인 요청·결과 등 서로 다른 메시지는 새 ID를 갖는다. 소비 중복 기록은 소비 처리 역할 + 메시지 ID로 관리하고 같은 역할의 여러 인스턴스가 공유한다. 승인·중단 업무는 결제 시도 ID와 업무 종류로 구분한다. 원승인 시도당 하나의 전액 환불 업무와 환불 ID를 재사용한다. 안내는 공동구매·회차·대상·안내 종류로 구분하되 대상 단위·채널은 미정이다. 결과는 업무 식별자·결과 종류·현재 상태를 함께 확인하며, 같은 업무 식별자의 금액·대상 불일치는 충돌로 기록한다. 외부 멱등성 키는 승인·환불 업무별로 고정한다. 상세 원칙은 [핵심 결제 흐름 설계](%ED%95%B5%EC%8B%AC%20%EA%B2%B0%EC%A0%9C%20%ED%9D%90%EB%A6%84%20%EC%84%A4%EA%B3%84.md)의 8.11절을 따른다.

공동구매·결제·알림 등 각 소비 서비스의 업무 RDB에 별도 소비 처리 기록 테이블을 두기로 합의했다. 소비 처리 역할 + 메시지 ID 조합에 DB의 중복 저장 방지 제약을 두고, 기본 정보는 처리 역할·메시지 ID·처리 시각으로 시작한다. 처리 기록·해당 단계 업무 변경·필요한 후속 Outbox를 한 로컬 트랜잭션으로 커밋하거나 롤백한다. DB 커밋 후 Kafka에 소비 완료를 알리고, 그 사이 중단되면 재수신 시 커밋된 기록으로 중복 반영을 막는다. 처리 기록과 실제 외부 승인 완료를 구분하며 이미 접수한 미완료 작업은 영속 진행 기록으로 계속 복구한다. 테이블명·상세 컬럼·DB 제품·보관 기간·구체적인 오프셋 설정은 미정이다. 상세 원칙은 [핵심 결제 흐름 설계](%ED%95%B5%EC%8B%AC%20%EA%B2%B0%EC%A0%9C%20%ED%9D%90%EB%A6%84%20%EC%84%A4%EA%B3%84.md)의 8.12절을 따른다.

소비 실패는 정상적인 중복·업무 거절, 일시 오류, 처리 불가·한도 초과 메시지, 공통 장애를 구분하기로 합의했다. 일시 오류는 같은 메시지를 간격을 두어 한도 내 재시도하고, 처리 불가·한도 초과 메시지는 원본·Kafka 위치·소비 역할·오류 이력과 해석 가능한 식별자를 DLT에 보존해 운영 알림과 재처리 대상으로 관리한다. 공통 DB 장애는 영향받는 소비를 일시 중단하고 복구를 확인한다. DLT 저장 확인 전 원본 소비 위치를 넘기지 않으며 보관을 업무 완료·결제 실패 확정으로 취급하지 않는다. 원인 해결 후 기존 식별자와 현재 상태를 확인해 재처리한다. 보관 후 후속 소비의 파티션 보류·재개 원칙은 8.14절을 따르며 실제 오프셋 설정·중단 기록 모델·운영 API는 미정이다. 상세 원칙은 [핵심 결제 흐름 설계](%ED%95%B5%EC%8B%AC%20%EA%B2%B0%EC%A0%9C%20%ED%9D%90%EB%A6%84%20%EC%84%A4%EA%B3%84.md)의 8.13절을 따른다.

DLT 보관 후 해당 소비 그룹의 실패 토픽·파티션과 이미 읽은 후속 메시지의 업무 처리를 보류한다. 다른 파티션은 자신의 조건을 만족하면 진행할 수 있다. 중단 사유·원본 위치를 영속 기록해 재시작·재할당 시 다시 적용하고, 같은 식별자로 실패 건을 정상 재처리해 해당 소비 단계의 DB 반영을 확인한 뒤 재개한다. 정상 재처리나 아래 종결 예외를 확인하기 전에는 실패 원본을 넘기는 오프셋을 커밋하지 않는다. 같은 파티션의 다른 업무도 대기한다. 상세 원칙은 [핵심 결제 흐름 설계](%ED%95%B5%EC%8B%AC%20%EA%B2%B0%EC%A0%9C%20%ED%9D%90%EB%A6%84%20%EC%84%A4%EA%B3%84.md)의 8.14절을 따른다.

정상 재처리가 어려운 원본은 무효라는 근거와 필요한 업무가 누락되지 않는다는 확인을 갖춘 경우에만 운영 종결할 수 있다. 승인·환불 결과나 업무 영향이 불명확하면 보류를 유지한다. 원본 위치·사람·시각·사유·확인 근거를 별도 종결 기록으로 커밋한 뒤 해당 원본만 넘기며, 원본·오류 이력을 보존한다. 종결을 정상 처리 성공·결제 실패·환불 완료로 취급하거나 수량을 임의 해제하지 않는다. 기록 커밋 후 통지 전 중단은 같은 원본의 종결 적용을 이어간다. 운영 요청의 접수·실행과 동시 조작 제어는 8.16절을 따른다. 실제 저장·오프셋·권한·API는 미정이다. 상세 원칙은 [핵심 결제 흐름 설계](%ED%95%B5%EC%8B%AC%20%EA%B2%B0%EC%A0%9C%20%ED%9D%90%EB%A6%84%20%EC%84%A4%EA%B3%84.md)의 8.15절을 따른다.

실패 파티션의 운영 요청을 해당 소비 서비스 DB에 영속 접수하고 현재 담당 소비자가 실행한다. 요청 ID·작업 종류·소비 그룹과 역할·실패 원본 위치·보류 상태 버전을 연결하며, 같은 요청은 기존 진행을 반환하고 내용이 다르면 충돌로 처리한다. 같은 그룹·토픽·파티션의 충돌 작업은 동시에 실행하지 않는다. 접수·실행 중·완료·실패를 구분하고 접수만으로 완료를 표시하지 않는다. 실행권은 실행 ID·기한으로 관리하며 안전한 해제 또는 만료를 확인한 현재 파티션 담당자만 새 실행 ID로 원자적으로 인수한다. 요청 ID·원본 식별자는 유지한다. 실행권 확인과 업무·진행 기록은 같은 짧은 DB 트랜잭션에서 경합을 제어한다. 재시작·재할당 후에는 업무·종결 기록과 Kafka 커밋 위치를 확인해 남은 단계부터 이어가고 이전 담당자의 늦은 갱신을 차단한다. 실행권 만료로 결제 결과·원본 종결·확보 해제를 확정하지 않는다. 운영 실행권의 시간은 해당 서비스 DB를 기준으로 판단하고, 단계 경계에서 현재 담당 여부·실행 ID·보류 버전과 미만료 조건을 확인해 필요한 경우에만 갱신한다. 업무·진행 반영 때에도 권한을 다시 검사하며, 이전 실행자의 늦은 실패·완료 표시도 제한한다. 갱신 실패·불명 시 새 단계를 중단하고 저장된 권한·진행을 확인한다. 운영 요청별 한도 내에서 자동 복구하고 데이터 충돌·원인 수정 필요·반복 실패·장시간 무진행이면 영속 중단과 운영 알림으로 전환한다. 공통 장애는 영향받는 작업을 일시 중단하고 복구 후 재개한다. 재시도·무진행 이력은 요청 ID에 연결해 재시작·실행권 인수로 초기화하지 않는다. 자동 중단을 결제 실패·원본 종결·확보 해제로 해석하지 않으며 원본·진행을 보존한다. 원인 수정 후 같은 요청을 수동 재개하고 사람·시각·사유를 기록한다. 수동 재개는 같은 요청 안에 새 복구 회차와 한도·수정 근거를 기록하고 전체 이력을 보존한다. 재개 중복은 같은 회차를 반환하며 재시작·실행권 인수는 같은 회차의 한도를 이어간다. 기존 반영 근거를 확인해 남은 단계만 수행한다. 정확한 기한·제한시간·횟수·간격·DB 제어·권한·API는 해당 구현 설계에서 구체화한다. 상세 원칙은 [핵심 결제 흐름 설계](%ED%95%B5%EC%8B%AC%20%EA%B2%B0%EC%A0%9C%20%ED%9D%90%EB%A6%84%20%EC%84%A4%EA%B3%84.md)의 8.16~8.20절을 따른다.

구현 범위 3개를 합의했다. 결제 서비스는 HTTP로 별도 PG Mock 서버를 호출하고 승인·환불·결과 조회·멱등성·통신 장애를 검증한다. 초기 알림은 테스트 대역을 사용하고 실제 업체 연동은 후속으로 둔다. 알림 대역의 구체적인 구성·채널은 구현 설계에서 정한다. 미완료 Saga·승인·환불은 각 서비스 내부의 주기적인 작업으로 자신의 DB 진행을 확인해 기존 식별자로 이어간다. 초기 사용자·운영 수단은 API와 테스트 클라이언트로 구성하고 화면·대시보드는 후속으로 둔다. 이번 세션은 합의 반영과 인계로 마무리하며 다음 세션에서 데이터와 동시성 3개 항목을 검토한다. 상세 결정은 [핵심 결제 흐름 설계](%ED%95%B5%EC%8B%AC%20%EA%B2%B0%EC%A0%9C%20%ED%9D%90%EB%A6%84%20%EC%84%A4%EA%B3%84.md)의 10절을 따른다.

최신 합의에서는 핵심 데이터·로컬 트랜잭션과 공동구매 행 비관적 잠금을 초기 MVP 기준으로 채택했다. 참여·시도·확보 및 Saga 진행·환불을 구분하며 공동구매 집계와 상세 기록을 함께 갱신한다. 잠금 획득 후 상태·수량·기한을 재검사하고 성사·무산 결정과 후속 작업을 영속화해 참여 정리·환불을 나누어 처리한다. 상세 범위는 핵심 결제 흐름 설계 11절을 따른다. RDB는 PostgreSQL로 확정했고 버전·물리 구성은 미정이며 구체적인 DDL·격리 수준·쿼리·설정값은 미정이다. 초기 선택의 목적·재검토 조건·대안·검증 방법은 [MVP 설계 재검토 목록](../decisions/MVP%20%EC%84%A4%EA%B3%84%20%EC%9E%AC%EA%B2%80%ED%86%A0%20%EB%AA%A9%EB%A1%9D.md)에 관리한다.

초기 폴링 간격은 길게 잡는 방향으로 합의했다. 정확한 초 단위 값은 구현 전에 정한다. 반복 조회 빈도를 낮추는 대신 승인 의뢰·결과 전달 대기와 수량 확보 유지 시간이 늘어날 수 있으므로, 구현 후 DB 조회 부하·메시지 적체·전체 업무 완료 시간을 함께 측정해 조정한다. 결제 기한과 결과 확인에 따른 수량 전환·해제 규칙은 유지한다.

Kafka의 Exactly-once 기능과 외부 DB·외부 시스템에 대한 업무 중복 방지는 구분해서 설계한다. 메시지 재전달과 결과 응답 유실을 고려한다.

API와 메시지 계약의 주요 방향도 합의했다. 변경 요청에 사용자·작업 종류·Idempotency-Key를 적용하고 동일 키의 내용 충돌은 409로 거절한다. 공통 정보와 업무별 본문의 JSON을 사용하며 초기에는 별도 스키마 관리 서버 없이 계약 문서와 직렬화·호환성 테스트로 관리한다. Kafka는 결제 명령·결제 결과·알림 의뢰를 분리하고 결제 키는 원승인 시도 ID, 알림 키는 공동구매 ID다. 발행에는 acks=all·프로듀서 멱등성을 적용하고 소비는 자동 커밋을 끈 뒤 DB 반영 후 연속 처리 완료 범위까지만 커밋한다. 상세 계약은 [API와 메시지 계약](API%EC%99%80%20%EB%A9%94%EC%8B%9C%EC%A7%80%20%EA%B3%84%EC%95%BD.md), 재검토 조건은 MVP 설계 재검토 목록 R-08~R-10을 따른다. 관측과 검증까지 합의했고 다음 검토는 구현 순서와 단계별 완료 기준이다. 정확한 경로·DTO·버전·토픽명·파티션 수·병렬도·보관·설정값은 미정이다.

## 4. Resilience4j 적용 범위

Resilience4j는 일반적으로 애플리케이션 안에 포함하는 라이브러리다.

- 외부 결제 연동 등 HTTP 호출에 대해 타임아웃·Circuit Breaker·재시도 정책을 검토한다.
- 변경 요청의 재시도는 멱등성과 실제 처리 결과 확인 방법을 함께 검토한다.
- Kafka 소비 실패는 소비자 재시도·오류 처리·DLT 정책으로 다룬다.
- 타임아웃은 상대 시스템에서 업무 처리가 실패했다는 확정 증거가 아니므로 결과 확인·대사 방식을 정한다.

## 5. 모니터링과 성능 검증

```text
k6가 테스트 대상에 부하 발생
  → 애플리케이션이 요청·비동기 업무 처리
  → Prometheus가 노출된 메트릭 수집
  → Grafana에서 대시보드로 확인
```

k6는 부하 테스트 도구다. Prometheus·Grafana는 메트릭 수집·시각화를 담당한다. k6 자체 결과를 Grafana에서 함께 보고 싶다면 테스트 결과 출력·수집 경로를 별도로 정한다.

2026-10-28 JSON 로그·Actuator·Micrometer·Prometheus·Grafana와 운영 알림의 초기 구성을 합의했다. 로그에 요청·공동구매·결제 시도·메시지 ID와 처리 단계·오류를 남기고 개별 ID는 메트릭 라벨로 사용하지 않는다. 관측할 주요 지표는 다음과 같다.

| 구분 | 지표·확인 대상 |
|---|---|
| HTTP 요청 | 요청 수, 처리량, 오류율, 응답시간 p95·p99 |
| 애플리케이션 | JVM 메모리, GC, 스레드, DB 커넥션 등 |
| 비동기 업무 | 접수부터 최종 반영까지 걸린 시간, 접수·완료·미완료 수와 경과 시간 |
| Saga | 미완료·보상 대기·보상 실패 건수, 보상 완료 시간 |
| 메시지 처리 | Outbox 적체·최장 대기·재시도·중단, 소비 지연·실패, DLT 적재·파티션 보류 |
| 업무 정합성 | 목표 판정의 일관성, 중복 참여·결제·환불, 미완료 후속 처리 여부 |

위 지표가 모두 자동 제공된다는 의미는 아니다. Actuator·Micrometer의 기본 지표와 직접 구현할 업무 지표를 구분하고 Kafka·DB 지표의 수집 경로·수집 간격·대시보드는 해당 구현 설계에서 정한다.

비동기 접수 API가 빠르게 응답하더라도 최종 업무 완료가 늦을 수 있으므로, HTTP 응답시간과 전체 업무 완료 시간을 함께 측정한다.

운영 알림은 Kafka를 거치지 않는 Prometheus → Alertmanager → 로컬 테스트 수신기로 시작한다. 알림 묶음·중복 억제와 기존 운영 개입 원칙을 유지하고 정확한 임계값·재알림 간격·외부 수신 채널은 구현 시 정한다. 별도 로그 수집·분산 추적 서버는 분석의 어려움이 확인되면 비교한다.

검증은 업무 규칙·실제 PostgreSQL/Kafka 연동·PG Mock 전체 흐름·인증과 권한으로 나눈다. 응답과 DB 최종 상태·수량 집계·PG Mock 거래 기록을 함께 판정하고 초과 확보·중복 승인/환불·수량 이중 반영을 허용하지 않는다. 장애 주입 위치와 복구 순서를 고정해 재현한다.

k6는 결제 접수 유입을 고정하고 초당 2건·준비 2분/측정 5분을 기준 부하로 둔다. 초당 5건·10건의 증가 부하와 여러 공동구매 분산/특정 공동구매 집중을 비교한다. 기준 부하의 접수 p95 500ms 미만·예상 밖 오류율 1% 미만·정상 결제 최종 반영 p95 120초 이내는 측정 전 목표다. 정합성 위반 0건을 필수로 확인하고 실제 유입·거절·접수·완료·미완료 건수와 종료 후 DB/PG 거래 대사를 함께 남긴다. 상세 합의는 [관측과 검증 설계](%EA%B4%80%EC%B8%A1%EA%B3%BC%20%EA%B2%80%EC%A6%9D%20%EC%84%A4%EA%B3%84.md), 재검토 조건은 MVP 설계 재검토 목록 R-20~R-22를 따른다.

## 6. 구현·테스트·개선 범위

프로젝트 범위는 기능 구현부터 부하 테스트, 트러블슈팅, 트레이드오프에 따른 설계·구현 수정 및 재검증까지 포함한다.

```text
초기 설계·기준 구현
  → 정합성·장애·부하 테스트
  → 관측·문제 재현·원인 분석
  → 대안·트레이드오프 검토
  → 필요한 설계·구현 변경
  → 같은 조건으로 재검증
```

- 테스트 환경, 데이터 규모, 부하 모델과 관측 지표를 기록한다.

- 변경 전후 성능과 정합성을 비교하고, 추가된 복잡성·운영 비용·잔여 한계를 설명한다.
- 실제로 관측한 문제와 의도적으로 주입한 장애를 구분한다.
- 합의한 초기 성능 목표는 관측과 검증 설계를 따르고 도구별 세부 설정·스크립트는 해당 구현 단계에서 구체화한다.

## 7. 설계 결정 현황과 미정 항목

| 항목 | 상태 |

| 세션 저장소·공유 방식 | 회원 서비스 PostgreSQL의 Spring Session JDBC로 공유. 유휴 만료 30분. Redis는 후속 검토 후보. 정리·세부 설정은 미정 |

| 사전 수량 확보 | 공동구매 서비스가 승인 전에 확보하고 확인한 결과에 따라 전환·해제. 결과 불명 시 유지하며 시간 경과만으로 해제하지 않음. 초기 제어는 공동구매 행 비관적 잠금으로 합의. 상세 DDL·격리 수준·쿼리는 구현 설계에서 결정 |

| 로그·메트릭·분산 추적 | JSON 로그·식별자 연결, Actuator·Micrometer·Prometheus·Grafana 채택. 별도 로그 수집·분산 추적 서버는 후속 재검토 |

## 8. 합의한 실행 환경과 초기 설정

단일 PostgreSQL 서버의 서비스별 DB·계정, Kafka 브로커 1개, 같은 저장소의 Config 파일, 비밀값의 Git 제외와 별도 주입, 개발·전체·검증 프로필로 시작한다. 단일 DB의 자원·장애 공유와 단일 브로커의 복제 기반 고가용성 검증 한계를 재검토 목록에 기록했다.

세션 유휴 만료는 30분, 내부 HTTP·PG 연결 제한시간은 1초·응답 대기는 5초다. Outbox는 10초 간격·최대 50건 조회, 미완료 복구는 30초 간격, Outbox 일시 장애 재시도는 점진적 대기 증가·최대 60초와 무작위 차이를 적용한다. 초기 업무 관련 기록은 자동 삭제하지 않고 완료 기록 정리를 후속 검토한다. HTTP 시간 초과를 업무 실패로 확정하지 않는다.

상세 범위와 남은 구현 조건은 [실행 환경과 초기 설정](%EC%8B%A4%ED%96%89%20%ED%99%98%EA%B2%BD%EA%B3%BC%20%EC%B4%88%EA%B8%B0%20%EC%84%A4%EC%A0%95.md), 재검토 조건은 MVP 설계 재검토 목록 R-14~R-19를 따른다. 이전 절의 버전·물리 구성·초기값 미정 표기는 이번 합의 범위만큼 갱신된다. 관측과 검증까지 합의했고 다음 검토는 구현 순서와 단계별 완료 기준이다. 코드 구현·기동·CI 실행은 수행하지 않았다.
