# 업무 규칙과 상태

정리 기준: 2026-10-29. 현재 합의한 MVP 업무 규칙이다. 상세 저장 모델·API 필드·구현 결과는 별도로 관리한다.

[서비스 책임·API·인증](architecture.md) · [결제·메시지 처리](payment-and-messaging.md) · [검증](verification.md)

<a id="requirements"></a>

## MVP 범위

- 최소 기능으로 공동구매의 등록·모집·결제·성사·무산 흐름을 완성한다.
- 현재 합의한 규칙을 기준으로 구현하고, 추가 기능은 필요가 생겼을 때 확장한다.
- 추가 판매를 원하는 판매자는 새로운 공동구매를 수동으로 등록한다. 자동 추가 판매·자동 재등록은 초기 범위에 넣지 않는다.
- 사용자가 먼저 생각하고 결정하며, AI는 요청한 한 단계의 검토·설계·구현을 진행한다.
- 서비스 책임·API·인증은 [아키텍처](architecture.md), 데이터·경합 제어는 [결제·메시지 처리](payment-and-messaging.md#section-10)를 따른다.

## 사용자와 역할

| 역할 | 주요 행동과 책임 |
|---|---|
| 일반 회원·구매자 | 공동구매 참여, 결제, 정해진 조건에 따른 취소 |
| 판매자·공동구매 대표 | 상품·공동구매 등록, 물품 직접 공급 |

<a id="quantity-and-deadlines"></a>

## 수량과 결제 기한

| 항목 | 규칙 | 예시 |
|---|---|---|
| 기준 수량 | 판매자가 최초 입력하는 최소 10개인 정수 수량. 공동구매 성립에 필요한 결제 완료 수량 | 100개 |
| 최초 모집 목표 | 기준 수량 × 120%를 계산한 뒤 소수점 이하를 올림한 참여 신청 수량 | 기준 100개면 120개, 기준 11개면 14개 |
| 재모집 수량 | 기준 수량에서 취소되지 않은 결제 완료 수량을 뺀 부족분. 20%를 다시 추가하지 않음 | 90개 결제 유지 시 10개 추가 모집 |
| 최종 마감 | 판매자가 최초 등록한 최종 기한. 새 모집·결제 접수를 종료하며, 유효 승인은 이 시각 미만에 완료되어야 함 | 필요한 결제 결과 확인 후 미달이면 전체 취소 |
| 결제 안내 시점 | 공동구매 서비스가 회차의 결제 개시와 개시 시각·기한을 확정해 저장한 시각. 같은 회차 참여자에게 공통 적용 | 알림 전달 시각과 별도로 관리 |
| 결제 기한 | 회차 공통 결제 개시 시각부터 168시간과 공동구매 최종 마감 중 빠른 시각 | 최종 마감이 3일 남았다면 최대 3일 |

판매자에게 등록 전에 20% 추가 모집 조건과 주의사항을 설명하고, 입력 수량과 실제 모집 목표를 안내한다. 최초 모집 목표와 실제 구매 확정 기준 수량을 구분한다.

최소 10개 조건은 판매자가 최초 설정하는 기준 수량에 적용한다. 재모집 수량은 실제 부족분이므로 10개 미만일 수 있다.

7일은 168시간으로 계산한다. 같은 회차의 유효한 미결제 참여자에게 공통 개시 시각과 공통 기한을 적용하고, 기존 결제 완료분에는 다시 결제를 요구하지 않는다. 대상 참여자는 결제 가능 여부와 절대적인 결제 기한을 조회할 수 있어야 한다.

결제 개시의 상태 변경과 정보 저장이 실패하면 개시된 것으로 취급하지 않는다. 개시는 성공했으나 알림이 지연·실패하면 기존 개시 시각과 기한을 유지해 전달을 복구하며, 자동 연장하지 않는다. 중복 개시 처리·알림 재시도·실제 전달·읽음 확인도 개시 시각이나 기한을 바꾸지 않는다. 최종 마감에 도달했다면 새 결제 회차를 열지 않는다.

각 결제 시도에는 접수 당시 회차의 결제 기한을 적용한다. 유효한 시도로 기한 내 접수되었고 실제 승인 완료 시각이 해당 기한 미만인 결제만 성립 판단에 반영한다. 기한과 같거나 이후에 성공한 결제는 제외하고 전액 환불한다. 결과 수신·반영은 마감 후에도 가능하며, 수신 시각을 실제 승인 완료 시각으로 대신하지 않는다. 새 회차를 시작해도 이전 시도의 기한을 늘리지 않는다.

마감에는 새 결제 접수를 종료한다. 결과가 불명확한 기존 시도는 즉시 미승인이나 참여 취소로 단정하지 않고 확인을 계속한다. 결과 확인 시간은 승인 기한의 연장을 의미하지 않는다. 실제 연동 대상이 제공하는 승인 완료 시각의 근거와 정밀도 등은 연동 설계에서 확인한다.

<a id="workflow"></a>

## 업무 흐름

1. 판매자가 상품·공동구매 초안을 임시 저장하고 작성 완료 후 게시한다.
2. 구매자는 모집 중인 공동구매에 참여 신청한다.
3. 최초 모집 목표에 도달하면 모집을 닫고 회차 공통 결제 개시 시각과 기한을 확정해 결제를 안내한다. 재모집에서는 부족한 수량을 채우면 새 회차를 개시하고 안내한다. 알림 전달 결과는 결제 기간의 시작 기준으로 사용하지 않는다.
4. 취소되지 않은 기존 결제 완료 수량에 이번 참여 건의 전체 수량을 더했을 때 기준 수량을 초과하면 해당 결제 요청 건 전체를 거절한다. 유효한 결제 완료 수량이 정확히 기준 수량에 도달하는 즉시 공동구매의 구매를 확정하고 결제 접수를 종료한다. 남은 미결제 확정 참여는 취소하고, 미확정 시도는 별도로 확인한다.
5. 회차 결제 기한이 끝나면 새 결제 접수를 닫고 필요한 기존 결제 결과를 확인한다. 결과 확인 후에도 미달이고 최종 마감이 남아 있다면 미결제 확정 참여를 취소하고 부족한 수량만 재모집한다. 기존 유효 결제 완료분은 성립 또는 최종 마감 기준 판정을 기다린다.
6. 구매자는 결제 전과 결제 완료 후 공동구매 확정 전까지 취소할 수 있다. 결제 완료분을 취소하면 환불한다. 취소로 수량이 부족해진 경우 최종 마감 전까지 부족분을 재모집한다. 공동구매 구매 확정 후에는 구매자 취소를 허용하지 않는다.
7. 최종 마감에는 새 모집·결제 접수를 닫는다. 필요한 기존 결제 결과를 확인한 뒤 최종 마감 기준의 유효 결제 완료 수량이 기준에 미달하면 공동구매 전체를 취소하고 이미 결제한 금액도 전액 환불한다. 회차 마감의 결과 확인 중 최종 마감이 지났다면 새 회차를 시작하지 않는다.

예를 들어 기준 수량 100개, 최초 모집 목표 120개라면 100개 결제 완료 즉시 구매를 확정한다. 남은 20개의 미결제 참여는 취소되며, 해당 공동구매에서 추가 결제를 받지 않는다. 판매자가 더 판매하려면 새 공동구매를 수동으로 등록한다.

## 공동구매 상태

| 상태·진행 정보 | 의미와 주요 전환 |
|---|---|
| 등록 임시 저장 `DRAFT` | 판매자가 초안을 저장한 상태. 게시하면 모집 중으로 전환 |
| 게시·모집 중 | 참여를 받는 상태. 최초 목표 또는 재모집 수량을 채우면 결제 대기로 전환 |
| 결제 대기 | 회차 공통 결제 개시 후 결제를 받는 상태. 유효 결제 완료 수량이 기준을 채우면 완료로 전환. 결제 기한 종료 시 접수를 닫고 필요한 결과 확인 진행 |
| 마감 결과 확인 중 | 새 결제는 받지 않고 기존 미확정 결과를 확인. 유효 결제로 기준 수량을 채우면 완료. 확인 후 미달이면 최종 마감이 남을 때 재모집, 지났다면 만료 |
| 완료·구매 확정 | 기준 수량 결제가 완료되어 공동구매가 성립한 상태. 결제 접수 종료 및 남은 미결제 참여 취소. 구매자 취소 불가 |
| 만료 | 필요한 결과 확인 후 최종 마감 기준의 유효 결제 수량이 미달해 무산 판정한 상태. 공동구매 전체 취소 및 결제 완료분 환불 처리 |

여기서 완료는 공동구매의 성립·구매 확정을 의미한다. 만료는 공동구매의 무산 판정이며, 환불 처리가 모두 끝났다는 의미까지 포함하지 않는다. 개별 참여의 상태 초안과 현재 합의한 전환·재시도·재참여 규칙은 [개별 참여 상태 설계](#participation)를 따른다.

마감 결과 확인 중을 별도 공동구매 상태로 두기로 합의했다. 새 결제·재시도를 받지 않고 기존 시도의 결과를 확인한다. 결과 확인 중에도 구매 확정 전의 기존 구매자 취소 정책을 유지한다. 실제 DB 모델·enum 표기·API 필드 계약은 후속 설계에서 정한다.

## 구매자 취소 규칙

| 시점 | 구매자 취소 | 처리 |
|---|---|---|
| 참여 신청 후, 결제 전 | 허용 | 참여 취소 |
| 결제 완료 후, 공동구매 구매 확정 전 | 허용 | 참여·결제 취소 및 환불. 취소된 수량은 성립 판단에서 제외 |
| 공동구매 구매 확정 후 | 불가 | 구매 확정 유지 |

취소는 **참여 한 건의 전체 수량**에 대해서만 허용한다. 부분 취소는 제공하지 않으며, 결제한 참여 건을 취소하면 해당 건의 전체 수량을 성립 판단에서 즉시 제외하고 결제 금액 전액을 환불한다. 같은 구매자의 다른 참여 건은 유지한다.

위 규칙은 구매자의 취소 요청에 대한 정책이다. 공동구매 최종 마감 시 미달로 인한 전체 취소·환불과 구매 확정 시 남은 미결제 참여의 취소는 시스템이 처리하는 별도 사유다.

진행 중인 결제의 구매자 취소는 다음과 같이 처리한다.

- 취소와 구매 확정은 공동구매 서비스의 원자적인 상태 변경 순서로 판단한다. 구매 확정이 먼저 반영되면 구매자 취소를 거절한다.
- 취소가 먼저 수락되면 해당 참여를 성립 판단에서 제외한다. 승인 중단·결과 확인·필요한 환불은 별도로 추적한다.
- 취소 후 승인 성공이 뒤늦게 확인되어도 참여를 성립 대상에 다시 포함하지 않고 해당 건의 결제 금액 전액을 환불한다. 참여 상태는 참여 취소 → 환불 대기 → 환불 완료로 진행하며, 실제 환불 완료를 확인한 뒤에만 환불 완료로 바꾼다.

위 추가 규칙은 구매자 취소에 적용한다. 구매자 취소가 먼저 수락된 참여는 실제 승인이 기한 내였더라도 성립 대상에 복귀시키지 않고 환불한다. 마감 경합의 합의한 기준과 결과 확인·재모집·무산 순서는 [핵심 결제 흐름 설계](payment-and-messaging.md)의 6절을 따른다.

## 개별 참여의 상태와 재참여

### 상태 초안

`참여 신청 / 결제 완료 / 참여 취소 / 구매 확정 / 환불 대기 / 환불 완료`

참여 한 건의 업무 상태를 나타내며 기존 구성을 유지한다. 결제 시도의 진행 중·결과 확인 중·반영 완료와 확인된 승인 결과는 별도로 관리한다. 환불 진행도 구분해 추적한다. 상세 기준은 핵심 결제 흐름 설계의 2절을 따르며, DB 모델·API 필드·이력 보관 계약은 후속 설계에서 정한다.

### 주요 전환

| 이전 상태 | 다음 상태 | 전환 조건 |
|---|---|---|
| 참여 없음 | 참여 신청 | 공동구매가 모집 중이고 남은 모집 수량이 있으며 참여 조건을 충족 |
| 참여 신청 | 결제 완료 | 유효한 시도로 기한 내 접수되었고 실제 승인 완료 시각이 해당 기한 미만이며, 구매자 취소로 제외되지 않았고 해당 건 전체 수량을 반영해도 기준 수량을 초과하지 않음. 결과 수신·반영은 마감 후에도 가능 |
| 참여 신청 | 참여 취소 | 구매자가 결제 전에 취소하거나, 결제 기한 종료·공동구매 구매 확정·최종 마감 처리에서 시스템이 미결제를 확정한 참여를 취소 |
| 참여 신청 | 환불 대기 | 실제 승인 완료 시각이 해당 결제 기한과 같거나 이후인 성공 건을 확인. 성립 판단에서 제외하고 전액 환불 |
| 결제 완료 | 구매 확정 | 취소되지 않은 결제 완료 수량이 기준 수량을 채워 공동구매의 구매가 확정 |
| 결제 완료 | 환불 대기 | 공동구매 구매 확정 전에 구매자 취소가 받아들여지거나, 필요한 결과 확인 후 최종 마감 기준 미달로 공동구매가 무산 |
| 참여 취소 | 환불 대기 | 구매자 취소가 먼저 수락된 참여에서 진행 중이던 결제의 승인 성공을 뒤늦게 확인. 성립 대상에는 다시 포함하지 않음 |
| 환불 대기 | 환불 완료 | 실제 환불이 완료된 사실을 확인 |

- 결제 후 취소를 받아들이면 `환불 대기`로 전환한다. 해당 참여는 이미 취소된 것으로 취급하며, 환불 완료를 기다리지 않고 성립 판단 수량에서 제외한다.
- 공동구매 구매 확정 후에는 구매자 취소를 허용하지 않는다.
- 공동구매가 재모집으로 전환되어도 취소하지 않은 기존 참여자는 `결제 완료`를 유지한다.
- 환불 처리가 완료되기 전까지 `환불 완료`로 바꾸지 않는다. 환불 실패·복구의 상세 방식은 후속 설계에서 정한다.
- 승인 진행 중 구매자 취소를 수락하면 `참여 취소`로 전환하고 실제 결제의 중단·결과 확인을 별도로 추적한다. 결과가 불명확한 동안에도 참여 취소는 유지한다.
- 구매자 취소 수락 뒤 승인 성공을 확인하면 `환불 대기`로 전환하고 전액 환불한다. 실제 환불 완료를 확인하면 `환불 완료`로 전환한다.
- 구매자 취소가 먼저 수락된 참여는 실제 승인이 기한 내였더라도 성립 대상에 복귀시키지 않고 환불한다.
- 구매자 취소가 없는 결과 불명 참여는 마감 시에도 즉시 참여 취소로 바꾸지 않고 결과를 확인한다. 그동안 신규 결제·재시도는 허용하지 않는다.
- 기한 내 실제 승인이 확인되면 마감 후에도 결제 완료로 반영할 수 있다. 기한 외 승인 성공은 결제 완료를 거치지 않고 환불 대기로 전환한다.

### 결제 실패와 재시도

- 결제 실패가 확인되면 참여 상태는 `참여 신청`을 유지한다.
- 결제 기한이 남아 있고 공동구매가 결제를 접수 중이면 재시도를 허용한다.
- 기한 종료나 공동구매 구매 확정으로 미결제 참여가 취소되면 재시도를 허용하지 않는다.
- 참여 상태에 별도의 `결제 실패`를 추가하지 않는다. 미승인 확정·업무 반영·확보 해제 뒤 조건이 유효한 재시도는 새 결제 시도 ID로 기록하고 이전 이력을 보존한다.

### 취소 후 재참여

- 공동구매가 모집 중이고 남은 모집 수량이 있으면, 취소한 구매자의 재참여를 허용한다.
- 재참여는 새로운 참여 건으로 생성한다.
- 이전 참여의 취소·환불 기록은 보존한다. 새 참여 건의 결제와 이전 참여 건의 환불은 각각 추적한다.

### 구매 수량

- 판매자가 등록하는 **기준 수량은 최소 10개인 정수**로 제한한다.
- 최소 10개 조건은 최초 기준 수량에 적용한다. 재모집에서는 기준 수량을 유지하면서 실제 부족분만 모집한다.
- 최초 모집 목표는 **기준 수량 × 120%를 계산한 뒤 소수점 이하를 올림**한다. 예를 들어 기준 수량 11개이면 최초 모집 목표는 14개다.
- 한 번의 참여에서 여러 개 구매를 허용한다.
- 목표금액은 **판매자 기준 수량 × 상품 단가**로 계산한다. 재모집 중에도 이 기준을 유지한다.
- 같은 공동구매에서 **구매자 한 명의 유효 참여금액 합계가 목표금액의 10% 이하**여야 한다. 정확히 10%인 경우는 허용하고 초과하면 허용하지 않는다.
- `참여 신청`·`결제 완료`·`구매 확정` 참여의 금액을 합산한다. `참여 취소`·`환불 대기`·`환불 완료` 참여는 이미 취소되었으므로 합계에서 제외한다.
- 참여 건이 여러 개이거나 취소 후 새 참여 건으로 신청하더라도, 같은 구매자의 유효 참여 건을 합산해 상한을 적용한다.
- 신규 신청 시 **기존 유효 참여금액 합계 + 신청 수량 × 상품 단가 ≤ 목표금액 × 10%**를 충족해야 한다.
- 수량은 정수이므로 상한을 초과하지 않는 정수 수량까지만 허용한다. 동일 단가 기준 최대 합계 수량은 `판매자 기준 수량 × 10%`의 소수점 이하를 버린 값이다.

예: 판매자 기준 수량 100개·상품 단가 1만 원이면 목표금액은 100만 원이다. 구매자 한 명은 합계 10개·10만 원까지 참여할 수 있다. 이미 유효한 참여가 6개라면 추가 신청은 최대 4개다.

### 기준 수량을 초과하는 결제

- **취소되지 않은 기존 결제 완료 수량 + 이번 참여 건의 전체 수량 > 판매자 기준 수량**이면 해당 결제 요청 건 전체를 거절한다.
- 남은 수량만큼 일부 결제하는 방식으로 자동 처리하지 않는다. 거절된 건의 수량은 결제 완료 수량에 반영하지 않는다.
- 초과로 거절된 참여 건은 `참여 신청` 상태를 유지한다. 결제 기한과 접수 조건이 유효하면 기존 재시도 규칙을 적용하며, 재시도할 때도 수량 상한을 다시 확인한다.
- 취소되지 않은 결제 완료 수량은 기준 수량 이하여야 하며, 정확히 기준 수량을 채우면 즉시 공동구매의 구매를 확정한다.

예: 기준 수량 100개에서 이미 98개가 결제되었다면, 3개짜리 참여 건의 결제는 전체 거절한다. 결제 완료 수량은 98개를 유지한다. 2개짜리 참여 건의 결제가 성공하면 100개가 되어 구매를 확정한다.

## 상품 정보와 판매 조건

### 합의한 수정 범위

MVP에서는 판매자가 입력하는 아래 상품 정보와 판매 조건을 임시 저장 상태에서만 수정하고, 최초 게시 후에는 고정한다.

| 항목 | 임시 저장 중 | 게시 후 |
|---|---|---|
| 상품명·설명 | 수정 허용 | 수정 불가 |
| 상품 단가 | 수정 허용 | 수정 불가 |
| 판매자 기준 수량 | 수정 허용 | 수정 불가 |
| 최종 마감 | 수정 허용 | 수정 불가 |

임시 저장 정보의 수정은 해당 공동구매를 등록한 판매자만 할 수 있다. 게시 시 필수 정보와 기존 업무 조건을 다시 확인하고 판매 조건을 확정한다. 필수 필드와 입력 검증의 상세 구현은 데이터·API 설계에서 정한다.

### 게시 후 적용 범위

- 최초 게시부터 고정한다. 첫 참여가 생길 때까지 수정할 수 있는 예외는 두지 않는다.
- 게시 직후 참여자가 없거나, 이후 모든 참여가 취소되어 유효 참여가 없어져도 판매자 수정 권한을 다시 열지 않는다.
- 재모집으로 돌아와도 최초 게시한 상품 정보·단가·기준 수량·최종 마감을 유지한다.
- 게시 후 임시 저장 상태로 되돌려 편집하는 기능은 MVP 범위에 추가하지 않는다.
- 고정 대상은 표에 명시한 판매자 입력 정보다. 공동구매·참여 상태, 모집·결제 완료 수량, 재모집 부족분, 회차별 결제 개시 시각과 기한은 기존 업무 규칙에 따라 변경한다.

회차별 기한이 새로 계산되어도 판매자가 설정한 최종 마감을 변경하는 것으로 취급하지 않는다. 새 기한은 기존 합의대로 회차 개시 후 168시간과 고정된 최종 마감 중 빠른 시각이다.

### 이유와 비용

단가는 참여금액과 결제금액의 기준이다. 환불은 해당 건에서 실제 결제한 금액 전액이라는 기존 정책을 유지한다. 기준 수량은 성립 기준·최초 모집 목표·구매자별 10% 상한과 연결되고, 최종 마감은 모집·결제·무산 판정의 기준이 된다. 게시 후 이 값들을 고정하면 기존 참여 조건과 새로운 요청의 기준이 달라지는 문제를 줄일 수 있다.

상품명과 설명도 구매자가 판단한 상품의 내용을 바꿀 수 있으므로 MVP에서는 함께 고정한다. 오탈자만 허용하는 예외나 변경 이력·변경 안내 기능은 이번 초기 범위에 추가하지 않는다.

대신 오탈자와 잘못 게시한 정보도 기존 공동구매에서 수정할 수 없다는 불편이 있다. 다른 상품 정보나 판매 조건으로 모집하려면 새 공동구매를 수동 등록한다. 이는 기존 공동구매를 자동 취소하거나 기존 참여·결제·환불 기록을 새 공동구매로 옮기는 처리를 의미하지 않는다. 판매자에 의한 게시 취소·전체 중단은 이번 수정 정책의 범위에 포함하지 않는다.

### 초안 버전과 수정·게시 경합

2026-11-12에 판매자가 조회한 초안 버전으로 수정·게시하는 규칙을 합의했다. 수정이 성공할 때마다 초안 버전이 올라간다. 공동구매 서비스는 같은 행을 잠근 뒤 판매자 소유권과 임시 저장 상태를 확인하고, 새 요청의 버전이 현재 버전과 같은지 확인한다.

| 먼저 반영된 처리 | 뒤따르는 새 요청의 결과 |
|---|---|
| 초안 수정 | 이전 버전의 수정·게시를 `409`로 거절하고 갱신된 초안을 유지한다. 판매자가 최신 내용을 조회한 뒤 현재 버전으로 다시 요청할 수 있다. |
| 게시 | 뒤따르는 수정을 거절하고 게시 시 확정한 정보를 유지한다. |

현재 버전의 게시 요청은 필수 입력과 마감 조건을 통과하면 판매자가 확인한 내용으로 게시된다. 성공한 요청의 재전송과 API 오류 계약은 [009 수정·게시 경합과 멱등성](../implementation/plan/009-group-purchase-product.md#transactions)을 따른다.

## 구현 단계에서 정할 상세 계약

- 후속 실제 PG·알림 업체의 연동 대상·방식과 PG Mock·알림 테스트 대역의 상세 계약.
- 마감 결과 확인 중을 포함한 진행 정보의 구체적인 DB 모델·enum 표기·API 필드 및 멱등성 계약.
- 실제 결제 연동 대상이 제공하는 승인 완료 시각의 근거·신뢰성·정밀도·시간대 확인과 장기 결과 불명 건의 복구·운영 기준.

위 항목은 현재 합의된 기능으로 가정하지 않는다. 이후 설계·구현에 필요한 시점에 MVP에 맞는 작은 범위로 결정한다.

요청 멱등성의 방향은 [API 계약](architecture.md#api-contract), 비관적 잠금·로컬 트랜잭션의 방향은 [데이터와 경합 제어](payment-and-messaging.md#section-10)로 합의했다. 미정 범위는 구체적인 필드·DDL·쿼리·연동 계약이다.
