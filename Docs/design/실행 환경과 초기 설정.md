# 실행 환경과 초기 설정

작성 기준: 2026-10-28 대화 내용 반영

상태: 최종 실행 환경과 초기값의 방향은 합의했다. 2026-10-28 사용자 요청으로 Java 21·Spring Boot 4.0.9·Maven Wrapper 3.9.16의 단일 기본 프로젝트만 생성했다. 아래 서비스별 모듈·Compose·Cloud 등은 후속 단계의 목표 구성이다. 전체 MSA 연동·컨테이너 실행은 아직 수행하지 않았다.

## 1. 버전·빌드·저장소 구조

- Java 21과 Maven Wrapper를 사용한다. 정확한 JDK 배포판·패치와 Maven Wrapper 버전은 프로젝트 생성 때 고정한다.
- 단일 저장소에 공동구매·결제·회원·알림·Gateway·Config·Eureka·PG Mock을 각각 실행 가능한 모듈로 둔다. 서비스별 독립 빌드·실행·배포 경계를 유지하고 엔티티·업무 로직을 공유하지 않는다.
- Spring Boot 4.0.x + Spring Cloud 2025.1.x를 호환 조합 후보로 채택한다. Resilience4j·Spring Security·Spring Session JDBC·Kafka 등 연동 라이브러리를 포함해 의존성 및 기동을 검증한 뒤 정확한 패치 버전을 고정한다. 후보 채택이 연동 검증 완료를 뜻하지 않는다.
- PostgreSQL·Kafka·Docker 이미지 등의 정확한 버전은 최소 실행 구성을 만들 때 확인·고정한다. 공통 설정·모듈 경로·이미지 빌드 방식도 해당 구현 설계에 포함한다.

초기에는 한 저장소에서 관련 변경과 검증을 추적하는 비용을 줄인다. 저장소·공유 코드 경계와 버전 재검토는 MVP 설계 재검토 목록 R-14를 따른다.

## 2. 로컬 실행과 물리 구성

| 영역 | 합의한 초기 구성 |
|---|---|
| 실행 기준 | Docker Compose 기반 로컬 재현 환경부터 완성 |
| PostgreSQL | 서버 하나에 서비스별 DB·계정 분리. 서비스는 자신이 소유한 DB에 접근 |
| Kafka | 초기 브로커 1개. 다중 브로커·복제 기반 장애 검증은 후속 범위 |
| Config | 같은 저장소의 파일로 일반 설정 관리 |
| 비밀값 | Git에서 제외하고 Compose secrets 등의 방식으로 서비스에 주입 |
| 실행 구분 | 개발용·전체 실행·검증용 프로필 구분 |
| 초기 CI | 빌드·테스트·이미지 빌드. 서버 자동 배포는 후속 범위 |

업무 DB·Outbox·소비 기록의 서비스별 소유권과 로컬 트랜잭션 경계는 유지한다. 단일 PostgreSQL 서버는 자원·장애 영향을 공유하며 서비스별 서버 독립성을 검증한 구성이 아니다. 필요가 관측되면 서비스별 DB 서버 분리를 비교한다. PG Mock의 저장 방식은 별도 테스트 대역 구현 설계에서 정한다.

Kafka 단일 브로커에서 acks=all·프로듀서 멱등성·소비 멱등성과 장애 후 재개를 검증할 수 있지만 복제 기반 고가용성의 근거로 사용하지 않는다. 복제 수·최소 동기 복제본 수·토픽 파티션 수 등은 해당 실행 구성에 맞춰 명시한다.

Eureka·Config·Gateway와 업무 서비스·PG Mock의 최소 연결을 구성하고 Prometheus·Grafana 등 관측 구성은 관측·검증 합의와 연결한다. 내부 API 비공개·서비스별 자격 증명·환경별 쿠키 설정은 인증 설계를 유지한다.

CI 공급자·저장소 원격 위치·서버 배포 대상·구체적인 프로필과 Compose 경로는 아직 미정이다. 로컬 검증부터 가능한 구성으로 만들고 실제 CI·배포의 외부 작업은 해당 구현 요청을 따른다.

## 3. 합의한 초기 운영값

| 항목 | 초기 기준 |
|---|---|
| 세션 유휴 만료 | 30분 |
| 내부 HTTP·PG 연결 제한시간 | 1초 |
| 내부 HTTP·PG 응답 대기 제한시간 | 5초 |
| Outbox 조회 | 10초 간격, 한 번에 최대 50건 |
| 미완료 업무 복구 조회 | 30초 간격 |
| Outbox 일시 장애 재시도 | 점진적으로 대기 증가, 최대 60초와 무작위 차이 적용 |
| 업무 관련 기록 | 초기에는 자동 삭제 없이 시작. 완료 기록 정리 정책은 후속 검토 |

위 값은 초기 구현·측정의 기준이며 성능 목표 달성이나 최적값을 뜻하지 않는다. 설정 파일에서 관리해 재현 가능한 조건으로 조정한다. HTTP 제한시간 초과는 상대의 업무 실패 확정이 아니며 기존 식별자로 실제 결과를 확인한다.

Outbox 재시도는 일시 장애·발행 여부 불명에 적용한다. 원인 수정이 필요한 오류의 영속 중단, 장기 일시 장애의 운영 알림과 자동 재시도 병행, 기존 메시지 ID·순번 유지 원칙을 바꾸지 않는다. 정확한 증가식·무작위 범위와 Kafka 클라이언트의 별도 제한시간은 구현 설계에서 정한다.

조회 최대 50건이 외부 호출 대기 동안 하나의 DB 트랜잭션을 유지한다는 의미는 아니다. 선점 기한·Kafka 전송 제한시간·단계별 실행 제한과 갱신을 작업 단위에 맞춰 함께 정한다. 만료 후 이전 실행자의 갱신 차단과 재시작 후 재개 원칙을 유지한다.

업무·시도·멱등성·Outbox·소비 및 운영 이력은 초기 자동 삭제 없이 보관하고 용량·조회 비용을 측정한 뒤 완료 기록의 정리 대안을 비교한다. 미완료·결과 불명 기록을 임의로 삭제하지 않는다. 이 방침은 30분 세션 만료를 없애거나 Kafka 로그의 무기한 보존을 확정하는 뜻이 아니다. 세션 정리 작업·Kafka 보존·로그 보관은 각각 구현 설계에서 정한다.

## 4. 구현 시 확인할 항목

- Maven Wrapper로 같은 버전·의존성을 재현하고 각 실행 모듈의 기동·연결을 확인한다.
- Spring Boot·Cloud·Resilience4j 등 연동 호환을 확인하고 실제 버전·설정·이미지를 기록한다.
- 서비스별 DB 계정의 접근 범위와 업무·Outbox·소비 기록의 로컬 원자성을 확인한다.
- 개발·전체·검증 프로필의 실행 방법과 필요한 자원을 문서화한다.
- 비밀값의 Git 제외·서비스별 주입과 로그 미노출, 내부 API 접근 경계를 확인한다.
- Outbox·미완료 작업의 간격·조회 상한·재시도 대기와 재시작 후 이력 유지를 확인한다.
- HTTP 제한시간을 넘긴 PG Mock 거래를 결과 불명으로 추적해 중복 승인·환불 없이 복구하는지 확인한다.
- CI에서 빌드·필요한 테스트·이미지 빌드를 재현하고 서버 자동 배포와 구분한다.

위 항목은 구현 후 확인할 계획이며 실행 결과가 아니다. 초기 선택의 재검토 조건·대안·비용은 [MVP 설계 재검토 목록](../decisions/MVP%20%EC%84%A4%EA%B3%84%20%EC%9E%AC%EA%B2%80%ED%86%A0%20%EB%AA%A9%EB%A1%9D.md) R-14~R-19를 따른다.
