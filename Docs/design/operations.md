# 실행 환경과 관측

정리 기준: 2026-10-29. Gradle·application.yml·Docker Compose를 사용한다. 현재 코드는 Maven 초기 앱이며 전환과 전체 실행은 아직 구현하지 않았다.

<a id="runtime"></a>

## 버전·빌드·저장소

- Java 21과 Gradle Wrapper를 사용한다. 정확한 Gradle 버전은 현재 Spring Boot와의 호환을 확인해 전환 단계에서 고정한다. Gradle DSL은 Groovy를 초안으로 제안한다.
- 단일 저장소에 공동구매·결제·회원·알림·Gateway·Config·Eureka·PG Mock을 각각 실행 가능한 모듈로 둔다. 서비스별 독립 빌드·실행·배포 경계를 유지하고 엔티티·업무 로직을 공유하지 않는다.
- Spring Boot 4.0.x + Spring Cloud 2025.1.x를 호환 조합 후보로 채택한다. Resilience4j·Spring Security·Spring Session JDBC·Kafka 등 연동 라이브러리를 포함해 의존성 및 기동을 검증한 뒤 정확한 패치 버전을 고정한다. 후보 채택이 연동 검증 완료를 뜻하지 않는다.
- PostgreSQL·Kafka·Docker 이미지 등의 정확한 버전은 최소 실행 구성을 만들 때 확인·고정한다. 공통 설정·모듈 경로·이미지 빌드 방식도 해당 구현 설계에 포함한다.

초기에는 한 저장소에서 관련 변경과 검증을 추적하는 비용을 줄인다. 저장소·공유 코드 경계와 버전 재검토는 MVP 설계 재검토 목록 R-14를 따른다.

## 로컬 실행·설정·일괄 기동

| 영역 | 합의한 초기 구성 |
|---|---|
| 실행 기준 | Docker Compose 기반 로컬 재현 환경부터 완성 |
| PostgreSQL | 서버 하나에 서비스별 DB·계정 분리. 서비스는 자신이 소유한 DB에 접근 |
| Kafka | 초기 브로커 1개. 다중 브로커·복제 기반 장애 검증은 후속 범위 |
| Config | 같은 저장소의 파일로 일반 설정 관리 |
| 비밀값 | Git에서 제외하고 Compose secrets 등의 방식으로 서비스에 주입 |
| 실행 구분 | 개발용·전체 실행·검증용 프로필 구분 |
| 초기 CI | 빌드·테스트·이미지 빌드. 서버 자동 배포는 후속 범위 |

업무 DB·Outbox·소비 기록의 서비스별 소유권과 로컬 트랜잭션 경계는 유지한다. 단일 PostgreSQL 서버는 자원·장애 영향을 공유하며 서비스별 서버 독립성을 검증한 구성이 아니다. 필요가 관측되면 서비스별 DB 서버 분리를 비교한다. PG Mock의 저장 방식은 별도 테스트 대역 구현 설계에서 정한다.

Kafka 단일 브로커에서 acks=all·프로듀서 멱등성·소비 멱등성과 장애 후 재개를 검증할 수 있지만 복제 기반 고가용성의 근거로 사용하지 않는다. 복제 수·최소 동기 복제본 수·토픽 파티션 수 등은 해당 실행 구성에 맞춰 명시한다.

Eureka·Config·Gateway와 업무 서비스·PG Mock의 최소 연결을 구성하고 Prometheus·Grafana 등 관측 구성은 관측·검증 합의와 연결한다. 내부 API 비공개·서비스별 자격 증명·환경별 쿠키 설정은 인증 설계를 유지한다.

Compose 실행 정의는 루트 `compose.yml`에 둔다. CI 공급자·저장소 원격 위치·서버 배포 대상과 환경별 프로필의 상세 값은 구현 계획에서 정한다. 로컬 검증부터 가능한 구성으로 만들고 실제 CI·배포의 외부 작업은 해당 구현 요청을 따른다.

### YAML 설정과 전체 기동 계획

사용자 확인에 따라 애플리케이션의 기본 설정은 `application.yml`로 관리한다. 환경별 파일은 `application-local.yml`·`application-docker.yml`을 제안하며 구체적인 프로필과 설정값은 각 구현 계획에서 정한다.

전체 일괄 기동은 Docker Compose로 관리한다. 실행 정의는 루트 `compose.yml`에 두고 `docker compose up --build -d` 한 명령으로 애플리케이션·인프라를 기동한다. 각 서비스를 구현할 때 해당 이미지·Compose 정의·프로필을 함께 추가한다. 준비 상태를 healthcheck와 필요한 의존 조건으로 확인하고 서비스의 실행 중 재연결·복구는 별도로 검증한다. Config 최초 접속에 필요한 주소 등은 앱 시작 설정에서 제공해 Eureka와의 순환 의존을 피한다.

## 초기 운영값과 보관

| 항목 | 초기 기준 |
|---|---|
| 세션 유휴 만료 | 30분 |
| 내부 HTTP·PG 연결 제한시간 | 1초 |
| 내부 HTTP·PG 응답 대기 제한시간 | 5초 |
| Outbox 조회 | 10초 간격, 한 번에 최대 50건 |
| 미완료 업무 복구 조회 | 30초 간격 |
| Outbox 일시 장애 재시도 | 점진적으로 대기 증가, 최대 60초와 무작위 차이 적용 |
| 업무 관련 기록 | 초기에는 자동 삭제 없이 시작. 완료 기록 정리 정책은 후속 검토 |

위 값은 초기 구현·측정의 기준이며 성능 목표 달성이나 최적값을 뜻하지 않는다. 설정 파일에서 관리해 재현 가능한 조건으로 조정한다. HTTP 제한시간 초과는 상대의 업무 실패 확정이 아니며 기존 식별자로 실제 결과를 확인한다.

Outbox 재시도는 일시 장애·발행 여부 불명에 적용한다. 원인 수정이 필요한 오류의 영속 중단, 장기 일시 장애의 운영 알림과 자동 재시도 병행, 기존 메시지 ID·순번 유지 원칙을 바꾸지 않는다. 정확한 증가식·무작위 범위와 Kafka 클라이언트의 별도 제한시간은 구현 설계에서 정한다.

조회 최대 50건이 외부 호출 대기 동안 하나의 DB 트랜잭션을 유지한다는 의미는 아니다. 선점 기한·Kafka 전송 제한시간·단계별 실행 제한과 갱신을 작업 단위에 맞춰 함께 정한다. 만료 후 이전 실행자의 갱신 차단과 재시작 후 재개 원칙을 유지한다.

업무·시도·멱등성·Outbox·소비 및 운영 이력은 초기 자동 삭제 없이 보관하고 용량·조회 비용을 측정한 뒤 완료 기록의 정리 대안을 비교한다. 미완료·결과 불명 기록을 임의로 삭제하지 않는다. 이 방침은 30분 세션 만료를 없애거나 Kafka 로그의 무기한 보존을 확정하는 뜻이 아니다. 세션 정리 작업·Kafka 보존·로그 보관은 각각 구현 설계에서 정한다.

<a id="runtime-checks"></a>

## 실행 구성 검증

- Gradle Wrapper로 같은 버전·의존성을 재현하고 각 실행 모듈의 빌드·기동·연결을 확인한다.
- YAML 설정·프로필이 실제 반영되는지, Compose의 한 명령 기동과 준비 상태 의존성이 재현되는지 확인한다.
- Spring Boot·Cloud·Resilience4j 등 연동 호환을 확인하고 실제 버전·설정·이미지를 기록한다.
- 서비스별 DB 계정의 접근 범위와 업무·Outbox·소비 기록의 로컬 원자성을 확인한다.
- 개발·전체·검증 프로필의 실행 방법과 필요한 자원을 문서화한다.
- 비밀값의 Git 제외·서비스별 주입과 로그 미노출, 내부 API 접근 경계를 확인한다.
- Outbox·미완료 작업의 간격·조회 상한·재시도 대기와 재시작 후 이력 유지를 확인한다.
- HTTP 제한시간을 넘긴 PG Mock 거래를 결과 불명으로 추적해 중복 승인·환불 없이 복구하는지 확인한다.
- CI에서 빌드·필요한 테스트·이미지 빌드를 재현하고 서버 자동 배포와 구분한다.

위 항목은 구현 후 확인할 계획이며 실행 결과가 아니다. 초기 선택의 재검토 조건·대안·비용은 [MVP 설계 재검토 목록](../decisions/design-review.md) R-14~R-19를 따른다.

<a id="http-resilience"></a>

## HTTP 장애 대응 범위

Resilience4j는 일반적으로 애플리케이션 안에 포함하는 라이브러리다.

- 외부 결제 연동 등 HTTP 호출에 대해 타임아웃·Circuit Breaker·재시도 정책을 검토한다.
- 변경 요청의 재시도는 멱등성과 실제 처리 결과 확인 방법을 함께 검토한다.
- Kafka 소비 실패는 소비자 재시도·오류 처리·DLT 정책으로 다룬다.
- 타임아웃은 상대 시스템에서 업무 처리가 실패했다는 확정 증거가 아니므로 결과 확인·대사 방식을 정한다.

## 로그·메트릭·운영 알림

### 초기 구성과 추적

- JSON 로그 + Spring Boot Actuator·Micrometer + Prometheus·Grafana로 시작한다.
- 로그에 요청·공동구매·결제 시도·메시지 ID, 처리 단계, 오류 원인을 남겨 HTTP와 비동기 처리를 연결한다.
- 개별 ID는 로그에서 추적하고 메트릭 라벨로 사용하지 않는다. 메트릭은 서비스·작업 종류·결과처럼 제한된 값으로 집계한다.
- 별도 로그 수집 서버·분산 추적 서버는 초기 구성에 추가하지 않고, 분석의 어려움이 확인되면 비교한다.

### 관측할 지표

| 범위 | 확인할 내용 |
|---|---|
| HTTP | 요청 수·처리량, 응답시간 p95·p99, 예상하지 않은 오류율 |
| 애플리케이션·DB | JVM·GC, DB 연결 풀 사용·대기, 경합 분석에 필요한 DB 근거 |
| Outbox·Kafka | 미발행 수·최장 대기시간·재시도·중단, 소비 지연·실패, DLT·파티션 보류 |
| 비동기 업무 | 접수·완료·미완료 건수, 접수부터 최종 반영까지 시간 |
| Saga·승인·환불 | 미완료·결과 불명·보상 대기·실패 건수와 경과 시간 |

위 지표가 모두 자동 제공된다는 뜻은 아니다. 업무 지표는 영속 기록에 맞춰 구현하고 Kafka·DB 지표의 수집 경로, 대시보드, 수집 간격·보관 기간은 해당 구현 설계에서 정한다. 요청별 로그 추적과 전체 업무의 집계 관측을 함께 사용한다.

### 운영 알림

```text
애플리케이션·인프라 상태 → Prometheus → Alertmanager → 로컬 테스트 수신기
```

- 운영 알림 경로는 Kafka를 거치지 않도록 구성해 Kafka 장애 중의 전달도 검증한다.
- 자동 재시도 중단·장기 일시 장애·장시간 미완료·파티션 보류 등 기존 복구 설계의 상태를 관측한다.
- 같은 서비스·원인의 알림 묶음, 중복 억제·재알림은 기존 운영 개입 원칙을 유지한다.
- 사용자에게 보내는 결제 안내 등 업무 알림 서비스와 운영 장애 알림의 목적·경로를 구분한다.
- 실제 외부 수신 채널, 정확한 임계값·묶음 키·재알림 간격은 구현 시 정한다. 로컬 알림 수신 확인을 실제 외부 통지 검증으로 간주하지 않는다.
