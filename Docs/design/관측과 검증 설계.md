# 관측과 검증 설계

작성 기준: 2026-10-28 대화 내용 반영

상태: 로그·메트릭·운영 알림, 정합성·중복·장애 검증, k6 부하 조건·초기 목표의 3개 항목을 합의했다. 아래 수치는 측정 전 목표이며 코드 구현·테스트·성능 측정은 아직 수행하지 않았다. 큰 설계 결정 6묶음의 주요 방향은 합의했고, 다음 검토는 구현 순서와 단계별 완료 기준이다. 구현 계획의 새 제안과 실제 구현 착수는 별도로 구분한다.

## 1. 로그·메트릭·운영 알림

### 초기 구성과 추적

- JSON 로그 + Spring Boot Actuator·Micrometer + Prometheus·Grafana로 시작한다.
- 로그에 요청·공동구매·결제 시도·메시지 ID, 처리 단계, 오류 원인을 남겨 HTTP와 비동기 처리를 연결한다.
- 개별 ID는 로그에서 추적하고 메트릭 라벨로 사용하지 않는다. 메트릭은 서비스·작업 종류·결과처럼 제한된 값으로 집계한다.
- 별도 로그 수집 서버·분산 추적 서버는 초기 구성에 추가하지 않고, 분석의 어려움이 확인되면 비교한다.

### 관측할 지표

| 범위 | 확인할 내용 |
|---|---|
| HTTP | 요청 수·처리량, 응답시간 p95·p99, 예상하지 않은 오류율 |
| 애플리케이션·DB | JVM·GC, DB 연결 풀 사용·대기, 경합 분석에 필요한 DB 근거 |
| Outbox·Kafka | 미발행 수·최장 대기시간·재시도·중단, 소비 지연·실패, DLT·파티션 보류 |
| 비동기 업무 | 접수·완료·미완료 건수, 접수부터 최종 반영까지 시간 |
| Saga·승인·환불 | 미완료·결과 불명·보상 대기·실패 건수와 경과 시간 |

위 지표가 모두 자동 제공된다는 뜻은 아니다. 업무 지표는 영속 기록에 맞춰 구현하고 Kafka·DB 지표의 수집 경로, 대시보드, 수집 간격·보관 기간은 해당 구현 설계에서 정한다. 요청별 로그 추적과 전체 업무의 집계 관측을 함께 사용한다.

### 운영 알림

```text
애플리케이션·인프라 상태 → Prometheus → Alertmanager → 로컬 테스트 수신기
```

- 운영 알림 경로는 Kafka를 거치지 않도록 구성해 Kafka 장애 중의 전달도 검증한다.
- 자동 재시도 중단·장기 일시 장애·장시간 미완료·파티션 보류 등 기존 복구 설계의 상태를 관측한다.
- 같은 서비스·원인의 알림 묶음, 중복 억제·재알림은 기존 운영 개입 원칙을 유지한다.
- 사용자에게 보내는 결제 안내 등 업무 알림 서비스와 운영 장애 알림의 목적·경로를 구분한다.
- 실제 외부 수신 채널, 정확한 임계값·묶음 키·재알림 간격은 구현 시 정한다. 로컬 알림 수신 확인을 실제 외부 통지 검증으로 간주하지 않는다.

## 2. 정합성·중복·장애 검증

| 검증 범위 | 주요 확인 사항 |
|---|---|
| 업무 규칙 | 기준 수량·개인 한도, 상태 전이, 취소·성사·마감 조건, 승인 기한 |
| 실제 PostgreSQL·Kafka 연동 | 동시 수량 확보, 취소·성사·마감 경합, 업무와 Outbox의 원자성, 중복 소비·재전달 |
| PG Mock·전체 흐름 | 승인·환불과 결과 조회, 응답 유실, 늦은 승인, 환불 실패, 프로세스 중단·재시작·복구 |
| 인증·권한 | 세션 공유·만료, CSRF, 타인 접근, 신원 헤더 위조·내부 호출자 확인, 운영 권한 |

검증 결과는 HTTP 응답과 함께 DB 최종 상태·상세 기록과 수량 집계·PG Mock 거래 기록을 비교해 판정한다. 초과 확보·중복 승인·중복 환불·수량 이중 반영은 허용하지 않는다. 결과 불명은 실패로 단정하지 않고 확보를 유지하는지, 늦은 승인은 유효 결제에서 제외하고 환불로 이어지는지 확인한다.

장애 재현은 사전 데이터·주입 위치·중단 시점·복구 순서를 고정한다. 예를 들어 PG 승인 성공 후 응답 유실, DB 커밋 후 Kafka 소비 완료 통지 전 중단, 실패 파티션의 재시작·재할당을 구분한다. 재처리·재개·운영 종결은 기존 식별자·저장된 진행·실행권을 근거로 판단하고, 이전 담당자의 늦은 갱신이나 이력·한도 초기화가 없는지도 해당 구현 단계에서 확인한다.

의도한 장애 상태가 유지되는 동안에는 보류·미완료 기록과 알림이 기대 결과일 수 있다. 원인 수정·복구 이후의 완료 또는 근거 있는 운영 보류를 별도로 확인하고, 테스트 시나리오의 기대 결과와 실제 결과를 기록한다.

## 3. k6 부하 조건과 초기 목표

### 부하 모델

결제 접수의 새 요청 유입량을 고정하는 arrival-rate 방식으로 시작하고 단계적으로 올린다. 한 작업의 접수 요청과 결과 조회를 구분해 집계한다.

| 항목 | 합의한 초기 기준 |
|---|---|
| 기준 부하 | 새 결제 접수 초당 2건, 준비 운동 2분·측정 5분 |
| 증가 부하 | 초당 5건·10건으로 올려 적체·병목 관측 |
| 비교 시나리오 | 여러 공동구매에 분산 / 특정 공동구매에 집중 |
| 접수 API | 기준 부하에서 p95 500ms 미만, 예상하지 않은 오류율 1% 미만 |
| 업무 완료 | 기준 부하의 정상 결제에서 접수부터 최종 반영까지 p95 120초 이내 |
| 필수 기준 | 정합성 위반 0건, 종료 후 미완료 작업·실제 거래 대사 |

초기 수치는 성능 보장이나 측정 결과가 아니다. 증가 부하·장애 주입 조건은 기준 부하의 목표 평가와 구분해 병목·적체·복구 특성을 분석한다. 기존 Outbox 10초·최대 50건, 복구 30초 등 초기 설정은 유지하고 실제 적체와 업무 완료시간을 근거로 비교한다.

### 측정과 판정

- 정상 결제가 지속되도록 충분한 참여자·수량을 준비한다. 수량 부족·마감 등 정상 업무 거절과 시스템 오류를 구분하고 각각 건수를 남긴다.
- 접수 API 응답시간, 조회 요청 부하, 접수부터 최종 반영까지 걸린 시간을 따로 집계한다. 로그인·사전 데이터 준비와 조회가 결제 접수 성능으로 섞이지 않도록 측정 범위를 명시한다.
- 요청한 유입량과 실제 발생한 요청·접수·거절·완료·미완료 건수를 함께 남긴다. 부하 발생기의 자원 부족이나 실행 누락도 기록해 목표 부하가 가해졌는지 확인한다.
- 정상 완료 건의 시간 분포와 함께 미완료 건수·경과 시간을 기록한다. 빠르게 끝난 일부 건의 p95만으로 전체가 정상 처리되었다고 판정하지 않는다.
- 신규 유입 종료 후 남은 비동기 작업을 관찰하고 DB·PG Mock 거래와 대사한다. 관찰 종료 조건·상한과 결과 조회 간격은 스크립트 구현 시 명시하고, 잔여 미완료·불일치를 누락하지 않는다.
- 버전·CPU·메모리·서비스 구성·DB 연결 수·데이터 규모·폴링 및 재시도 설정·PG Mock 지연과 장애 조건을 기록한다. 같은 조건으로 변경 전후를 비교한다.

## 4. 구현 시 남길 검증 근거와 재검토

검증 기록에는 대상 버전·환경·사전 데이터·실행 명령·부하 및 장애 조건·기대 결과·관측 결과·DB 및 거래 대사·잔여 문제를 남긴다. 아직 수행하지 않은 검증은 계획으로 표시한다.

초기 선택의 목적·재검토 조건·대안·비용은 [MVP 설계 재검토 목록](../decisions/MVP%20%EC%84%A4%EA%B3%84%20%EC%9E%AC%EA%B2%80%ED%86%A0%20%EB%AA%A9%EB%A1%9D.md) R-20~R-22에서 관리한다. 로그 분석의 어려움, 검증 누락·불안정, 부하의 대표성·측정 환경의 한계를 관측하면 대안을 비교하며 개선 효과를 미리 단정하지 않는다.
