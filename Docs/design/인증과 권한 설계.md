# 인증과 권한 설계

작성 기준: 2026-10-28 대화 내용 반영

상태: 세션 저장·공유·로그아웃, Gateway 인증 확인·내부 신뢰·쿠키와 CSRF, 역할별 업무 권한의 초기 방향을 합의했다. 초기 구현은 Spring Security + Spring Session JDBC이며 Redis 전환은 후속 검토 후보로 관리한다. 코드 구현·실행 검증은 수행하지 않았다.

## 1. 세션 저장·공유·만료·로그아웃

- 회원 서비스가 세션을 소유하고 자신의 PostgreSQL에 Spring Session JDBC로 저장한다. 여러 회원 서비스 인스턴스는 같은 세션 저장소를 사용한다.
- 로그인 성공 시 세션 ID를 변경하고 로그아웃 시 현재 세션을 무효화한다. 유휴 만료의 초기값은 이후 실행 환경 합의에서 30분으로 정했다. 테이블·정리 주기·저장 설정은 구현 설계에서 구체화한다.
- Gateway와 다른 업무 서비스가 회원 DB의 세션 테이블을 직접 읽지 않는다. 인증 확인은 회원 서비스의 내부 API를 사용한다.
- 세션 조회·갱신은 DB 부하에 추가된다. 초기에는 기존 PostgreSQL을 활용해 별도 저장소의 실행·장애 대응 구성을 줄인다.
- Redis 도입은 아직 확정하지 않았다. 세션 접근 부하·업무 DB 자원 경합·인증 지연을 관측한 뒤 JDBC 최적화와 Redis 전환을 비교한다. Redis의 추가 운영·장애 대응 비용과 전환 시 기존 세션의 처리도 함께 검토한다. 상세 재검토 항목은 MVP 설계 재검토 목록 R-11을 따른다.

로그아웃·세션 만료는 이후 인증 확인에서 반영한다. 이미 인증을 마치고 실행 중인 요청이나 접수 완료한 결제·환불·Saga까지 자동 취소하는 의미가 아니다. 업무의 취소 가능 여부와 후속 처리에는 기존 업무 규칙을 적용한다.

## 2. Gateway 인증 확인과 내부 신뢰

보호된 외부 요청은 Gateway가 회원 서비스의 내부 인증 확인 API를 호출해 세션 유효성·현재 역할·계정 상태를 확인한 뒤 전달한다. 로그인 등 공개적으로 접근해야 하는 경로는 보호된 업무 경로와 구분하고 구체적인 목록은 구현 설계에서 정한다.

Gateway는 외부에서 보낸 사용자 신원·역할 헤더를 제거하고 검증한 회원 ID·역할을 내부 요청 정보로 전달한다. 인증 정보가 없거나 유효하지 않으면 보호된 업무 요청을 허용하지 않는다. 인증 확인 장애를 유효한 세션으로 추정해 통과시키지 않으며 인증 거절과 확인 불가 장애를 구분해 응답 계약에 반영한다.

내부 API는 외부에 공개하지 않고 서비스별 호출 자격 증명으로 호출자를 확인한다. 업무 서비스는 임의의 외부 요청이 보낸 신원 헤더를 신뢰하지 않으며 허용된 내부 호출자를 확인한다. 호출 자격 증명 형식·전달 방식·교체·보관과 네트워크 구성은 관련 구현 설계에서 구체화한다. 세션 쿠키·내부 자격 증명을 로그에 기록하지 않는다.

이 방식은 회원 서비스에 인증 책임을 모으는 대신 보호된 요청마다 내부 호출과 세션·회원 조회가 추가된다. 인증 확인 실패가 보호된 요청에 영향을 주는 비용과 최적화 후보는 재검토 목록 R-12를 따른다. 인증 결과의 별도 캐시는 현재 합의에 포함하지 않는다.

## 3. 쿠키와 CSRF

세션 쿠키는 HttpOnly·SameSite=Lax를 적용하고 HTTPS 환경에서는 Secure를 적용한다. 로컬 HTTP 개발 환경과 HTTPS 환경의 쿠키 설정을 구분해 관리하며 구체적인 이름·경로·도메인·교차 출처 정책은 구현 설계에서 정한다.

쿠키 인증의 변경 요청에는 로그인·로그아웃을 포함해 CSRF 토큰 검증을 적용한다. SameSite 설정만으로 CSRF 검증을 대체하지 않는다. 테스트 클라이언트와 k6도 토큰 발급·세션 쿠키 유지·변경 요청의 토큰 전달을 재현한다.

Gateway를 통과하는 업무 변경 요청도 실제 업무 실행 전에 검증한다. 회원 서비스가 소유한 세션과 토큰 확인을 Gateway의 인증 확인 흐름에 연결하고 로그인·로그아웃은 회원 서비스의 보안 처리와 연결한다. 발급 경로·전달 헤더·검증 배치·토큰 갱신과 내부 확인 API의 요청 계약은 구현 설계에서 구체화한다. API 요청 멱등성 키는 인증·CSRF·권한 검사를 대체하지 않는다.

## 4. 역할과 업무 권한

Gateway는 공통 인증·역할 검사를 수행하고 데이터를 소유한 서비스가 역할·소유 관계·현재 업무 상태를 함께 확인해 최종 허용 여부를 판단한다. 회원 서비스의 인증 확인은 현재 역할·계정 상태를 확인해 다음 확인부터 변경을 반영한다. 권한 정보를 세션 생성 당시 값만으로 계속 허용하지 않는다.

| 역할 | 허용할 업무 범위 |
|---|---|
| 구매자 | 본인 참여·결제 시도 조회와 허용된 시점의 취소 |
| 판매자 | 본인 공동구매 등록·게시와 임시 저장 중 수정 |
| 운영자 | 복구 상태 조회·재처리·재개·근거를 갖춘 종결 |

운영자도 구매 확정·환불 완료 등 업무 상태를 임의로 덮어쓰지 않는다. 기존 운영 요청·실행권·복구 회차·이력·종결 근거 규칙을 적용한다. 운영자 권한은 초기 관리 절차로 부여하며 일반 회원이 스스로 운영자 권한을 설정하는 API는 두지 않는다. 정확한 역할 코드·여러 역할 보유·운영 권한 부여 절차는 구현 설계에서 정한다.

공동구매의 참여·결제 접수 등 기존 구매자 기능은 그대로 유지한다. 위 표는 인증·권한 경계를 정리한 것이며 기존 기능을 축소하지 않는다. 대상의 소유 관계와 상태 검사는 실제 업무를 변경하는 트랜잭션 안에서 기존 잠금·경합 규칙과 함께 적용한다.

## 5. 구현 후 검증할 항목

- 여러 회원 서비스 인스턴스 사이에서 같은 세션으로 인증하고 재시작 후 저장된 세션을 확인한다.
- 로그인 시 ID 변경, 유휴 만료·현재 세션 로그아웃 후 인증 거절을 확인한다.
- 역할·계정 상태 변경 뒤 다음 인증 확인에 새 조건이 적용되는지 확인한다.
- 외부 신원·역할 헤더 위조, 내부 API 직접 접근과 유효하지 않은 서비스 자격 증명을 거절하는지 확인한다.
- 회원 서비스·세션 DB 장애를 인증 성공으로 처리하지 않는지 확인한다.
- 로그인·로그아웃·업무 변경의 CSRF 누락·오류와 유효 토큰을 검증한다. 멱등성 키가 있어도 검증을 생략하지 않는다.
- 타인의 참여·결제 시도 조회·취소와 판매자의 타인 공동구매 수정·게시를 막는지 확인한다.
- 구매 확정 이후 취소와 게시 이후 판매 조건 수정이 기존 규칙대로 거절되는지 확인한다.
- 운영 요청의 역할·대상·사유·이력을 검사하고 업무 상태의 임의 변경을 막는지 확인한다.
- 세션 조회·갱신량·인증 확인 지연·DB 부하와 업무 API의 전체 응답시간을 함께 측정한다.

위 항목은 검증 계획이며 테스트 결과가 아니다. 세부 API·시간·설정은 해당 구현 설계에 포함한다.
