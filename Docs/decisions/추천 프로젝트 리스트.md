# 취업용 Spring MSA 개인 프로젝트 추천 리스트

작성 기준: 2026-10-24 대화 내용

## 현재 선택 결과

- **목표 달성형 공동구매로 최종 주제를 확정했다.**
- 범위는 구현·부하 테스트·트러블슈팅·트레이드오프 검토·설계 및 구현 변경·재검증까지 포함한다.
- 이번 세션은 큰 윤곽 정리까지이며, 상세 설계는 다음 세션부터 시작한다.
- 최신 방향과 다음 세션 인계 내용은 [프로젝트 개요](../%ED%94%84%EB%A1%9C%EC%A0%9D%ED%8A%B8%20%EA%B0%9C%EC%9A%94.md)를 기준으로 확인한다.
- 아래 후보와 초기 추천안은 주제를 검토했던 기록으로 보관한다. 서비스 구성·결제 정책 등 개별 제안은 확정된 공동구매 설계가 아니다.

## 1. 배경과 추천 기준

- Spring 기반 웹 애플리케이션 개발 경력 약 5년.
- 취업을 위한 개인 프로젝트이며, 후보 검토 후 목표 달성형 공동구매를 선택함.
- Spring Cloud·Kafka·Saga·세션/쿠키·Docker Compose·Prometheus·Grafana·k6를 적용할 계획.
- 아래 추천은 기술 적용의 자연스러움, 개인 개발 범위, 면접에서 설명할 설계·검증 포인트를 기준으로 한 판단임.
- 채용 성과를 보장하거나 실제 채용 공고를 분석해 매긴 순위는 아님.

관련 문서: 설계 방법 (로컬 전용: `Docs/process/설계 방법.md`), [기술 범위](../design/%EA%B8%B0%EC%88%A0%20%EB%B2%94%EC%9C%84.md)

## 2. 추천 주제 비교

| 주제 | 핵심 업무 흐름 | Saga 보상 예시 | 설명할 설계 포인트 | 범위·난이도 |
|---|---|---|---|---|
| **한정 수량 상품 예약 주문** | 재고 예약 → 결제 → 주문 확정 | 결제 취소, 재고 예약 해제 | 재고 동시성, 멱등성, 비동기 처리, 장애 복구 | 초기 1순위 추천안. 최종 미선택 |
| **공연·클래스 좌석 예약** | 좌석 선점 → 결제 → 예약 확정 | 좌석 선점 해제, 결제 취소 | 중복 예약 방지, 선점 만료, 결제와 만료의 경합 | 좌석별 상태 관리가 추가됨 |
| **B2B 발주·출고 요청** | 발주 접수 → 재고 할당 → 출고 접수 | 재고 할당 해제, 출고 요청 취소 | 업무 상태 전이, 외부 시스템 연동, 재처리 | 실제 업무 규칙을 명확하게 정의해야 함 |
| **목표 달성형 공동구매 — 최종 선택** | 참여 → 모집 종료 → 성사·무산 → 후속 처리 | 무산 시 결제 정책에 따른 취소·환불 | 마감 처리, 대량 보상, 장시간 유지되는 업무 흐름 | 상세 결제 정책과 초기 범위는 다음 세션에서 결정 |

기존 업무 경험이 유통·물류·기업 업무 시스템과 관련 있다면 B2B 발주·출고도 유력한 후보다. 실제 업무 경험에서 나온 예외 규칙과 설계 이유를 설명할 수 있다는 장점이 있다.

## 3. 초기 추천안: 한정 수량 상품 예약 주문·결제·취소 시스템 — 미선택

### 프로젝트 개요

판매 시작 시간이 정해진 한정 수량 상품을 예약 주문한다. 재고와 결제는 각각의 서비스에서 처리하고, 중간 장애가 발생해도 주문 상태를 복구한다.

초기 범위 제안:

- 단일 판매자.
- 주문당 상품 한 종류.
- 수량 기반 재고.
- 주문 접수·상태 조회·취소.
- 결제 시뮬레이터를 통한 승인·거절·응답 유실·취소 실패 재현.
- 세션·쿠키 로그인.
- 메트릭 대시보드와 부하·장애 테스트.

이 범위와 아래 서비스 구성은 추천안이며 사용자 확정 사항은 아니다.

### 핵심 서비스 구성안

| 서비스 | 책임 |
|---|---|
| 주문 | 주문 접수·상태 관리, Saga 진행 상태 저장·보상 조정 |
| 상품·재고 | 상품 정보, 판매 가능 수량, 재고 예약·확정·해제 |
| 결제 | 승인·취소·결과 조회, 결제 시뮬레이터 연동 |

알림 또는 판매 집계 소비자는 확장 후보로 둔다. 주문 확정 이벤트를 각 목적에 맞게 독립적으로 처리하는 구조를 보여줄 수 있다.

상품과 재고는 먼저 함께 두고, 독립적인 변경·확장 필요성이 생겼을 때 분리를 검토한다. 로그인 처리 주체와 세션 저장·공유 구조는 별도로 설계한다.

### Saga 구성 제안

초기 추천은 주문 서비스 내부의 Orchestration이다.

```text
주문 접수
  → 재고 예약
  → 결제 승인
  → 재고 예약을 판매 확정으로 전환
  → 주문 확정
```

주문 서비스는 Kafka로 명령을 보내고 처리 결과를 받아 다음 단계 또는 보상을 결정한다. 진행 상태를 DB에 보관하고 재시작 후 처리 재개 방법을 설계한다.

| 상황 | 처리 방향 |
|---|---|
| 재고 예약 실패 | 주문 거절 |
| 결제 승인 거절 | 재고 예약 해제, 주문 취소 |
| 결제 승인 후 재고 확정이 최종적으로 실패 | 결제 취소와 재고 상태 정리 |
| 결제 응답 유실 | 실제 결제 상태 확인 후 진행·보상 판단 |
| 보상 실패 | 보상 대기 상태 저장, 재시도·재처리 |

예시 흐름은 상세 설계의 출발점이다. 타임아웃을 확정 실패로 취급하지 않고, 이미 처리된 작업의 결과와 늦게 도착한 메시지를 확인하도록 설계한다. 각 명령과 보상은 중복 실행에도 안전해야 한다.

### 핵심 구현·검증 과제

| 과제 | 구현·검증 포인트 |
|---|---|
| 재고 동시성 제어 | 조건부 갱신·락 등 선택 근거, 경합 시 초과 판매 방지 |
| Outbox | DB 커밋 후 메시지 발행 전 프로세스 종료에도 발행 복구 |
| 소비 멱등성 | 같은 명령·이벤트가 반복되어도 중복 예약·결제 방지 |
| 예약 만료 | 만료와 결제 성공이 경합하는 경우의 상태 전이 |
| 보상 복구 | 취소 실패 재시도, 미완료 Saga 추적, 운영 재처리 |
| 관측 | 업무 ID·Saga ID로 진행·실패·보상을 연결해 확인 |
| 부하 검증 | 요청 처리량과 전체 업무 완료 성능, 정합성 함께 측정 |

### 재현할 테스트 시나리오

1. 재고 100개에 주문 요청 1,000건을 보내 초과 판매 여부를 검증한다.
2. 같은 이벤트를 여러 번 전달해 업무 결과 중복 반영 여부를 확인한다.
3. DB 반영 직후 프로세스를 종료하고 재시작해 발행·소비 복구를 확인한다.
4. 결제 승인은 성공시키고 응답만 유실해 결과 조회·대사를 검증한다.
5. 재고 예약 만료 시점과 결제 성공 시점을 겹치게 한다.
6. 보상 중 결제 서비스를 중단한 뒤 복구해 미완료 보상의 재개를 확인한다.

위 수치는 테스트 조건 예시이며 측정 결과가 아니다. 실제 실행 환경·부하 조건·성공 기준과 결과를 함께 기록한다.

### 모니터링과 포트폴리오 산출물

- k6: 로그인·쿠키 유지, 주문 부하, 상태 조회 시나리오.
- Prometheus·Grafana: HTTP 응답시간, 전체 주문 완료 시간, 보상 완료 시간, 미완료 Saga 수, Consumer Lag 등.
- 설계 문서: 서비스 분리 근거, 상태 전이·시퀀스, API·이벤트 계약.
- 검증 자료: 장애 재현 절차, 테스트 결과, 대시보드, 개선 전후 비교와 한계.

프로젝트 제목 예시:

> Kafka 기반 한정 수량 주문 시스템: 재고 동시성 제어와 Saga 보상·장애 복구

## 4. 대안: 공연·클래스 좌석 예약

특정 공연 또는 클래스의 좌석을 일정 시간 선점한 뒤 결제로 확정하는 시스템이다.

- 핵심 흐름: 좌석 선점 → 결제 → 예약 확정.
- 보상: 좌석 선점 해제, 결제 취소.
- 주요 과제: 동일 좌석 중복 선점 방지, 선점 만료, 만료 직전 결제 결과 처리.
- 시연 장점: 좌석 상태와 중복 예약 여부를 직관적으로 확인할 수 있음.
- 범위 제안: 단일 공연 또는 클래스, 단순 좌석 배치, 결제 시뮬레이터부터 시작.

예약·동시성 문제에 관심이 있고 화면에서 상태를 보여주는 시연을 중요하게 생각할 때 적합하다.

## 5. 대안: B2B 발주·출고 요청

기업 고객의 발주를 접수하고 재고를 할당한 뒤 외부 물류 시스템에 출고 요청을 전달하는 시스템이다.

- 핵심 흐름: 발주 접수 → 재고 할당 → 출고 요청 접수.
- 보상: 출고 전 요청 취소, 재고 할당 해제.
- 주요 과제: 주문·출고 상태 전이, 외부 응답 유실, 중복 요청 방지, 재처리.
- 시연 장점: 외부 시스템 장애와 운영 복구 절차를 설명하기 좋음.
- 범위 제안: 단일 창고, 단순 발주 단위, 외부 물류 시스템 시뮬레이터.

실제 출고·배송이 진행된 이후에는 단순 요청 취소와 다른 반품·회수 업무가 될 수 있으므로, 초기 보상 가능 경계를 출고 요청 단계까지 명확하게 정의한다.

## 6. 최종 선택: 목표 달성형 공동구매

모집 기간 안에 목표 수량 또는 참여 조건을 충족하면 주문을 확정하고, 무산되면 취소·환불하는 시스템이다.

- 핵심 흐름의 윤곽: 참여 → 모집 종료 → 성사·무산 판단 → 결과에 따른 후속 처리. 결제 시점은 다음 세션에서 결정.
- 보상 후보: 결제 정책에 따라 무산된 참여 건의 결제 취소·환불.
- 주요 과제: 마감 시점의 참여 경합, 대량 후속 처리·보상, 장시간 유지되는 업무 흐름, 실패 건 재처리.
- 시연 장점: 모집 마감 전후 상태와 대량 보상 진행을 보여줄 수 있음.
- 범위 제안: 단일 모집 상품, 단순 목표 조건, 결제 시뮬레이터.

모집 종료까지 결제 승인·실결제 중 어떤 상태를 유지할지, 취소와 환불의 조건을 어떻게 정할지 먼저 결정한다. 개인 프로젝트에서는 업무 규칙을 좁혀 시작하는 것이 좋다.

## 7. 최종 주제 선택 기준

- 여러 서비스가 관여하는 핵심 업무를 한 문장으로 설명할 수 있는가?
- 중간 실패 시 보상할 작업과 결과를 확인해야 할 작업이 명확한가?
- 동시 요청이 경합하는 지점이 있는가?
- 메시지 중복·지연·응답 유실을 의미 있게 재현할 수 있는가?
- 개인이 핵심 흐름과 복구까지 완성할 수 있는 범위인가?
- 본인의 기존 업무 경험과 연결해 설계 이유를 설명할 수 있는가?

최종 주제는 목표 달성형 공동구매로 확정했다. 상세 업무 규칙과 설계는 다음 세션부터 진행하며, 구현·테스트·개선 과정의 전체 범위는 프로젝트 개요에 정리했다.
