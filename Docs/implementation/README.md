## 단계별 진행

1. `plan/`에 목표·현재 상태·관련 설계·범위·변경 예정 파일·선택 근거·대안·검증 방법·완료 기준을 작성한다.
2. 사용자가 읽고 수정 의견을 주면 같은 계획을 먼저 변경하고 반영 범위를 공유한다. 계획 수정 요청만으로 구현에 착수하지 않는다.
3. 사용자가 진행을 요청한 단계의 구현·필요한 검증을 진행한다. 핵심 코드는 [직접 작성 방식](#guided-coding)에 따라 기준 구현 검증 → 사용자 작성 → 리뷰·재검증까지 마친다. 합의한 범위 안의 세부 작업마다 승인을 반복하지 않는다.
4. 상위 `implementation/`에 같은 번호의 기록으로 실제 변경·실행 명령·검증 결과·남은 작업을 남기고 계획과 서로 연결한다. 결과 문서에는 사용자 직접 테스트 방법을 포함하고, 외부 HTTP 처리나 인증·권한 경계가 달라졌으면 [HTTP 요청 흐름](#http-request-flow)을 추가한다.
5. 해당 단계에서 도입·변경한 기술·기능의 학습 문서를 아래 [구현 완료 후 학습 문서](#implementation-explanations) 기준으로 자동 생성·갱신한다.
6. 결과와 갱신한 학습 문서를 공유하고 다음 단계는 사용자의 진행 요청을 따른다.

계획 파일명은 `001-<english-task-name>.md`를 사용한다. 상태는 `검토 대기`, `진행 합의`, `구현 중`, `완료`로 관리하고 진행을 합의한 범위와 계획에서 달라진 내용을 기록한다. 실제로 수행하고 검증한 범위만 완료로 표시한다.

## 설계·구현 분리와 토큰 관리

2026-11-03 사용자 합의. 설계 채팅을 유지하고 구현은 단계별 새 채팅으로 나누는 것을 기본으로 한다. 사용자의 명시적인 범위·채팅 선택을 우선한다.

| 구분 | 작업 범위 | 전달할 결과 |
|---|---|---|
| 설계 채팅 | 관련 정책·코드·공식 자료를 필요한 만큼 확인하고 선택·대안·완료 기준 정리. 설계 요청만으로 코드·의존성·실행 설정을 바꾸거나 서비스를 기동하고 빌드·테스트하지 않음 | 같은 단계 계획의 실행 요약·상세 설계. 미합의 추천은 검토 대기로 표시 |
| 구현 채팅 | 요청한 확정 계획의 구현·필요한 검증·문제 수정·결과 기록. 합의 범위의 세부 작업마다 승인을 반복하지 않음 | 같은 번호의 결과 문서·직접 테스트 방법·관련 학습 문서·짧은 인계 |

읽기와 기록의 기준:

1. 재개 시 `AGENTS.md`·짧은 인계·해당 계획의 실행 요약을 우선 확인한다. 추가 설계·코드·과거 기록은 현재 작업에 필요한 부분만 읽는다. 읽기 분량을 고정해 필요한 사실 확인을 생략하지 않는다.
2. 각 계획 앞에는 20~30줄 안팎의 실행 요약을 둔다. 상태·목표·포함/제외 범위·기존 합의와 추천 선택·지켜야 할 경계·관련 파일·검증/완료 기준·미정 사항을 담는다. 상세 설계와 충돌하면 구현 전에 같은 계획에서 정리한다.
3. 계획은 범위·선택·완료 기준, 결과 문서는 실제 변경·실행 근거·미검증 항목을 관리한다. 인계는 현재 단계·계획/결과 링크·브랜치·마지막 확인한 PR/CI·다음 작업만 10~20줄 안팎으로 유지한다. 전체 진행 정리와 과거 대화는 필요할 때 참고한다.
4. 설계 내용은 설계 채팅에서 합의하고 구현 채팅에는 확정 계획을 전달한다. 구현 중 범위·업무 규칙·소유권·완료 기준을 바꿔야 하는 충돌이 드러나면 근거·영향·대안을 알리고 관련 작업을 보류한다. 영향을 받지 않는 승인된 작업은 계속한다. 범위 안의 구현 세부 선택은 진행한다.
5. 설계만 하는 작업에서는 문서 형식·링크 등 해당 변경을 확인한다. 구현에서는 변경 영향에 맞는 검증과 단계의 필수 완료 검사를 수행한다. 관련 변경·실패·환경 변화·미해결 우려가 없으면 이미 유효한 검증을 반복하지 않는다.
6. 원격 상태·컨테이너 상태·전체 빌드를 매 응답마다 조회하지 않는다. 구현 착수·브랜치 기준 결정·PR 작업이나 실제 상태가 필요한 판단에서 최신 상태를 확인하고, 이전 근거에는 확인 시점과 대상 SHA를 표시한다.
7. 채팅에는 선택·결과·남은 문제를 간결하게 적고 긴 로그는 필요한 부분과 위치만 연결한다. 이미 답한 개념 설명과 문서 내용을 반복해 붙이지 않는다.
8. 2026-11-04 사용자 추가 규칙: PR 생성·업데이트와 push 후에는 CI 완료 대기·반복 조회를 하지 않는다. PR 링크·최종 head·Checks 링크와 조회 당시 확인한 상태만 안내하고 종료하며, 조회하지 않은 CI는 미확인으로 표시한다. 사용자가 결과를 확인한 뒤 문제를 알려주거나 CI 확인·대기를 별도로 요청하면 해당 범위를 진행한다. 착수·브랜치 기준 판단에 필요한 최신 상태 확인과 로컬 필수 검증은 유지한다.

설계 동의와 구현 착수 요청은 구분한다. 사용자가 구현을 요청하면 해당 단계의 필요한 수정·검증·기록까지 완료한다.

## 핵심 코드 직접 작성

2026-11-04 사용자 요청. AI가 핵심 코드의 동작하는 기준 구현을 먼저 작성·검증하고, 해당 코드를 같은 파일의 참고 주석으로 전환한다. 사용자는 주석을 보며 표시된 실행 구간에 직접 따라 작성한다. 대상 선정과 파일·클래스·메서드·작성 위치·순서는 AI가 안내하며, 사용자가 지정한 범위가 있으면 우선한다. 이 방식의 합의만으로 미확정 설계의 채택이나 구현 착수를 뜻하지 않는다.

### 진행 순서

1. 계획에 직접 작성할 핵심 구간·학습 목적·확인할 동작을 표시한다. AI는 상태 전이·트랜잭션 경계·동시성·멱등성·오류 처리처럼 실제 선택과 실패 조건이 드러나는 부분을 고르고, 설정·의존성·반복 코드는 구현한다.
2. 구현 요청을 받은 범위의 기준 코드를 정상 실행 가능한 상태로 작성하고 필요한 테스트·실행 검증을 수행한다. 검증하지 않은 코드를 검증된 참고 코드로 표시하지 않는다.
3. 2026-11-04 사용자 변경 요청: 구현별 Step을 기본 6개씩 동시에 열어 한 번에 작성할 수 있게 한다. 남은 구간이 6개 미만이면 남은 구간을 함께 준비하며, 이미 작성·검증한 코드는 다시 비우지 않는다. 각 Step은 한 메서드 또는 연관 블록으로 구분한다. 클래스·import·메서드 선언과 주변 연결은 유지하고, 해당 핵심 구현을 같은 파일의 `//` 참고 주석으로 둔다. `LEARN-01` 같은 구간 표식으로 참고 코드와 입력 위치를 구분한다. 그대로 주석을 해제하는 대신 그 아래에 직접 입력할 위치를 제공한다.
   - 각 `LEARN-XX 직접 작성 위치` 바로 위에 메서드의 호출 위치, 호출 시점이나 조건, 그 흐름에서 맡는 역할을 한두 줄의 `//` 주석으로 적는다.
4. 활성 구현을 비운 메서드는 `throw new UnsupportedOperationException("작성 대기: LEARN-01");`처럼 작성 대기를 드러낸다. 빈 메서드·항상 성공하는 반환값·기존 구현 우회로 기능이 정상인 것처럼 보이게 하지 않는다. 주석 범위는 컴파일 가능한 메서드 본문 중심으로 고르고, 생성자 초기화 등으로 컴파일이 불가능하면 구간 경계를 조정한다.
5. 사용자에게 파일 링크·클래스/메서드·표식, 따라 작성할 범위, 핵심 이유, 제거할 임시 예외, 정상·실패 확인 방법을 안내하고 **사용자 작성 대기**로 인계한다. 사용자 입력이 필요한 구간을 AI가 대신 채우지 않으며, 직접 작성과 무관한 승인된 작업은 진행할 수 있다.
6. 사용자가 작성 완료를 알리면 실제 파일 변경을 리뷰하고 필요한 검증을 수행한다. 핵심 부분의 오류는 위치·이유·수정 방향을 안내해 사용자가 고치도록 한다. 사용자가 수정을 맡기면 해당 범위를 수정한다. 한 묶음의 작성 결과를 함께 리뷰·검증하고 정상·주요 실패 동작 확인 후 다음 묶음을 준비한다.
7. 재작성한 실행 코드로 검증을 마치면 중복 참고 주석과 임시 표식을 정리한다. 유지할 학습 설명은 `Docs/explanations/`로 연결한다. 모든 직접 작성 구간·필수 검증을 마친 뒤 단계 완료와 PR용 산출물을 정리한다.

### 상태와 검증 기록

- 계획의 상위 상태는 기존 기준을 쓰고, 구현 중의 하위 상태를 **기준 구현 검증 완료 → 사용자 작성 대기 → 재작성 코드 검증 완료**로 기록한다. 현재 작성할 구간·남은 구간·다음 행동을 결과 문서와 짧은 인계에서 찾을 수 있게 한다.
- 주석 전환 전의 테스트 성공은 당시 기준 구현의 근거다. 작성 대기 상태의 현재 소스가 같은 테스트를 통과한다고 표시하지 않는다. 비워둔 로직의 테스트는 실패할 수 있으며 이를 건너뛰거나 기대값을 낮춰 통과시키지 않는다.
- 사용자 작성 대기는 미완료 학습 작업이다. 최종 기능 완료·전체 테스트 성공은 재작성한 활성 코드 기준으로 판단한다. PR용 코드에는 작성 대기 placeholder와 중복 정답 주석을 남기지 않는다.

## HTTP 요청 흐름

외부 HTTP 요청의 처리나 인증·권한 경계가 달라진 단계는 결과 문서의 구현 설명 뒤에 `## HTTP 요청 흐름`을 둔다. GitHub에서 렌더링되는 Mermaid `sequenceDiagram`으로 실제 구현을 따라 그린다. [009 게시·공개 조회 예시](009-group-purchase-product.md#http-request-flow)

- 처리 경계가 다른 대표 요청을 고른다. 공개 조회와 보호 요청처럼 인증 경로가 다르면 그림을 나눈다. 여러 API가 같은 경로를 쓰면 대표 요청으로 설명하고 해당 API들을 함께 적는다.
- 외부 HTTP 메서드·경로, 필요한 입력·헤더 이름, Gateway와 서비스 사이의 호출, 인증·인가를 판단하는 위치, 해당 요청의 DB 읽기 또는 커밋과 응답을 표시한다. 쿠키·토큰·자격 증명은 이름만 쓴다.
- 정상 흐름과 주요 실패를 함께 보여 준다. 요청이 멈추는 구성요소, 응답 상태, 호출이 이어지는지 또는 DB 변경이 남는지 드러내고, 세부 오류는 본문이나 직접 테스트 절차로 연결한다.
- 그림을 해당 시점의 코드·라우트와 대조한다. 기준 구현 검증 후 직접 작성 대기 상태라면 그림의 대상이 검증한 기준 구현임을 표시한다.

## 사용자 직접 테스트 방법

2026-10-30 사용자 요청으로 추가했다. 매 단계의 구현·테스트 결과를 공유할 때 사용자가 직접 재현할 수 있도록 결과 문서와 최종 안내에 테스트 경로를 제공한다.

- 준비 사항: 필요한 도구·버전, 작업 디렉터리, 사전 실행 서비스·포트·환경변수·테스트 데이터. 비밀값은 실제 값 대신 주입 방법을 설명한다.
- 실행 순서: 사용 환경에 맞는 복사 가능한 명령과 요청 예시를 제공한다. 여러 터미널이 필요하면 각각 구분한다.
- 기대 결과: 응답 상태·핵심 본문·로그 또는 저장 상태와 성공/실패 판단 기준을 적는다. 정상 흐름과 해당 단계의 주요 실패 상황을 포함한다.
- 종료·복구: 프로세스 종료, 임시 설정 원복, 테스트 데이터 정리와 재실행 방법을 적는다. 데이터 삭제가 필요한 명령은 영향 범위를 표시한다.
- 검증 상태: AI가 실제 실행해 확인한 항목과 사용자가 실행할 절차·환경 제약으로 미검증한 항목을 구분한다. 자동 테스트 결과만으로 수동 절차까지 검증했다고 표시하지 않는다.

후속 계획에도 사용자 직접 테스트 범위와 기대 결과를 완료 기준에 포함한다. 이미 승인한 구현 범위의 테스트 안내를 위해 별도 승인을 반복하지 않는다.

## 구현 완료 후 학습 문서

2026-11-04 사용자 추가 규칙. 단계 또는 요청받은 스텝의 구현·검증을 마치면 별도 설명 요청 없이 `Docs/explanations/`의 관련 주제 문서를 자동 생성·갱신한다. 기존 Config Server·Eureka Server·API Gateway 학습 문서의 설명 방식을 따른다.

- 대상: 이번 구현에서 도입하거나 역할·동작이 달라진 기술·기능. 같은 주제 문서가 있으면 해당 부분을 갱신하고, 없으면 영문 kebab-case 파일명으로 새 문서를 만든다.
- 필수 내용: 무엇이며 어떤 문제를 해결하는지 기본 개요 1~2문장, 현재 프로젝트에서 담당하는 역할, 실제 구현을 따라가는 적용 예시 1개. 이해에 필요한 기본 용어와 주의점은 짧게 덧붙인다.
- 구현 연결: 관련 코드·설정 위치와 해당 단계 결과·직접 테스트 문서를 연결한다. 결과 문서와 최종 안내에서도 생성·갱신한 학습 문서를 연결한다.
- 사실 구분: 현재 구현·검증한 범위를 기준으로 설명하고, 학습용 가정·미구현 계획·미검증 동작은 명시적으로 구분한다. 실제 비밀값은 기록하지 않는다.
- 문서 책임: 긴 실행 로그·검증 근거는 결과 문서에 유지하고 학습 문서에는 역할과 적용 흐름을 설명한다. 기존 설명을 복사해 별도 문서로 늘리지 않는다.
- 보관: `Docs/explanations/`의 기존 Git 제외 정책을 유지한다. 사용자가 대화로만 설명하거나 문서 작성을 제외하라고 명시하면 그 요청을 우선한다.
