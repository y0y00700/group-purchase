## 실행 요약

- 판매자가 공동구매와 상품 정보를 함께 임시 저장·수정·게시하고, 구매자가 게시된 정보를 조회할 수 있게 한다.
- 공개 목록은 최종 마감 전 모집 건을 보여 준다. 공개 상세는 게시 이력이 있는 건을 마감 후에도 보여 준다.
- 판매자 전용 목록·상세는 본인 초안과 게시 건을 보여 준다. 변경과 판매자 조회는 현재 `SELLER` 역할을 요구한다.
- 초안의 다섯 입력값은 각각 비워둘 수 있다. 전체 교체 요청에는 다섯 필드가 필요하며, 비울 필드는 `null`로 보낸다. 게시 시 전부 채워졌는지 다시 확인한다.
- 게시하면 `DRAFT`에서 `RECRUITING`으로 전환한다. 상품명·설명·원화 단가·기준 수량·최종 마감은 이때 고정한다.
- 기준 수량은 최소 10개다. 최초 모집 목표는 기준 수량 × 120%를 올림한 정수다. 판매자는 초안 상세에서 목표를 미리 확인한다.
- 수정과 게시는 PostgreSQL의 같은 공동구매 행을 잠근 뒤 소유권·상태와 요청의 초안 버전을 확인한다. 버전이 다른 새 요청은 409다. 게시 가능 여부는 잠금 후 DB 시각으로 판단한다.
- 등록·수정·게시에는 `Idempotency-Key`를 적용한다. 성공 결과는 업무 변경과 같은 트랜잭션에 저장하고 현재 권한을 다시 확인한 뒤 재현한다.
- Gateway는 공개·보호 라우트 각각의 메서드와 원시 경로를 제한한다. 보호 요청에는 008의 인증·CSRF·서비스 호출자 검증을 사용한다.
- 실제 보호 조회·변경 API로 인증 검사를 옮기고 개발용 `auth-probe`를 제거한다.
- 공동구매 서비스의 `purchase`에 DDD 계층을 적용한다. JDBC와 Flyway를 재사용한다.
- 참여·취소는 010, 결제·회차·최종 마감에 따른 상태 전이는 해당 후속 단계에서 다룬다.
- 기준 구현을 검증한 뒤 직접 작성할 여섯 Step을 한 번에 준비하고, 작성한 코드로 재검증한다.
- 완료 기준은 실제 PostgreSQL 경합·롤백 검증, Gateway 보안 회귀, 전체 Gradle·Compose·Windows 제품 JAR, 직접 테스트 및 학습 문서다.
- 구현을 시작할 때 최신 `main`과 PR·병합 커밋 CI를 확인한다. 검토 시점의 원격 확인 근거는 [008 결과](../008-gateway-authentication.md#pull-request)에 있다.

## 기존 합의와 009 범위

상품 정보와 판매 조건은 공동구매 서비스가 소유하며 공동구매 한 건에 함께 저장한다. 판매자 UUID는 Gateway가 검증한 신원에서 가져온다. 회원 DB 접근은 기존 회원 서비스의 인증 흐름에서 이루어진다. 009에서 다루는 상태는 `DRAFT`와 `RECRUITING`이며, 최초 게시 뒤에는 판매자 입력값을 고정한다. [상품 정보와 판매 조건](../../design/business-rules.md#product-policy) · [서비스 소유권과 API 계약](../../design/architecture.md#api-contract)

## API와 권한

경로의 `{id}`는 소문자 하이픈 표준형 UUID를 사용한다. 공개 조회는 세션 없이 사용할 수 있다. 판매자 조회와 변경은 현재 `SELLER` 역할이 필요하며, 변경에는 유효한 CSRF 토큰과 멱등성 키가 필요하다.

| 메서드와 경로 | 용도와 결과 |
|---|---|
| `GET/HEAD /api/group-purchases` | 공개 모집 목록. `RECRUITING`이고 조회 시점이 최종 마감 미만인 건을 반환. 200 |
| `GET/HEAD /api/group-purchases/{id}` | 공개 상세. 게시한 건을 조회하고 `recruitmentOpen`으로 현재 모집 가능 여부를 표시. 초안·없는 ID는 404 |
| `GET/HEAD /api/group-purchases/mine` | 현재 판매자 본인의 초안과 게시 건 목록. 200 |
| `GET/HEAD /api/group-purchases/mine/{id}` | 현재 판매자 본인의 관리용 상세. 타인 소유·없는 ID는 404 |
| `POST /api/group-purchases` | JSON으로 초안 등록. 빈 객체 허용. 201과 본인 상세 `Location` |
| `PUT /api/group-purchases/{id}` | 다섯 입력 필드와 조회한 `draftVersion`을 JSON으로 전송. 필드를 비우려면 `null` 사용. 200 |
| `POST /api/group-purchases/{id}/publish` | JSON의 `draftVersion`으로 판매자가 확인한 초안을 게시. 200 |

- 변경 성공의 공통 본문은 `{id, detailPath}`이며 `detailPath`는 본인 상세 경로다. 현재 상태와 최신 상품 정보는 조회 API에서 읽는다. HEAD의 상태와 응답 헤더는 같은 GET을 따르며 본문은 생략한다.
- 상세는 `id`, `status`, 입력 필드 다섯 개, `initialRecruitmentTarget`, `publishedAt`, `recruitmentOpen`을 반환한다. 초안의 게시 시각·확정 모집 목표는 `null`, 모집 여부는 `false`다. 본인 상세에는 `createdAt`, `updatedAt`, `draftVersion`, `projectedInitialRecruitmentTarget`도 포함한다. 예상 목표는 기준 수량이 있는 초안에서 계산하며 기준 수량이 없는 초안과 게시 건에서는 `null`이다. 본인 목록에는 기본 상세 필드 중 설명을 뺀 항목과 생성·갱신 시각을 표시한다. 공개 목록에는 공개 상세 필드 중 설명을 뺀 항목을 표시한다.
- 목록은 `{items, nextCursor}`를 반환한다. `limit`은 기본 20, 허용 범위 1~100이다. 공개는 `(published_at, id)`, 본인은 `(created_at, id)` 내림차순으로 읽는다. 커서는 해당 목록 유형과 마지막 항목의 정렬 값을 담은 불투명 토큰이며 끝 페이지에서는 `null`이다. 잘못된 커서·범위는 400이다. 다음 페이지에서도 현재 마감과 소유권을 적용한다.
- 공개 목록은 모집 중인 건이 없으면 빈 목록을 반환한다. 마감 시 해당 건은 목록에서 빠지며 기존 상세 주소의 `recruitmentOpen`은 `false`가 된다. 공개 상세 조회는 SQL에서 게시 이력이 있는 행만 읽는다. 요청에 쿠키가 있어도 같은 공개 응답을 반환한다. 회원 전용으로 제한하면 상품을 보기 전 로그인이 필요하고 회원 서비스 장애가 조회에도 영향을 준다.
- 본인 전용 경로를 따로 두면 공개 상세와 인증 정책을 고정할 수 있다. 같은 URL에서 세션 유무에 따라 초안 공개 여부를 바꾸면 Gateway에서 선택적 인증과 캐시 경계를 추가로 다뤄야 한다.

### Gateway와 오류

- 고정 경로는 기존 `ExactPath`, ID 경로는 원시 경로에서 UUID 한 구간만 허용하는 제한된 매칭을 사용한다. 메서드를 함께 등록하고 원래 경로를 전달한다. 인코딩된 구분자·중복 슬래시·세미콜론·후행 슬래시·유사 경로·미지원 메서드는 Gateway 404로 처리한다. 기존 공개 ping과 회원 경로를 유지한다.
- 공개 요청은 회원 인증 확인을 호출하지 않고 신원·자격 증명 헤더를 정리한다. 상품 조회 라우트에서 쿠키·Authorization·CSRF 헤더도 제거하고 응답에는 `Cache-Control: no-store`를 적용한다. 직접 루프백 호출에서도 공개 핸들러가 반환할 수 있는 데이터는 같은 공개 범위로 제한된다.
- 보호 요청은 008의 회원 확인과 내부 자격 증명을 재사용한다. Gateway는 확인된 역할에 `SELLER`가 있는지 확인하고, 공동구매 서비스도 검증된 신원에서 역할과 소유권을 확인한다. 판매자 역할이 포함된 복수 역할은 허용한다. 보호 핸들러의 직접 호출은 유효한 내부 자격 증명 없이는 403이다.
- 오류는 006의 `application/problem+json`과 요청 ID를 사용한다. 입력·키 형식 오류는 400, 세션 실패는 401, CSRF·판매자 역할 실패는 403이다. 타인 소유와 존재하지 않는 대상은 같은 404로 응답한다. 유효한 요청이 현재 상태에서 거절되는 경우 409로 응답하며 `GROUP_PURCHASE_NOT_DRAFT`, `GROUP_PURCHASE_DRAFT_VERSION_MISMATCH`, `GROUP_PURCHASE_NOT_READY`, `GROUP_PURCHASE_DEADLINE_PASSED`, `IDEMPOTENCY_KEY_CONFLICT`로 구분한다. 공동구매 DB 잠금 대기 한도를 넘기면 롤백 후 503 `GROUP_PURCHASE_BUSY`를 반환한다. 회원 확인 장애의 502·503·504 계약을 유지한다.

## 입력과 저장

| JSON 필드 | 제안하는 입력과 저장 규칙 |
|---|---|
| `productName` | 양끝 공백 정리 후 1~100자 |
| `productDescription` | 양끝 공백 정리 후 1~2,000자. 내부 줄바꿈은 유지 |
| `unitPrice` | 1~1,000,000,000 사이의 JSON 정수. 단위는 원, PostgreSQL `bigint` |
| `baseQuantity` | 10~1,000,000 사이의 JSON 정수, PostgreSQL `integer` |
| `finalDeadline` | 초까지 쓰고 UTC 오프셋을 포함한 ISO 8601 시각. 소수 초는 최대 3자리. `timestamptz(3)`에 저장하고 UTC로 반환 |

문자열 길이는 유니코드 코드 포인트로 센다. 요청별 정의에 없는 필드, 중복 키, 잘못된 자료형·날짜는 400으로 응답한다. 등록 시 누락된 필드는 `null`과 같은 의미다. 초안은 다섯 필드가 모두 비어 있어도 저장할 수 있다. 제공한 값은 표의 형식·범위에 맞아야 한다. 과거 마감이 들어 있는 초안도 보관할 수 있으며 게시하려면 마감을 미래로 수정해야 한다. `PUT`에는 다섯 필드가 모두 있어야 한다. 이 방식은 전체 교체의 의미를 유지하면서 입력 필드 누락으로 값이 지워지는 일을 막는다.

- 다음 Flyway 마이그레이션에 `app.group_purchases`를 추가한다. `id uuid`가 기본 키이고 `seller_id uuid`, 상태, 위 입력값, `initial_recruitment_target`, `draft_version bigint`, 생성·갱신·게시 시각을 둔다. 초안 버전은 1에서 시작해 성공한 수정마다 1씩 올리고 게시 시 마지막 버전을 유지한다. 판매자 ID는 서비스 간 참조값으로 보관한다. 기존 V1은 그대로 적용하고 새 DB와 V1이 이미 적용된 DB에서 업그레이드를 검증한다.
- DB 제약으로 상태, 입력 범위, 초안의 게시 시각·모집 목표가 비어 있다는 조건과 게시 건의 필수값·모집 목표·시각 관계를 검증한다. 목록은 공개 `(published_at DESC, id DESC)`의 모집 상태 부분 인덱스와 본인 `(seller_id, created_at DESC, id DESC)` 인덱스를 사용한다.
- 게시는 `finalDeadline > now`일 때 허용한다. 입력 다섯 개를 확인하고 최초 모집 목표를 정수 계산 `(baseQuantity * 6 + 4) / 5`로 구한다. 기준 수량 11개면 14개를 모집한다. 초안 상세의 예상 목표와 게시 시 확정 목표는 같은 계산을 사용한다. 사용자 직접 테스트 문서는 초안 등록 예시 앞에 20% 추가 모집 규칙을 설명한다. 저장되는 판매 조건과 목표는 이후 참여·결제의 기준이 된다. ## 수정·게시 경합과 멱등성

변경은 PostgreSQL `READ COMMITTED` 로컬 트랜잭션에서 실행한다. 수정·게시는 대상 행을 `SELECT … FOR UPDATE`로 잠근다. 새 변경은 소유권 확인과 키 선점 후 최신 행의 상태와 버전을 확인한다. 수정이 먼저 커밋되어 게시 요청의 버전이 오래되면 409를 반환한다. 판매자가 새 상세를 확인하고 새 키와 현재 버전으로 게시를 다시 요청할 수 있다. 게시가 먼저 커밋되면 새 수정은 409다. 게시 판단 시각은 잠금과 키 확인 뒤 DB의 `clock_timestamp()`를 밀리초 단위로 잘라 얻는다. 대기 중 마감에 도달하면 게시를 거절한다. 공개 조회는 SQL 문장 시작 시각을 기준으로 모집 여부를 계산한다. [프로젝트 경합 규칙](../../design/payment-and-messaging.md#section-10-3) · [PostgreSQL 행 잠금](https://www.postgresql.org/docs/18/explicit-locking.html#LOCKING-ROWS) · [PostgreSQL 시각 함수](https://www.postgresql.org/docs/18/functions-datetime.html#FUNCTIONS-DATETIME-CURRENT)

변경 트랜잭션에는 잠금 획득당 초기 한도 2초를 적용한다. 공동구매 행 잠금과 멱등성 키 충돌 대기에 같은 한도를 적용한다. 한도 초과 시 롤백하고 503을 반환하며, 잠금이 풀린 뒤 원래 요청을 같은 키로 재시도할 수 있다. Gateway 응답 한도는 현재 5초다. Gateway 504나 응답 유실 시에도 같은 키와 요청 내용으로 재시도해 커밋된 결과를 확인한다. [PostgreSQL 잠금 대기 한도](https://www.postgresql.org/docs/18/runtime-config-client.html#GUC-LOCK-TIMEOUT)

1. Gateway에서 세션·CSRF·현재 역할을 확인하고 공동구매 서비스에서 호출자와 역할을 확인한다. 헤더는 정확히 하나의 `Idempotency-Key`를 받으며 `[A-Za-z0-9._~-]{1,128}` 형식이다.
2. `app.group_purchase_idempotency`에 `(member_id, operation, idempotency_key)` 기본 키를 둔다. 작업은 초안 등록·수정·게시로 구분한다. 요청 지문은 대상 UUID, `draftVersion`, 정규화한 입력값 중 해당 작업에 쓰는 값을 고정 순서 UTF-8 JSON으로 직렬화해 SHA-256으로 계산한다. 시각은 UTC 에포크 밀리초 정수로 표현한다. 요청 JSON의 필드 순서, 같은 순간의 시간대 표기, 양끝 공백, 등록의 누락과 `null`은 같은 내용으로 본다. DB에 지문 형식 버전과 `bytea` 해시를 저장하고, 재요청은 저장된 형식으로 비교한다. 결과 공동구매 ID·상태 코드·본문·`Location`·생성 시각을 저장하며, 선점한 기록은 같은 트랜잭션 안에서 성공 결과로 채운다.
3. 기존 자원을 대상으로 하는 요청은 공동구매 행의 소유권을 확인한 뒤 키를 선점한다. 등록은 키를 먼저 선점한 뒤 새 공동구매 행을 만든다. 키 선점은 `INSERT … ON CONFLICT DO NOTHING`으로 시도하고 충돌하면 별도의 다음 SQL 문으로 커밋된 기록을 읽는다. 해당 요청이 접근할 수 있는 대상에서 지문이 다르면 409다. 지문이 같으면 업무 상태를 다시 변경하지 않고 저장한 결과를 재현한다. 등록 재시도도 결과로 가리키는 공동구매의 현재 소유권을 확인한다. [PostgreSQL Read Committed](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-READ-COMMITTED)
4. 처음 확보한 키에는 새 변경을 실행한다. 수정·게시는 `DRAFT` 확인 후 요청 버전과 현재 버전이 같은지 확인한다. 업무 행과 성공 응답의 상태·본문·`Location`을 한 트랜잭션에서 저장하고 커밋 이후 응답한다. 검증 실패나 DB 롤백에서는 키와 업무 변경이 함께 되돌아간다. 동일 키로 재시도하면 최초 성공 상태·본문·`Location`을 받고, 현재 요청 ID는 새로 부여된다. 과거에 성공한 수정은 버전이 바뀌었거나 이후 게시가 완료돼도 같은 키와 원래 요청으로 결과를 재현할 수 있다.
5. 009에서는 성공한 키를 만료시키지 않는다. 기한 없이 중복 등록을 막는 대신 기록이 누적된다. 유효기간을 도입할 때는 응답 유실 뒤 재시도할 수 있는 기간과 만료 후 중복 등록 정책을 함께 정한다.

## 설계 검토와 합의

- **2026-11-12 합의** — 수정·게시 요청에 조회한 초안 버전을 요구한다. 다른 탭에서 단가가 바뀐 뒤 이전 화면에서 게시를 누르면 409를 반환한다. 판매자는 최신 판매 조건을 확인하고 게시를 다시 요청한다. [수정·게시 업무 규칙](../../design/business-rules.md#draft-version)
- **공개 범위와 빈 초안은 유지한다.** 마감 뒤에는 상세 주소에서 모집 종료 여부를 확인할 수 있다. 빈 초안 등록은 허용하고, 전체 수정에서 빠진 필드는 400으로 처리한다.
- **단가·수량 한도와 키 보관안은 유지한다.** 최대 입력의 목표금액은 1,000조 원이며 64비트 정수와 JSON 소비자의 일반적인 안전 정수 범위에 들어간다. 이 값은 009의 저장 상한이다. 성공 키를 계속 비교할 수 있도록 지문 형식과 호환성 검증을 명시했다.
