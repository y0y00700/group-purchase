## 실행 요약

- 목표는 구매자가 게시된 공동구매에 참여하고, 자신의 참여 내역을 조회하고, 결제 전 참여 한 건 전체를 취소할 수 있게 하는 것이다.
- 공동구매 서비스에 `participation/{domain,application,interfaces,infrastructure}`를 두고, 참여·수량 집계·멱등성 기록을 기존 공동구매 PostgreSQL에 저장한다. [서비스 책임](../../design/architecture.md#service-boundaries)
- 구매자의 여러 유효 참여를 합쳐 기준 수량의 10%까지 허용한다. 최초 모집 목표를 넘는 신청은 전량 거절한다. 취소한 건은 두 한도에서 빠지고 재참여는 새 건으로 생성한다. [구매 수량과 재참여](../../design/business-rules.md#participation)
- 010에서는 목표에 도달하면 새 모집을 닫고, 마감 전에 취소로 빈자리가 생기면 모집을 다시 연다. 기존 `RECRUITING` 상태와 `recruitmentOpen`으로 이를 표현한다. 회차 개시·결제·결제 후 취소·정산·자동 마감은 016에서 연결한다. [로드맵](roadmap.md)
- 신청·본인 목록·본인 상세·취소는 현재 `BUYER` 역할을 요구한다. Gateway와 서비스에서 역할을 검사하며, 변경은 CSRF와 `Idempotency-Key`를 요구한다. 타인 참여 조회·취소는 없는 건과 같은 404다.
- 신청·취소는 공동구매 행부터 잠근다. 그 잠금 안에서 현재 상태·기한과 수량을 검증하고, 참여 행·모집 수량·멱등성 응답을 한 트랜잭션으로 커밋한다. [경합 원칙](../../design/payment-and-messaging.md#section-10-3)
- 동일 키·동일 요청은 성공 응답을 재현한다. 대상이나 수량을 바꾸면 409를 반환한다. 대기 중 마감에 도달한 신규 신청은 409, 잠금 대기 한도 초과는 503이다.
- 변경 위치는 공동구매 서비스의 참여 패키지·공동구매 저장소·Flyway V3, Gateway 라우트와 역할 검사, 두 모듈의 테스트와 기존 스모크 검증이다.
- 완료 기준은 경계 수량·취소·재참여·동시 요청·롤백·권한 검증, 사용자가 직접 작성한 여섯 구간의 재검증, Gradle·Compose·Windows 제품 JAR 확인, 직접 테스트와 HTTP 흐름·학습 문서 기록이다.
- 2026-11-18 구현 착수 범위에 아래 API 경로, 목표 도달과 마감 전 취소 처리, 마감 후 본인 미결제 취소, 공동구매 전체 카운터와 구매자별 유효 참여 합산을 반영했다. [API](#api-contract) · [모집 상태](#recruitment) · [저장과 경합](#transactions) · [구현 기록](../010-participation.md)

## 현재 출발점

009에서 판매자가 단가·기준 수량·최종 마감을 게시하면 최초 모집 목표를 확정한다. Gateway는 세션 없는 게시 조회와 `SELLER` 역할의 업무 요청을 구분한다. 009 결과의 PostgreSQL·Compose·Windows 제품 JAR 검증을 출발점으로 삼는다. 원격 확인 시점과 결과는 [인계](../../handoff.md)에 기록한다. [009 최종 결과](../009-group-purchase-product.md#final-results)

## 모집과 취소

- 신청 수량은 1 이상의 정수다. 모집 잔여량은 `initialRecruitmentTarget - recruitedQuantity`이고, 구매자별 추가 가능 수량은 `floor(baseQuantity / 10) - 해당 구매자의 유효 참여 수량 합계`다. 게시 후 단가가 고정되므로 수량으로 비교해도 금액 기준과 같다. 예를 들어 기준 수량 25개는 최초 모집 목표 30개이고, 한 구매자는 합계 2개까지 참여할 수 있다.
- 두 한도를 정확히 채우는 신청은 허용한다. 어느 한도를 넘으면 신청 전체를 거절한다. 상품 단가를 참여 건에 기록하고 금액은 수량과 단가의 곱으로 계산한다.
- 최초 모집 목표에 도달한 건은 공개 모집 목록에서 빠지고, 공개 상세의 `recruitmentOpen`은 `false`다. 010에서 공개 상세의 `status`는 `RECRUITING`으로 유지한다. 모집 여부는 상태, DB 시각이 최종 마감 미만인지, 모집 잔여량이 양수인지로 판단한다. 공개 조회 시각은 009와 동일하게 SQL 문장 시작 시각(`statement_timestamp()`)을 사용하고, 공개 모집 목록에는 같은 조건을 페이지 조회 전에 적용한다.
- 취소하면 `APPLIED`가 `CANCELLED`로 바뀌고 해당 행의 전체 수량이 모집 집계와 구매자 합계에서 빠진다. 마감 전에 만석이 풀리면 최초 모집 목표까지 생긴 빈자리를 다시 채운다. 이 동작은 결제 회차를 열기 전인 010에 한정한다. 회차 기한 종료 후 결제 완료 수량을 기준으로 부족분을 재모집하는 정책은 016에서 적용한다. [수량과 결제 기한](../../design/business-rules.md#quantity-and-deadlines)
- 010에서는 최종 마감 정각 이후에도 본인의 `APPLIED` 참여 전체를 취소할 수 있고 모집은 닫힌 상태로 유지된다. 최종 마감은 새 신청 접수에 적용하며, 취소는 [구매자 취소 규칙](../../design/business-rules.md#cancellation)을 따른다. 자동 마감과 구매 확정 전후의 취소 처리는 이후 Saga 단계에서 적용한다. 같은 키로 성공한 취소를 다시 보내면 최초 응답을, 새 키로 이미 취소한 행을 취소하면 409를 반환한다.
- 재참여에는 새 키와 새 참여 ID를 사용한다. 취소한 참여는 본인 목록과 상세에서 계속 확인할 수 있다. 한 구매자의 여러 유효 참여 건은 허용한다. [취소 정책](../../design/business-rules.md#participation)

## API와 권한

| 메서드와 경로 | 입력과 성공 응답 |
|---|---|
| `POST /api/group-purchases/{id}/participations` | 공동구매 ID와 JSON `{"quantity":2}`. 201, 본인 상세 `Location`, 본문 `{id, detailPath}` |
| `GET/HEAD /api/participations/mine` | 본인 참여 목록. 200과 `{items, nextCursor}` |
| `GET/HEAD /api/participations/mine/{id}` | 본인 참여 상세. 200 |
| `POST /api/participations/{id}/cancel` | 참여 ID와 빈 요청 본문. 200과 `{id, detailPath}` |

- 신청은 대상 공동구매 아래에 두고, 조회는 구매자의 전체 참여를 다루므로 009의 본인 목록과 같은 `/mine` 형태를 쓴다. 취소는 참여 ID로 지정하는 상태 변경이다. 취소한 건도 본인 상세에서 계속 조회하며, 신청의 `Location`과 신청·취소의 `detailPath`는 모두 `/api/participations/mine/{id}`를 가리킨다.
- 목록과 상세의 참여 필드는 `id`, `groupPurchaseId`, `status`, `quantity`, `unitPrice`, `amount`, `appliedAt`, `cancelledAt`이다. 금액 단위는 원이며 시각은 UTC로 반환한다. `APPLIED`의 `cancelledAt`은 `null`이다. HEAD 응답은 GET의 상태·헤더를 따르고 본문을 생략한다.
- 목록은 `(applied_at, id)` 내림차순으로 읽고 `limit`은 기본 20, 허용 범위 1~100이다. 009와 같은 방식으로 마지막 정렬 값을 담은 참여 목록용 커서를 사용한다. 모든 페이지에서 현재 구매자 ID로 범위를 제한한다.
- `{id}`는 기존 `UuidPath`의 소문자 하이픈 UUID 한 구간으로 제한한다. 신청 JSON은 `quantity` 한 필드를 받고 자료형·범위·중복 키·알 수 없는 필드를 검증한다. 표현 가능한 입력 범위는 1~1,000,000이다. 업무상 모집·구매자 한도는 DB의 현재 판매 조건으로 판정한다.
- Gateway는 기존 회원 확인 흐름과 내부 자격 증명을 사용한다. 보호 라우트의 요구 역할을 명시해 판매자 라우트에는 `SELLER`, 참여 라우트에는 `BUYER`를 적용한다. 역할 설정이 빠지거나 지원하지 않는 값이면 보호 요청을 거절한다. 업무 서비스도 검증된 Gateway 신원에서 `BUYER`를 확인하고 참여 조회·취소에 구매자 소유권을 적용한다. `BUYER`가 포함된 복수 역할은 허용한다. Gateway가 외부 신원 헤더를 제거하며, 보호 응답에 `Cache-Control: no-store`를 적용한다.

| HTTP 상태 | 조건 |
|---|---|
| 400 | JSON·수량 형식·목록 입력·`Idempotency-Key` 오류 |
| 401 | 세션 누락·만료·로그아웃 |
| 403 | 변경 요청의 CSRF 검증 실패, `BUYER` 역할 없음, 보호 라우트의 역할 설정 오류(`INVALID_ROUTE_POLICY`), 유효한 내부 자격 증명 없이 서비스 직접 호출 |
| 404 | 없는 공동구매·미게시 초안 신청, 타인 또는 존재하지 않는 참여 조회·취소, Gateway 경로·메서드 불일치 |
| 409 | `RECRUITMENT_CLOSED`, `RECRUITMENT_QUANTITY_EXCEEDED`, `BUYER_PARTICIPATION_LIMIT_EXCEEDED`, `PARTICIPATION_ALREADY_CANCELLED`, `IDEMPOTENCY_KEY_CONFLICT` |
| 503 | 공동구매 DB 잠금 대기 한도 초과 시 `GROUP_PURCHASE_BUSY` |

업무 충돌은 `application/problem+json`과 기존 요청 ID 계약을 사용한다. 신규 신청은 상태·기한, 모집 잔여량, 구매자 한도 순으로 검사한다. 마감 전 만석에는 모집 잔여량 초과를 반환한다. 회원 확인·Gateway 장애에는 008의 기존 오류 형식을 적용한다. [Gateway 인증 결과](../008-gateway-authentication.md) · [API 오류 기준](../006-api-observability-baseline.md)

## 저장과 트랜잭션

### Flyway V3와 조회

| 위치 | 제안 |
|---|---|
| `app.group_purchases` | `recruited_quantity integer NOT NULL DEFAULT 0`. 초안은 0, 게시 건은 0 이상 최초 모집 목표 이하로 제한한다. V2에서 이미 게시한 건은 참여 데이터가 없으므로 0으로 시작한다. |
| `app.participations` | 참여 UUID 기본 키, 공동구매 FK, 구매자 UUID, 양의 수량, 단가, 상태, 신청·취소 시각. DB에서 상태와 취소 시각의 일관성을 검증한다. 금액 계산에는 `bigint` 범위를 사용한다. |
| `app.participation_idempotency` | `(buyer_id, operation, idempotency_key)` 기본 키, 버전이 있는 SHA-256 지문, 참여 FK, 성공 상태·본문·`Location`, 생성 시각. `APPLY`는 201과 `Location`, `CANCEL`은 200을 저장한다. |

공동구매 전체 수량은 잠근 행의 카운터로 확인한다. 구매자별 수량은 같은 공동구매 잠금 안에서 `(group_purchase_id, buyer_id) WHERE status = 'APPLIED'` 부분 인덱스로 해당 구매자의 행을 찾아 합산한다. 유효 참여가 없으면 합계는 0이다. 010에서 `recruited_quantity`는 같은 공동구매의 `APPLIED` 수량 합계와 항상 같아야 한다. 결제 상태를 추가할 때 구매자 한도에 포함하는 상태와 인덱스 조건을 함께 갱신한다. 본인 목록에는 `(buyer_id, applied_at DESC, id DESC)` 인덱스를 사용한다. 공개 모집 여부와 공개 목록에는 동일한 모집 가능 조건을 사용한다. [구매 수량](../../design/business-rules.md#participation)

전체 참여를 매 신청에 다시 집계하는 방식은 파생 카운터를 줄일 수 있으나 같은 공동구매의 유효 참여 전체를 잠금 안에서 읽어야 한다. 제안 방식은 공개 조회와 모집 상한 검사를 단순화하는 대신 참여와 카운터를 함께 변경하는 경계를 요구한다. 구매자별 합계 조회가 잠금 점유 시간의 주요 원인으로 측정되면 구매자 집계를 별도 행으로 관리하는 방법을 재검토한다. [경합 재검토 기준](../../decisions/design-review.md)

### 명령 흐름

1. **신청**은 PostgreSQL `READ COMMITTED`에서 게시한 공동구매 행을 `SELECT … FOR UPDATE`로 잠근다. 신청 키 선점 뒤 모집 상태와 모집·구매자 수량을 읽고, 잠금과 키 대기 이후의 DB `clock_timestamp()`로 최종 마감 미만인지 확인한다. 새 신청은 참여 행을 삽입하고 공동구매 카운터를 신청 수량만큼 증가시킨 뒤 응답을 저장한다. 마감 판정 시각은 DB에서 업무 허용을 판단한 시점이다.
2. **취소**는 본인 참여를 잠금 없이 읽어 공동구매 ID를 찾고, 공동구매 행부터 잠근 뒤 해당 참여 행을 잠그며 구매자·공동구매 ID를 재확인한다. 취소 키 선점 후 `APPLIED`일 때만 `CANCELLED`로 바꾸고 수량을 한 번 차감한다. 참여 행의 잠금과 상태 검사를 거치므로 다른 키의 동시 취소가 수량을 중복 차감할 수 없다.
3. **멱등성**은 009의 키 형식과 선점 방식을 적용한다. 신청 지문은 `(groupPurchaseId, quantity)`, 취소 지문은 `(participationId)`를 고정 순서로 직렬화한 값이다. 선점 `INSERT … ON CONFLICT DO NOTHING`의 충돌 결과는 다음 SQL 문에서 읽는다. 대상 접근을 확인한 요청이 같은 키와 지문을 보내면 저장한 참여의 현재 조회 권한을 확인한 뒤 상태 코드·본문·`Location`을 재현한다. 성공 이후 모집 종료나 참여 취소에 도달해도 재현할 수 있다. 접근 가능한 다른 대상이나 수량으로 키를 재사용하면 409다.
4. **커밋과 실패**는 참여 행·공동구매 카운터·멱등성 기록을 원자적으로 처리한다. 업무 거절과 DB 실패는 키 선점까지 롤백한다. 잠금에는 009와 같은 `SET LOCAL lock_timeout = '2s'`를 적용한다. 503·Gateway 응답 시간 초과·응답 유실 뒤에는 같은 키와 요청으로 재시도할 수 있다. 성공 키 보관은 009와 같이 만료 없이 시작하고 데이터 누적을 운영 단계에서 검토한다. [009 트랜잭션](009-group-purchase-product.md#transactions)

참여용 저장소는 009의 판매자 명령·응답을 담은 스키마와 변경 주기가 다르므로 참여의 상태와 FK를 자체 제약으로 관리한다. HTTP 키 형식과 지문 생성, DB 선점 구현은 이미 쓰는 패턴을 적용하고, 의미가 동일한 코드가 생기는 범위에서 공유한다. 009에 저장된 응답과 지문은 마이그레이션 후에도 재현해야 한다.

## 검증과 완료 기준

| 검증 | 기대 결과 |
|---|---|
| 수량 경계와 구매자 합계 | 기준 수량 20개에서 한 구매자의 합계 2개(정확히 10%)를 허용한다. 기준 수량 25개와 최초 모집 목표 30개에서는 동일 구매자의 1개 신청 두 건을 허용하고 세 번째 1개는 409다. 잔여량을 정확히 채우면 공개 모집 목록에서 빠지고 상세는 계속 조회된다. |
| 취소와 재참여 | 본인 참여 한 건을 취소하면 해당 수량이 두 상한에서 빠진다. 마감 전이면 모집에 다시 나타나고 재참여에 새 ID가 생긴다. 마감 정각 이후의 신청은 거절되고 미결제 취소 후에도 모집은 닫혀 있다. |
| PostgreSQL 경합 | 두 구매자가 마지막 자리를 다투거나 같은 구매자가 남은 개인 한도를 동시에 신청해도 성공한 수량만 반영된다. 여러 취소와 신청/취소 경합 뒤에도 모집 카운터와 유효 참여 합계가 일치한다. |
| 키 재현과 롤백 | 같은 키·같은 요청이 동시에 오면 하나의 참여와 같은 성공 응답을 남긴다. 같은 키로 다른 게시 건을 동시에 신청하면 하나가 성공하고 다른 하나는 409다. 업무 변경 뒤 성공 기록 저장을 실패시켰을 때 참여·수량·선점 기록이 함께 롤백되고 같은 키로 다시 시도할 수 있다. |
| DB 시각과 대기 | 잠금을 기다리는 사이 마감이 지나면 새 신청이 409다. 잠금 대기 한도를 넘으면 503으로 롤백하고, 잠금 해제 후 같은 키로 재시도할 수 있다. |
| 권한과 공개 범위 | 타인·없는 참여의 조회와 취소는 같은 404다. 세션 누락·역할 박탈·CSRF 누락·위조 신원 헤더·내부 자격 증명 없는 직접 호출은 거절된다. 기존 판매자 경로와 게시 전 비공개 규칙을 재검증한다. |
| 설치·업그레이드 | 신규 DB의 V1~V3과 V2까지 적용된 DB의 V3을 확인하고, 기존 초안·게시 건의 데이터 및 009 멱등성 응답을 검증한다. |
| 통합 실행 | Gradle 빌드, Compose 실기동, Windows 제품 JAR에서 Gateway를 통한 신청·조회·취소를 확인한다. 결과에 실제 명령과 통과 범위를 기록한다. |

결과 문서에 구매자와 판매자의 테스트 계정 준비, Gateway 요청, 응답·수량 확인, 종료·데이터 정리 방법을 담는다. 신청·취소의 HTTP 흐름을 Mermaid로 기록하고, 한도·잠금·멱등성 학습 문서를 코드와 연결한다. [결과 기록 기준](../README.md#workflow) · [검증 설계](../../design/verification.md)
