# 구현 순서 제안

작성일: 2026-10-29

001~011의 로컬 구현과 검증을 완료했다. 단계별 근거와 원격 상태는 [구현 목록](../README.md)과 [프로젝트 인계](../../handoff.md)를 따른다.

## 진행 방식

한 번에 하나의 공통 구성 또는 도메인 기능을 다룬다. 착수할 작업의 상세 계획을 먼저 작성하고 사용자가 읽어본다. 수정 의견이 있으면 같은 계획 문서에 반영한 뒤 변경된 범위로 진행한다. 계획 수정 요청 자체를 구현 착수 요청으로 해석하지 않는다.

사용자가 진행을 요청하면 해당 단계의 구현·검증·결과 기록까지 완료한다. 다음 단계도 먼저 계획을 검토한다. 이미 진행을 합의한 범위 안의 세부 수정·검증은 중간 승인 항목으로 계속 나누지 않는다.

전체 순서는 의존관계를 기준으로 한 제안이며 사용자 의견과 앞 단계의 결과에 따라 바꿀 수 있다. 각 행의 상세 계획은 착수 전에 작성한다. 큰 작업은 같은 영역 안에서 검증 가능한 기능 단위로 더 나눈다. 아래 순번이 이후 상세 계획의 파일 번호를 모두 미리 확정하는 것은 아니다.

## 공통 기반

| 순서 | 작업 단위 | 구현 범위와 완료 기준 |
|---|---|---|
| 1 | Gradle 빌드·YAML 전환 | Gradle Wrapper·멀티 프로젝트로 전환하고 기존 앱을 공동구매 모듈로 이동. YAML 설정 로딩·전체 및 선택 빌드·기존 테스트 검증, 기존 GitHub Actions를 Gradle 검증으로 전환 |
| 2 | Config Server | YAML 일반 설정 제공, 환경 구분, 비밀값 별도 주입 경계. 첫 클라이언트 설정 수신·누락 시 동작과 첫 서버의 이미지·Compose 기동 확인 |
| 3 | Eureka Server | 서비스 등록·조회와 Config 접속 순서. 서버와 클라이언트 기동·재등록 확인 |
| 4 | API Gateway 기본 라우팅 | 서비스 탐색 기반 전달과 공개·내부 경로 구분. 테스트 요청 전달·대상 장애 동작 확인 |
| 5 | PostgreSQL 실행 기반 | Compose의 단일 서버, 업무 서비스별 DB·계정과 초기화·스키마 변경 관리 방식. 재시작 후 데이터 유지·다른 서비스 DB 접근 거절 확인 |
| 6 | API·로그·헬스 기준 | 공통 오류 형식·요청 식별자·JSON 로그와 Actuator 기본 지표. 기존 모듈에서 계약과 민감정보 미노출 확인, 이후 모듈에도 같은 기준 적용 |

2단계에서 Cloud 관련 의존성을 처음 도입할 때 기존 Boot와의 호환성을 공식 자료와 최소 연동으로 확인한다. 정확한 버전은 해당 계획에 기록하고 검증한다. Config의 최초 접속을 Eureka 조회에 의존시키지 않아 시작 의존성이 순환하지 않도록 한다.

4단계는 라우팅 기반을 검증하는 단계다. 보호된 업무 API의 인증 흐름은 7~8단계에서 완성하고 업무 API를 연결한다.

2026-10-29 사용자 수정·확인 반영: 빌드 도구는 Gradle Wrapper로 변경하고 서비스 설정은 `application.yml`, 전체 기동은 Docker Compose로 관리한다. 실행 정의는 루트 `compose.yml`에 두고 `docker compose up --build -d`로 기동한다. 첫 서버부터 각 구현 단계에 이미지·Compose 정의를 함께 추가해 이미 완성한 서비스들의 일괄 기동을 확인한다.

## 회원과 공동구매의 기본 기능

| 순서 | 작업 단위 | 구현 범위와 완료 기준 |
|---|---|---|
| 7 | 회원·세션 인증 | 회원·역할·계정 상태, 로그인·로그아웃, Spring Session JDBC, CSRF와 내부 인증 확인 API. 세션 공유·만료·CSRF 검증 |
| 8 | [Gateway 인증·내부 호출 신뢰](008-gateway-authentication.md#execution-summary) | 회원 서비스 인증 확인 연결, 외부 신원 헤더 제거, 내부 호출자 확인. 위조·직접 접근·인증 확인 장애 시 거절 검증 |
| 9 | [공동구매·상품 정보](009-group-purchase-product.md#execution-summary) | 임시 저장·수정·게시·조회, 가격·수량·기한 규칙과 판매자 소유권. 게시 후 수정 금지와 수정·게시 경합 검증 |
| 10 | [참여·조회·결제 전 취소](010-participation.md#execution-summary) | 참여 신청·조회·결제 전 취소, 모집 수량·구매자별 10% 한도와 요청 멱등성. 동시 참여·중복 요청·타인 접근 검증 |

상품 정보·공동구매·참여는 같은 공동구매 서비스 안에서 기능별로 구현한다. 별도 상품·참여 서비스를 추가하는 제안이 아니다. 결제 후 취소와 회차 전환 등 결제 결과에 의존하는 동작은 후속 Saga 단계까지 이어진다. 이때까지의 완료 표시는 해당 단계의 제한된 기능 범위에만 적용한다.

변경 API의 요청 멱등성은 첫 대상 API부터 업무 변경과 같은 트랜잭션으로 구현·검증한다. 공통 API 기준을 정하는 것만으로 각 도메인의 멱등성 구현이 끝난 것으로 보지 않는다.

## 결제와 메시지 흐름

| 순서 | 작업 단위 | 구현 범위와 완료 기준 |
|---|---|---|
| 11 | [Kafka 실행·메시지 계약](011-kafka-message-contract.md#execution-summary) | 단일 브로커 Compose, 토픽·키·소비 그룹, JSON 메시지와 버전. 실제 발행·수신과 직렬화·호환성 검증 |
| 12 | [Outbox 발행](012-outbox-publishing.md#execution-summary) | 서비스 소유 DB의 업무·Outbox 원자적 저장, 선점 ID·기한·순번, 재시도·중단·재선점. 발행 전후 중단·중복 전달·이전 선점자의 늦은 갱신 검증 |
| 13 | 메시지 소비 안정성 | 소비 기록과 업무·후속 Outbox의 원자성, 커밋 후 오프셋 반영, 실패 분류·DLT 보관·파티션 보류. 재전달·재시작과 실패 원본을 넘기지 않는 동작 검증 |
| 14 | PG Mock | 독립 HTTP 승인·환불·결과 조회와 멱등성, 거래 기록 및 지연·응답 유실 등 장애 재현. 재요청 결과와 거래 기록 대사 |
| 15 | 결제 도메인 | 승인·중단·환불 의뢰 처리, PG Mock 호출, 결과 불명 추적·복구와 결과 발행. 중복 승인·환불 방지와 재시작 복구 검증 |
| 16 | 공동구매 Saga | 결제 시도·사전 수량 확보·결과 반영·구매 확정, 결제 후 취소·환불, 회차 기한·재모집·최종 마감과 복구. 정상 흐름부터 취소·마감·늦은 승인 경합 순으로 나누어 검증 |
| 17 | 알림 도메인 | 결제 개시·안내 대상·기한과 알림 의뢰 연결, 테스트 대역 전달·결과·재시도·중복 방지. 알림 지연으로 업무 기한이 바뀌지 않는지 검증 |

12~13단계는 첫 적용 서비스에서 저장·전달 경계를 검증하고, 후속 결제·알림 서비스에 각 서비스가 소유하는 테이블과 트랜잭션으로 적용한다. 서비스 간 엔티티·업무 로직·DB 테이블을 공유하지 않는다. 공통 라이브러리의 필요성과 범위는 실제 적용 코드를 확인한 뒤 해당 계획에서 판단한다.

16단계는 범위가 크므로 상세 계획을 결제 접수·정상 결과 반영, 취소·환불, 기한·재모집·무산처럼 나누어 검토한다. 단계별로 필요한 알림 의뢰를 업무 변경과 함께 Outbox에 저장하고, 실제 전달은 알림 도메인 단계에서 연결한다. 이미 저장한 미완료 업무를 복구하지 않은 채 정상 경로만 완료로 표시하지 않는다.

## 운영·전체 검증

| 순서 | 작업 단위 | 구현 범위와 완료 기준 |
|---|---|---|
| 18 | 운영 복구 API | 미완료·보류 조회, 재처리·재개·근거 있는 종결, 요청 영속화·실행권·복구 회차·운영 권한과 이력. 중단·재할당·중복 조작·이전 실행자의 늦은 반영 검증 |
| 19 | 관측 환경 완성 | Prometheus·Grafana, 업무 지표·대시보드와 Alertmanager·로컬 수신기. Kafka 장애 중 운영 알림과 미완료·적체 관측 확인 |
| 20 | 전체 흐름·장애·부하 검증 | 각 단계에서 누적한 Compose 구성의 전체 일괄 기동, 테스트 데이터와 실행 절차, 기능·정합성·장애 시나리오 및 k6. DB·PG 거래 대사와 기존 설계의 측정 전 목표 비교 |
| 21 | CI 확장과 재현 문서 | 기존 GitHub Actions에 단계별 테스트·이미지 빌드 검증을 누적하고 전체 실행 문서 정리. 외부 이미지 게시·서버 자동 배포의 범위는 별도 계획에서 정함 |

로그·헬스·기본 지표와 해당 기능의 테스트는 앞 단계부터 포함한다. 19~20단계는 이를 전체 환경과 업무 흐름으로 연결하는 작업이다. 관측한 문제가 있으면 원인·대안·트레이드오프·변경·같은 조건의 재검증을 기록한다.

2026-10-29 CI 추가 반영: Maven 빌드·테스트용 GitHub Actions 워크플로가 저장소에 추가되었다. 1단계에서 Gradle 명령·캐시로 함께 전환하고 이후 기능별 검증을 해당 구현 단계부터 CI에 연결한다. 21단계는 기존 CI의 확장·정리이며, CI 도입을 마지막 단계까지 미루는 뜻이 아니다. 실제 실행 성공과 Ruleset 적용 여부는 별도로 확인한다.

2026-10-29 001 구현·검증 완료: [Gradle·YAML·CI 전환 결과](../001-multi-module-build.md)에 로컬 빌드·기동과 PR의 GitHub CI 성공 근거를 기록했다. 2026-10-30에는 [002 결과](../002-config-server.md)의 Config Server·첫 클라이언트·로컬 이미지·Compose 검증을 완료했다. 2026-11-02 PR #2 병합과 최종 head의 CI 성공을 확인하고 [003 Eureka 계획](003-eureka-server.md)을 작성했다.
