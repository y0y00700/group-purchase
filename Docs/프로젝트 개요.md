# 목표 달성형 공동구매 프로젝트 개요

작성 기준: 2026-10-28 대화 내용 반영

최신 진행: 2026-10-28 사용자 요청으로 단일 Spring Boot 프로젝트 하나와 Docs 문서 분류를 생성했다. Java 21·Spring Boot 4.0.9·Maven Wrapper 3.9.16을 사용한다. 서비스 모듈과 MSA 공통 구성은 후속 작업에서 단계별 커밋으로 추가한다. 기존 6묶음의 설계 합의는 목표 구조이며 현재 구현 상태와 구분한다. ERD·SA·인프라 설계도는 Docs/artifacts/에 저장 위치를 마련했고 실제 도식 작성은 대기다. 이번 범위는 [구현 기록](implementation/000-initial-project.md)과 [범위 결정](decisions/ADR-0001-initial-project-scope.md)을 따른다.

## 1. 이번 세션에서 확정한 방향

- 주제: **목표 달성형 공동구매**.
- 배경: Spring 기반 웹 애플리케이션 개발 경력 약 5년, 취업을 위한 개인 프로젝트.
- 현재 단계: 단일 Spring Boot 초기 프로젝트 생성과 Docs 문서 분류. MSA 공통 구성·서비스 모듈 분리는 이후 단계별로 진행한다.
- 초기 구현 방향: **최소 기능의 MVP를 먼저 완성하고, 필요에 따라 확장**한다.
- 프로젝트 범위: **구현 → 부하 테스트 → 관측·분석 → 트러블슈팅 → 트레이드오프 검토 → 설계·구현 변경 → 재검증**까지 포함.

## 2. 프로젝트 목표

> 목표 달성형 공동구매 서비스를 구현하고, 정합성·장애·부하 테스트로 확인한 문제를 분석하여, 트레이드오프를 고려한 설계·구현 변경과 재검증 과정을 근거와 함께 남긴다.

포트폴리오에서는 다음을 설명할 수 있도록 한다.

- 서비스와 데이터 책임을 어떻게 정했는가.
- 비동기 처리와 Saga 보상이 어떤 업무 문제를 해결하는가.
- 어떤 테스트 조건에서 어떤 문제를 관측했는가.
- 원인이라고 판단한 근거와 비교한 대안은 무엇인가.
- 변경으로 얻은 효과와 추가된 비용·복잡성은 무엇인가.
- 변경 후 성능과 업무 정합성이 어떻게 달라졌는가.
- 남은 한계와 후속 개선 가능성은 무엇인가.

## 3. 서비스의 큰 업무 윤곽

물품을 직접 공급하는 판매자가 공동구매를 등록하고, 참여 모집 후 결제를 받아 성사·무산을 판단하는 서비스다. 핵심 업무 규칙은 [MVP 요구사항](design/MVP%20%EC%9A%94%EA%B5%AC%EC%82%AC%ED%95%AD.md)을 기준으로 한다.

```text
임시 저장·게시
  → 기준 수량의 120%를 올림한 수량만큼 참여 모집
  → 회차 공통 결제 개시·안내: 개시 후 168시간과 최종 마감 중 빠른 시각을 기한으로 적용
  → 기준 수량 결제 완료 즉시 구매 확정·결제 접수 종료·미결제 참여 취소
  → 결제 기한 종료: 접수 종료·기존 결과 확인 후 미달이면 최종 마감 전 부족분 재모집
  → 최종 마감: 접수 종료·기존 결과 확인 후 유효 결제 미달이면 전체 취소·환불
```

판매자 입력이 100개라면 최초 모집 목표는 120개이며, 취소되지 않은 결제 완료 수량이 정확히 100개가 되는 즉시 구매를 확정한다. 기준 수량을 초과하게 만드는 결제 요청은 건 전체를 거절한다. 90개 결제 후 재모집할 때는 부족한 10개만 모집한다. 추가 판매를 원하면 판매자가 새 공동구매를 수동 등록한다.

판매자가 최초 설정하는 기준 수량은 최소 10개인 정수다. 최초 모집 목표는 기준 수량의 120%를 계산한 뒤 소수점 이하를 올림한다. 기준 수량 11개이면 최초 모집 목표는 14개다. 재모집은 실제 부족분을 모집하므로 10개 미만일 수 있다.

현재 기능 범위는 MVP로 잡고, 추가 기능과 정책은 실제 필요가 생겼을 때 확장한다. 세부 구현은 확정한 핵심 흐름을 기준으로 정한다.

## 4. 확정한 기술 방향

| 영역 | 기술·방식 |
|---|---|
| 애플리케이션·MSA | Spring Boot, Spring Cloud |
| 언어·빌드·저장소 | Java 21, Maven Wrapper, 단일 저장소의 개별 실행 모듈 |
| 공통 기반 | Eureka, Config, API Gateway |
| 인증 | 세션 + 쿠키 |
| 인증·세션 구현 | Spring Security + Spring Session JDBC. 회원 서비스 PostgreSQL에 저장·공유, Redis는 후속 검토 |
| 비동기 통신 | Kafka |
| 업무 RDB | PostgreSQL 서버 하나에 서비스별 DB·계정 분리. 정확한 버전·자원은 구현 때 고정 |
| 메시지 발행 신뢰성 | Transactional Outbox: 업무 RDB 내 테이블에 업무 변경과 메시지를 함께 저장하고 폴링으로 발행 |
| 분산 업무 일관성 | 공동구매 서비스의 Saga Orchestration 및 보상 처리 |
| 장애 대응 | Resilience4j |
| 실행 환경 | Docker / Docker Compose |
| 메트릭·대시보드 | Prometheus, Grafana |
| 부하 테스트 | k6 |

상품 정보·공동구매·참여는 공동구매 서비스에, 결제·회원·알림은 각각 독립 서비스에 둔다. 공동구매 서비스의 Saga Orchestration과 업무 RDB 내 Transactional Outbox·서비스 내부 폴링을 채택한다. 회원 서비스는 인증·역할과 PostgreSQL의 JDBC 세션을 관리한다. 초기 DB는 서버 하나의 서비스별 DB·계정이며 Outbox 조회는 10초 간격·최대 50건이다. Java 21·Maven Wrapper와 실행 구성의 상세 합의는 실행 환경 문서를 따르고, 정확한 패치 버전·DDL·선점 쿼리 등은 구현 설계에서 고정한다.

## 5. 구현과 검증의 전체 범위

| 단계 | 수행할 일 | 남길 결과 |
|---|---|---|
| 요구사항·초기 설계 | 업무 규칙, 서비스 책임, 통신·데이터·인증 정책 설계 | 요구사항과 초기 설계, 선택 근거 |
| 기준 구현 | 핵심 업무를 끝까지 연결하고 관측 환경 구성 | 실행 가능한 초기 버전과 기준 동작 |
| 정합성·장애 검증 | 동시 요청, 중복·지연 메시지, 실패·재시작·보상 복구 검증 | 재현 절차, 관측 결과, 정합성 확인 |
| 부하 테스트 | k6로 정의한 부하를 발생시키고 시스템·업무 지표 확인 | 환경·데이터·부하 조건과 기준 성능 |
| 문제 분석·대안 비교 | 로그·메트릭·데이터로 원인을 좁히고 대안의 비용·효과 검토 | 트러블슈팅 기록, 설계 결정 기록 |
| 변경·재검증 | 필요한 설계·코드·설정 변경 후 같은 조건으로 비교 | 변경 내용, 전후 결과, 정합성·회귀 확인 |
| 정리 | 구현·검증·변경 과정을 재현하고 설명할 수 있게 문서화 | 실행 안내, 테스트 스크립트, 최종 설계와 한계 |

부하 테스트와 분석은 구현 이후 한 번 수행하는 작업으로 끝내지 않고, 관측한 문제를 기준으로 필요한 만큼 반복한다. 개선 필요성이 확인되지 않은 부분은 유지한 이유를 설명할 수 있도록 한다.

실제로 관측한 병목과 의도적으로 주입한 장애는 기록에서 구분한다. 개선되지 않은 변경도 결과와 판단 근거를 남긴다.

## 6. 트러블슈팅·설계 변경 기록 형식

각 사례는 다음 흐름으로 기록한다.

1. **문제와 영향:** 어떤 상황에서 사용자·업무·시스템에 어떤 문제가 발생했는가.
2. **재현 조건:** 실행 버전, 테스트 데이터, 부하, 장애 주입, 자원 조건은 무엇인가.
3. **관측 근거:** 로그·메트릭·DB 상태에서 무엇을 확인했는가.
4. **원인 가설과 확인:** 어떤 가설을 세우고 무엇으로 검증했는가.
5. **대안·트레이드오프:** 성능, 정합성, 복구성, 구현 복잡성, 운영 비용을 어떻게 비교했는가.
6. **선택과 변경:** 어떤 대안을 선택해 설계·코드·설정을 어떻게 수정했는가.
7. **재검증:** 전후 결과와 부작용, 업무 정합성은 어떠한가.
8. **잔여 한계:** 해결하지 못한 부분과 후속 과제는 무엇인가.

전후 비교 시 애플리케이션 버전, 자원 제한, 데이터 규모, 부하 모델, 테스트 시간 등 비교 조건을 기록한다. 조건을 바꾸었다면 그 변화를 명시한다.

## 7. 검증의 큰 축

| 검증 축 | 확인할 내용 |
|---|---|
| 기능 | 모집·참여·마감·후속 처리의 핵심 업무 완료 |
| 정합성 | 확정할 업무 규칙에 맞는 목표 판정, 중복 처리 방지, 일관된 최종 상태 |
| 복구 | 일시 장애·프로세스 중단·메시지 재전달 후 업무·보상 처리 재개 |
| 성능 | 요청 응답시간, 처리량, 전체 업무 완료 시간, 비동기 적체 |
| 관측 | 문제 발생 시 업무 진행과 병목·실패 위치를 확인할 수 있는가 |
| 재현성 | 동일한 환경과 절차로 구현·부하·장애 시나리오를 재현할 수 있는가 |

비동기 접수 응답시간과 최종 업무 완료 시간은 구분한다. 부하를 올린 뒤에도 목표 판정과 결제·환불 등 업무 결과가 올바른지 확인한다.

구체적인 동시 사용자 수, 처리량·지연 목표, 데이터 규모와 테스트 시간은 실행 환경과 업무 규칙을 정한 뒤 결정한다. 현재 성능 수치나 개선 결과는 없다.

## 8. 프로젝트 완료 기준의 윤곽

- 확정한 핵심 업무가 구현되어 정상 흐름을 재현할 수 있다.
- 주요 실패·중복·경합 시나리오의 처리 결과와 복구 과정을 검증한다.
- Docker Compose 실행 방법과 테스트 재현 절차를 제공한다.
- k6 스크립트와 측정 환경·조건·결과를 남긴다.
- Prometheus·Grafana에서 핵심 지표를 확인할 수 있다.
- 관측한 문제에 대한 원인 분석, 대안 비교, 설계·구현 변경과 재검증 기록을 남긴다.
- 최종 설계가 초기 설계에서 달라진 이유와 남은 한계를 설명할 수 있다.

최종 수치 기준과 기능별 완료 조건은 다음 설계 단계에서 정한다.

## 9. 현재 설계와 다음 단계

핵심 업무 규칙과 공동구매 상태 초안을 [MVP 요구사항](design/MVP%20%EC%9A%94%EA%B5%AC%EC%82%AC%ED%95%AD.md)에 정리했다. 구매자의 취소는 결제 전과 결제 완료 후 공동구매 확정 전까지 허용하며, 공동구매 확정 후에는 허용하지 않는다. 취소는 참여 한 건의 전체 수량에 대해서만 허용하고, 결제한 건을 취소하면 해당 건의 결제 금액 전액을 환불한다. 개별 참여의 상태 초안과 결제 재시도·취소 후 재참여 규칙은 [개별 참여 상태 설계](design/%EA%B0%9C%EB%B3%84%20%EC%B0%B8%EC%97%AC%20%EC%83%81%ED%83%9C%20%EC%84%A4%EA%B3%84.md)에 정리했다. 여러 개 구매를 허용하며, 같은 공동구매에서 구매자별 유효 참여금액 합계는 목표금액(판매자 기준 수량 × 상품 단가)의 10% 이하여야 한다. 다음 설계에서는 필요한 부분만 한 단계씩 구체화한다.

상품 정보·공동구매·참여를 같은 서비스에 두고 결제·회원·알림을 각각 독립 서비스로 분리하는 초기 경계와 근거는 [도메인 책임과 서비스 경계](design/%EB%8F%84%EB%A9%94%EC%9D%B8%20%EC%B1%85%EC%9E%84%EA%B3%BC%20%EC%84%9C%EB%B9%84%EC%8A%A4%20%EA%B2%BD%EA%B3%84.md)에 정리했다. 공동구매 서비스는 결제 허용·참여 취소·성사 판정과 참여 상태 반영을 맡고, 결제 서비스는 승인·환불 실행과 결과 확인·기록을 맡는다. 회원 서비스는 회원 정보·인증·구매자 및 판매자 역할·로그인·로그아웃을 관리한다. 대상 공동구매·참여 건의 소유 관계와 업무 조건에 따른 권한 판단은 공동구매 서비스가 맡는다. 서비스 간 핵심 업무 흐름과 실패·복구 처리 설계를 시작했다. [핵심 결제 흐름 설계](design/%ED%95%B5%EC%8B%AC%20%EA%B2%B0%EC%A0%9C%20%ED%9D%90%EB%A6%84%20%EC%84%A4%EA%B3%84.md)에는 합의한 공동구매 서비스의 Saga Orchestration·구매자 취소·늦은 승인·마감 경합·안내 시점·공통 기한·사전 수량 확보·전환·해제 기준과 진행 상태·비동기 접수·결과 조회, 8절의 Transactional Outbox 도입·업무 RDB 내 저장·초기 폴링 발행을 기록했다. 폴링 발행기의 상세 동작과 중복·실패 복구의 상세 구현은 아직 미정이다.

AI는 학습 설명자·아키텍트/튜터·개발자·감독관 역할을 구분한다. 사용자가 생각하고 결정할 시간을 확보하고, 설계·구현은 요청한 범위를 따른다. 설계 제안에 동의하면 결정사항을 기록해 짧게 알린 뒤 같은 응답에서 다음 검토 묶음 약 3개의 범위·선택지·추천안을 바로 설명하며, 진행 여부를 다시 묻지 않는다. 새로운 제안은 사용자의 선택 전까지 확정하지 않으며 구현은 별도 요청을 따른다. 학습 설명자는 개요·기본 용어·적용 예시를 간결하게 설명하며, 프로젝트 생성 후 주제별 내용을 `docs/learning/`에서 관리한다. 상세 원칙은 AI 협업 범위 문서를 따른다.

알림 서비스는 메시지 구성·전달과 전달 내역·성공·실패 기록, 재시도와 중복 전달 방지 처리를 맡으며, 공동구매 서비스가 안내 시점·대상·기한을 결정한다. 전달 흐름은 공동구매 서비스 → Kafka → 알림 서비스로 잡는다. 안내 시점은 공동구매 서비스가 결제 개시와 개시 시각·기한을 확정해 저장한 회차 공통 결제 개시 시각으로 합의했다. 결제 기한은 개시 후 168시간과 최종 마감 중 빠른 시각이며, 알림 지연·실패·재시도·실제 전달·읽음 확인으로 기한을 바꾸지 않는다. 전달 채널·외부 연동 방식도 미정이다.

상품 정보는 공동구매 서비스가 공동구매별로 관리하며 MVP에서는 별도 상품 서비스를 두지 않는다. 같은 상품을 여러 공동구매에 등록하면 정보가 중복될 수 있다. 초기 업무 서비스는 공동구매(상품·참여 포함)·결제·회원·알림의 4개로 정리했다. [상품 정보 수정 정책](design/%EC%83%81%ED%92%88%20%EC%A0%95%EB%B3%B4%20%EC%88%98%EC%A0%95%20%EC%A0%95%EC%B1%85.md)에 따라 상품명·설명·단가·기준 수량·최종 마감은 임시 저장 중 소유 판매자만 수정하며 최초 게시 후에는 고정한다. 참여가 없거나 모두 취소되어도 수정 권한을 다시 열지 않고 재모집에서도 유지한다. 수정·게시의 선후는 원자적으로 판단하며, 시스템의 상태·수량 집계·회차별 기한 변경은 기존 규칙대로 진행한다.

진행 중 구매자 취소와 늦은 승인 처리는 합의했다. 취소 수락과 실제 결제 중단·결과 확인·환불을 나눠 추적하며, 취소가 먼저 수락된 참여의 늦은 승인 성공은 성립 판단에 반영하지 않고 전액 환불한다. 참여 취소 → 환불 대기 전환을 추가했고, 실제 환불 완료 확인 뒤에만 환불 완료로 바꾼다. 사전 수량 확보를 채택했고, 결과에 따른 확보 수량의 전환·해제와 결과 불명 시 유지 기준을 적용한다. 마감 경합 업무 규칙도 합의했다. 마감에 접수를 닫고 필요한 기존 결과를 확인하며, 실제 승인 완료 시각이 해당 기한 미만인 유효 결제만 성립 판단에 반영한다. 기한 외 성공은 참여 신청 → 환불 대기로 전환해 전액 환불한다. 마감 결과 확인 중은 별도 공동구매 상태로 두기로 했으며, 구체적인 DB 모델·API 계약과 복구 구현은 미정이다.

메시지 발행 신뢰성 검토에서 Transactional Outbox 도입을 합의했다. 각 서비스가 소유한 업무 데이터와 같은 영속 RDB에 Outbox 테이블을 두고, 업무 변경과 전달할 메시지를 같은 로컬 트랜잭션으로 저장한다. 초기 발행기는 각 서비스 내부에서 폴링으로 커밋된 메시지를 조회해 Kafka로 전달한다. 수량 확보·결제 시도와 승인 의뢰, 취소·환불 후속 의뢰, 결제 결과 저장과 결과 전달, 회차 결제 개시와 알림 의뢰에 적용한다. 재시작 후 전달을 재개할 수 있어야 하며, 중복 발행 가능성을 고려하며 소비 멱등성의 기본 원칙은 핵심 결제 흐름 설계의 8.10절을 따른다. Kafka 브로커의 자체 메시지 저장소와 애플리케이션의 Outbox 저장소는 구분한다. DB 제품·서비스별 물리 구성·테이블명·컬럼과 폴링의 구체적인 간격·상세 동작은 미정이다.

초기 폴링 간격은 길게 잡는 방향으로 합의했다. 정확한 초 단위 값은 구현 전에 정한다. 반복 조회 빈도를 낮추는 대신 승인 의뢰·결과 전달이 늦어질 수 있으며, 구현 후 DB 조회 부하·메시지 적체·전체 업무 완료 시간을 함께 측정해 간격을 조정한다. 결제 기한과 결과 확인에 따른 수량 전환·해제 규칙은 유지한다.

초기 폴링 발행기는 각 서비스 내부의 주기적인 작업으로 구성하기로 합의했다. 공동구매 서비스와 결제 서비스는 각각 자신의 Outbox를 조회해 발행한다. 서비스와 자원·배포·실행 수명을 공유하며, 재시작 후 영속 기록으로 전달을 재개한다. 여러 발행기의 경합에는 처리 중 상태·선점 ID·기한을 원자적으로 기록한 뒤 커밋하고 Kafka로 전송하는 방식을 적용한다. 현재 처리 중인 선점 ID에만 결과 갱신을 허용하고, 기한 만료 후 새 선점 ID로 재선점한다. 구체적인 DB 잠금·조건부 갱신 쿼리와 설정값은 후속 설계에서 정한다. 선점 만료는 발행 권한에 적용하며 결제 수량 확보를 해제하지 않는다.

메시지는 같은 결제 시도·같은 전달 방향 안에서 발행 순서를 관리하기로 합의했다. 서로 다른 시도는 병렬 전달할 수 있고, 공동구매 수량·취소·구매 확정의 경합은 공동구매 서비스의 원자적인 상태 변경으로 제어한다. 선점 만료 후 늦은 전송에 따른 중복·역순 도착에 대응하는 취소 기록·상태 전이 규칙은 유지한다. 상세 원칙은 [핵심 결제 흐름 설계](design/%ED%95%B5%EC%8B%AC%20%EA%B2%B0%EC%A0%9C%20%ED%9D%90%EB%A6%84%20%EC%84%A4%EA%B3%84.md)의 8.6절을 따른다.

같은 시도·방향의 순번 갱신·업무 변경·Outbox 저장을 같은 로컬 트랜잭션으로 묶고, 가장 앞선 미완료 메시지만 선점하기로 합의했다. 앞 메시지의 Kafka 전송 성공 확인과 현재 선점 ID에 따른 Outbox 완료 기록이 커밋된 뒤 다음 메시지를 허용한다. 실제 승인·환불 완료를 기다리지 않는다. 재시도 시 메시지 ID·순번은 유지하며 재선점 시 선점 ID를 새로 부여한다. 앞 메시지의 전송 중·실패·발행 여부 불명·재시도 대기 때문에 후속 메시지를 건너뛰어 선점하지 않는다. 재시도 원칙은 핵심 결제 흐름 설계의 8.8절을 따르며, 구체적인 DB·Kafka·소비 계약과 운영 임계값·권한·API는 후속 설계에서 정한다. 상세 원칙은 핵심 결제 흐름 설계의 8.7절을 따른다.

일시 발행 장애와 발행 여부 불명은 미완료 기록을 유지하고 간격을 점차 늘려 재시도한다. 간격에는 상한과 작은 무작위 차이를 두고 재시도 횟수·마지막 오류·다음 재시도 시각을 영속화한다. 장기 일시 장애는 운영 알림과 상한 간격의 자동 재시도를 병행한다. 직렬화·데이터·권한 문제처럼 원인 수정이 필요한 오류는 자동 재시도 중단을 영속화하고 원인 해결 후 재개한다. 재시작·선점 만료만으로 대기 시각이나 중단 기록을 무시하지 않으며, 앞 메시지를 건너뛰지 않는다. 발행 장애만으로 결제 미승인·확보 해제·기한 연장을 판단하지 않는다. 상세 원칙은 [핵심 결제 흐름 설계](design/%ED%95%B5%EC%8B%AC%20%EA%B2%B0%EC%A0%9C%20%ED%9D%90%EB%A6%84%20%EC%84%A4%EA%B3%84.md)의 8.8절을 따른다.

자동 재시도 상태와 운영 확인 상태를 구분한다. 원인 수정이 필요한 오류는 중단 기록 저장 후 즉시 알리고, 장기 일시 장애는 최초 실패 이후 경과 시간으로 판단해 알림과 자동 재시도를 병행한다. 최초 실패 시각은 재시도마다 덮어쓰지 않는다. 같은 서비스·원인의 장애는 묶어 알리고 재알림 간격을 두며 Kafka 장애 중에도 동작할 감시·전달 경로를 구성한다. 수동 재개는 원인 수정과 현재 중단 상태를 확인해 같은 메시지를 정상 선점 대상으로 돌리고 사람·시각·사유를 기록한다. 메시지 ID·순번·오류 이력은 유지한다. 알림 확인·재개 요청만으로 발행 완료나 문제 해결로 처리하지 않는다. 상세 원칙은 [핵심 결제 흐름 설계](design/%ED%95%B5%EC%8B%AC%20%EA%B2%B0%EC%A0%9C%20%ED%9D%90%EB%A6%84%20%EC%84%A4%EA%B3%84.md)의 8.9절을 따른다.

소비 멱등성과 업무 중복 방지의 다섯 원칙을 합의했다. 각 소비 서비스는 처리한 메시지 ID와 업무 식별자·현재 상태를 함께 확인하고, DB의 중복 처리 기록·해당 단계 업무 변경·필요한 후속 Outbox를 같은 로컬 트랜잭션으로 저장한다. 동시 중복도 한 번만 반영하도록 제어한다. 외부 승인·환불은 같은 업무의 재요청에 같은 멱등성 키를 사용하고 결과 불명 시 기존 작업을 확인한다. 미완료 작업의 복구와 새 결제 시도를 구분하며 중복·늦은 결과로 현재 상태를 되돌리지 않는다. 알림은 같은 안내의 전송 작업 중복 생성을 막고 실제 전달은 채널 연동에서 별도 확인한다. 식별자의 구성·수명·충돌 처리 원칙은 8.11절을 따르며, 구체적인 ID 형식·알림 대상 단위·상세 저장 모델·보관 기간·DB·API·외부 연동 계약은 미정이다. 상세 원칙은 [핵심 결제 흐름 설계](design/%ED%95%B5%EC%8B%AC%20%EA%B2%B0%EC%A0%9C%20%ED%9D%90%EB%A6%84%20%EC%84%A4%EA%B3%84.md)의 8.10절을 따른다.

메시지는 Outbox 최초 저장 시 ID를 부여하고 재발행 시 유지하며, 승인 요청·결과 등 서로 다른 메시지는 새 ID를 갖는다. 소비 중복 기록은 소비 처리 역할 + 메시지 ID로 관리하고 같은 역할의 여러 인스턴스가 공유한다. 승인·중단 업무는 결제 시도 ID와 업무 종류로 구분한다. 원승인 시도당 하나의 전액 환불 업무와 환불 ID를 재사용한다. 안내는 공동구매·회차·대상·안내 종류로 구분하되 대상 단위·채널은 미정이다. 결과는 업무 식별자·결과 종류·현재 상태를 함께 확인하며, 같은 업무 식별자의 금액·대상 불일치는 충돌로 기록한다. 외부 멱등성 키는 승인·환불 업무별로 고정한다. 상세 원칙은 [핵심 결제 흐름 설계](design/%ED%95%B5%EC%8B%AC%20%EA%B2%B0%EC%A0%9C%20%ED%9D%90%EB%A6%84%20%EC%84%A4%EA%B3%84.md)의 8.11절을 따른다.

공동구매·결제·알림 등 각 소비 서비스의 업무 RDB에 별도 소비 처리 기록 테이블을 두기로 합의했다. 소비 처리 역할 + 메시지 ID 조합에 DB의 중복 저장 방지 제약을 두고, 기본 정보는 처리 역할·메시지 ID·처리 시각으로 시작한다. 처리 기록·해당 단계 업무 변경·필요한 후속 Outbox를 한 로컬 트랜잭션으로 커밋하거나 롤백한다. DB 커밋 후 Kafka에 소비 완료를 알리고, 그 사이 중단되면 재수신 시 커밋된 기록으로 중복 반영을 막는다. 처리 기록과 실제 외부 승인 완료를 구분하며 이미 접수한 미완료 작업은 영속 진행 기록으로 계속 복구한다. 테이블명·상세 컬럼·DB 제품·보관 기간·구체적인 오프셋 설정은 미정이다. 상세 원칙은 [핵심 결제 흐름 설계](design/%ED%95%B5%EC%8B%AC%20%EA%B2%B0%EC%A0%9C%20%ED%9D%90%EB%A6%84%20%EC%84%A4%EA%B3%84.md)의 8.12절을 따른다.

소비 실패는 정상적인 중복·업무 거절, 일시 오류, 처리 불가·한도 초과 메시지, 공통 장애를 구분하기로 합의했다. 일시 오류는 같은 메시지를 간격을 두어 한도 내 재시도하고, 처리 불가·한도 초과 메시지는 원본·Kafka 위치·소비 역할·오류 이력과 해석 가능한 식별자를 DLT에 보존해 운영 알림과 재처리 대상으로 관리한다. 공통 DB 장애는 영향받는 소비를 일시 중단하고 복구를 확인한다. DLT 저장 확인 전 원본 소비 위치를 넘기지 않으며 보관을 업무 완료·결제 실패 확정으로 취급하지 않는다. 원인 해결 후 기존 식별자와 현재 상태를 확인해 재처리한다. 보관 후 후속 소비의 파티션 보류·재개 원칙은 8.14절을 따르며 실제 오프셋 설정·중단 기록 모델·운영 API는 미정이다. 상세 원칙은 [핵심 결제 흐름 설계](design/%ED%95%B5%EC%8B%AC%20%EA%B2%B0%EC%A0%9C%20%ED%9D%90%EB%A6%84%20%EC%84%A4%EA%B3%84.md)의 8.13절을 따른다.

DLT 보관 후 해당 소비 그룹의 실패 토픽·파티션과 이미 읽은 후속 메시지의 업무 처리를 보류한다. 다른 파티션은 자신의 조건을 만족하면 진행할 수 있다. 중단 사유·원본 위치를 영속 기록해 재시작·재할당 시 다시 적용하고, 같은 식별자로 실패 건을 정상 재처리해 해당 소비 단계의 DB 반영을 확인한 뒤 재개한다. 정상 재처리나 아래 종결 예외를 확인하기 전에는 실패 원본을 넘기는 오프셋을 커밋하지 않는다. 같은 파티션의 다른 업무도 대기한다. 상세 원칙은 [핵심 결제 흐름 설계](design/%ED%95%B5%EC%8B%AC%20%EA%B2%B0%EC%A0%9C%20%ED%9D%90%EB%A6%84%20%EC%84%A4%EA%B3%84.md)의 8.14절을 따른다.

정상 재처리가 어려운 원본은 무효라는 근거와 필요한 업무가 누락되지 않는다는 확인을 갖춘 경우에만 운영 종결할 수 있다. 승인·환불 결과나 업무 영향이 불명확하면 보류를 유지한다. 원본 위치·사람·시각·사유·확인 근거를 별도 종결 기록으로 커밋한 뒤 해당 원본만 넘기며, 원본·오류 이력을 보존한다. 종결을 정상 처리 성공·결제 실패·환불 완료로 취급하거나 수량을 임의 해제하지 않는다. 기록 커밋 후 통지 전 중단은 같은 원본의 종결 적용을 이어간다. 운영 요청의 접수·실행과 동시 조작 제어는 8.16절을 따른다. 실제 저장·오프셋·권한·API는 미정이다. 상세 원칙은 [핵심 결제 흐름 설계](design/%ED%95%B5%EC%8B%AC%20%EA%B2%B0%EC%A0%9C%20%ED%9D%90%EB%A6%84%20%EC%84%A4%EA%B3%84.md)의 8.15절을 따른다.

실패 파티션의 운영 요청을 해당 소비 서비스 DB에 영속 접수하고 현재 담당 소비자가 실행한다. 요청 ID·작업 종류·소비 그룹과 역할·실패 원본 위치·보류 상태 버전을 연결하며, 같은 요청은 기존 진행을 반환하고 내용이 다르면 충돌로 처리한다. 같은 그룹·토픽·파티션의 충돌 작업은 동시에 실행하지 않는다. 접수·실행 중·완료·실패를 구분하고 접수만으로 완료를 표시하지 않는다. 실행권은 실행 ID·기한으로 관리하며 안전한 해제 또는 만료를 확인한 현재 파티션 담당자만 새 실행 ID로 원자적으로 인수한다. 요청 ID·원본 식별자는 유지한다. 실행권 확인과 업무·진행 기록은 같은 짧은 DB 트랜잭션에서 경합을 제어한다. 재시작·재할당 후에는 업무·종결 기록과 Kafka 커밋 위치를 확인해 남은 단계부터 이어가고 이전 담당자의 늦은 갱신을 차단한다. 실행권 만료로 결제 결과·원본 종결·확보 해제를 확정하지 않는다. 운영 실행권의 시간은 해당 서비스 DB를 기준으로 판단하고, 단계 경계에서 현재 담당 여부·실행 ID·보류 버전과 미만료 조건을 확인해 필요한 경우에만 갱신한다. 업무·진행 반영 때에도 권한을 다시 검사하며, 이전 실행자의 늦은 실패·완료 표시도 제한한다. 갱신 실패·불명 시 새 단계를 중단하고 저장된 권한·진행을 확인한다. 운영 요청별 한도 내에서 자동 복구하고 데이터 충돌·원인 수정 필요·반복 실패·장시간 무진행이면 영속 중단과 운영 알림으로 전환한다. 공통 장애는 영향받는 작업을 일시 중단하고 복구 후 재개한다. 재시도·무진행 이력은 요청 ID에 연결해 재시작·실행권 인수로 초기화하지 않는다. 자동 중단을 결제 실패·원본 종결·확보 해제로 해석하지 않으며 원본·진행을 보존한다. 원인 수정 후 같은 요청을 수동 재개하고 사람·시각·사유를 기록한다. 수동 재개는 같은 요청 안에 새 복구 회차와 한도·수정 근거를 기록하고 전체 이력을 보존한다. 재개 중복은 같은 회차를 반환하며 재시작·실행권 인수는 같은 회차의 한도를 이어간다. 기존 반영 근거를 확인해 남은 단계만 수행한다. 정확한 기한·제한시간·횟수·간격·DB 제어·권한·API는 해당 구현 설계에서 구체화한다. 상세 원칙은 [핵심 결제 흐름 설계](design/%ED%95%B5%EC%8B%AC%20%EA%B2%B0%EC%A0%9C%20%ED%9D%90%EB%A6%84%20%EC%84%A4%EA%B3%84.md)의 8.16~8.20절을 따른다.

구현 범위 3개를 합의했다. 결제 서비스는 HTTP로 별도 PG Mock 서버를 호출하고 승인·환불·결과 조회·멱등성·통신 장애를 검증한다. 초기 알림은 테스트 대역을 사용하고 실제 업체 연동은 후속으로 둔다. 알림 대역의 구체적인 구성·채널은 구현 설계에서 정한다. 미완료 Saga·승인·환불은 각 서비스 내부의 주기적인 작업으로 자신의 DB 진행을 확인해 기존 식별자로 이어간다. 초기 사용자·운영 수단은 API와 테스트 클라이언트로 구성하고 화면·대시보드는 후속으로 둔다. 이번 세션은 합의 반영과 인계로 마무리하며 다음 세션에서 데이터와 동시성 3개 항목을 검토한다. 상세 결정은 [핵심 결제 흐름 설계](design/%ED%95%B5%EC%8B%AC%20%EA%B2%B0%EC%A0%9C%20%ED%9D%90%EB%A6%84%20%EC%84%A4%EA%B3%84.md)의 10절을 따른다.

### 다음 세션 인계

세션 2에서는 공동구매 서비스의 Saga Orchestration, 승인 전 사전 수량 확보·전환·해제, 참여 상태 유지와 시도별 진행 구분, 마감 결과 확인 중의 별도 상태, 202 접수·결과 조회 방식을 합의하고 문서에 반영했다. 사용자가 새 세션에서 이어가기로 하여 다음 항목의 설계는 진행하지 않았다. 코드 구현과 실행 테스트는 수행하지 않았다. 문서의 검증 시나리오는 이후 구현에서 확인할 후보이며 테스트 통과 결과가 아니다.

이번 세션에서는 메시지 발행 결과의 확인과 장애 후 전달 재개를 구분하고, 업무 변경과 발행할 메시지를 같은 로컬 트랜잭션으로 영속화하는 Transactional Outbox 도입을 합의했다. 이어서 Outbox를 각 서비스의 업무 RDB와 같은 DB에 테이블로 저장하고 초기에는 폴링으로 발행하기로 했다. Kafka 자체 메시지 저장소는 브로커가 관리한다. 설계 결정과 검증 시나리오 후보만 문서에 반영했으며, 코드 구현·실행 테스트는 수행하지 않았다.

후속 대화에서 초기 폴링은 긴 간격으로 시작하고 발행기는 각 서비스 내부에 구성하기로 합의했다. 공동구매·결제 서비스가 각각 자신의 Outbox를 조회하며, 정확한 간격과 스케줄러·스레드 구성은 미정이다. 구현·실행 테스트는 수행하지 않았다.

추가로 발행 대상은 처리 중 상태·선점 ID·선점 기한을 짧은 DB 트랜잭션으로 원자적으로 기록해 정하기로 합의했다. 커밋 후 Kafka로 전송하고, 현재 처리 중인 선점 ID에만 결과 갱신을 허용한다. 중단된 미완료 작업은 기한 만료 후 새 선점 ID로 재선점하며, 이전 발행기의 늦은 전송에 따른 중복은 소비 멱등성으로 다룬다. 선점 기한으로 결제 수량 확보를 만료시키지 않는다. 설계와 검증 시나리오 후보만 기록했으며 코드 구현·실행 테스트는 수행하지 않았다.

2026-10-27에는 같은 결제 시도·같은 전달 방향의 메시지 발행 순서를 관리하고, 서로 다른 시도는 병렬 전달할 수 있도록 범위를 합의했다. 선점 만료 후 늦은 전송·중복·역순 도착에도 기존 취소 기록과 상태 전이 규칙을 유지한다.

이어서 시도별·전달 방향별 순번 갱신·업무 변경·Outbox 저장을 같은 로컬 트랜잭션으로 묶고, 가장 앞선 미완료 메시지만 선점하기로 합의했다. Kafka 전송 성공을 확인하고 현재 선점 ID에 따라 Outbox 완료를 기록한 뒤 다음 메시지를 허용한다. 실제 결제 업무 완료를 기다리지 않으며, 앞 메시지가 실패·발행 여부 불명인 동안 후속을 건너뛰지 않는다. 재시도 시 메시지 ID·순번을 유지하고 재선점 시 새 선점 ID를 부여한다. 설계와 검증 시나리오 후보를 문서에 반영했으며 코드 구현·실행 테스트는 수행하지 않았다.

추가로 일시 발행 장애·발행 여부 불명은 상한과 작은 무작위 차이가 있는 간격으로 계속 재시도하고, 장기화하면 운영 알림을 병행하기로 합의했다. 원인 수정이 필요한 오류는 자동 재시도를 중단하고 원인 해결 후 재개한다. 재시도 횟수·마지막 오류·다음 재시도 시각과 중단 기록은 재시작 후에도 유지한다. 자동 재시도 중단과 장기 일시 장애를 구분하며, 어느 경우에도 미완료 메시지를 건너뛰거나 임의 완료 처리하지 않는다. 구체적인 오류 분류·시간 설정·운영 임계값·권한·API는 미정이며 코드 구현·실행 테스트는 수행하지 않았다.

이어서 자동 재시도 상태와 운영 확인 상태를 구분하고, 중단 기록 저장 후 즉시 알림·최초 실패 이후 경과 시간에 따른 장기화 알림·서비스와 원인별 묶음 및 재알림 간격의 원칙을 합의했다. Kafka 장애 중에도 운영 알림을 전달할 경로를 구성한다. 수동 재개는 원인 수정과 중단 상태를 확인해 같은 메시지를 정상 선점 대상으로 돌리고 사람·시각·사유를 기록하며, 실제 발행 성공과 Outbox 완료 기록 후에 문제를 해결된 것으로 표시한다. 장기 일시 장애에 수동 재개를 필수로 요구하지 않는다. 임계값·도구·채널·운영 권한·API는 미정이며 코드 구현·실행 테스트는 수행하지 않았다.

멱등성의 개념과 프로젝트 적용 범위를 설명한 뒤 메시지·업무 양쪽의 중복 판단, 처리 기록·업무 변경·후속 Outbox의 원자적 저장과 동시 중복 방지, 외부 승인·환불의 같은 업무 키와 결과 확인, 미완료 복구와 새 시도의 구분, 중복·늦은 결과에 따른 상태 역행 방지의 다섯 원칙을 합의했다. 요청 접수와 실제 외부 작업 완료를 구분하고 알림 전송 작업의 중복 생성도 막는다. 구체적인 ID 형식·상세 저장 모델·보관 기간·DB·API·외부 연동 계약은 미정이며 코드 구현·실행 테스트는 수행하지 않았다.

이어서 메시지 ID의 최초 저장·재발행 유지, 소비 처리 역할 + 메시지 ID의 중복 기록 기준, 시도 ID와 업무 종류에 따른 승인·중단 구분, 원승인당 전액 환불 업무·환불 ID 재사용을 합의했다. 결과는 업무 식별자·결과 종류·현재 상태를 함께 확인하고 같은 업무 식별자의 금액·대상 불일치는 충돌로 기록한다. 외부 멱등성 키는 승인·환불 업무별로 고정한다. 안내의 구분 기준은 공동구매·회차·대상·안내 종류이며 대상 단위·채널은 미정이다. 구체적인 ID 형식·메시지 필드·상세 저장 모델·API·연동 계약은 미정이며 코드 구현·실행 테스트는 수행하지 않았다.

추가로 각 소비 서비스의 업무 RDB에 별도 소비 처리 기록 테이블을 두고 소비 처리 역할 + 메시지 ID 조합에 DB 중복 저장 방지 제약을 두기로 합의했다. 처리 기록·해당 단계 업무 변경·필요한 Outbox를 함께 커밋하거나 롤백하고 DB 커밋 후 Kafka에 소비 완료를 알린다. 커밋 후 통지 전 중단은 재수신 시 저장된 기록으로 중복 반영을 막는다. 처리 기록은 해당 소비 단계의 저장 완료이며 실제 외부 승인·환불 완료와 구분한다. 실제 테이블명·상세 컬럼·DB 제품·보관 기간·오프셋 설정은 미정이며 코드 구현·실행 테스트는 수행하지 않았다.

이어서 소비 측의 정상적인 중복·업무 거절과 일시 오류·처리 불가 메시지·공통 장애를 구분하고, 일시 오류의 한도 재시도와 처리 불가·한도 초과 메시지의 DLT 보관·운영 알림·기존 식별자에 따른 재처리 원칙을 합의했다. 공통 DB 장애는 영향받는 소비를 일시 중단한다. DLT 저장 확인 전 원본 소비 위치를 넘기지 않으며 보관만으로 정상 소비 처리 완료나 실제 결제 실패를 확정하지 않는다. 정상 재처리가 어려운 원본의 운영 종결 예외는 8.15절에서 정했다. 실제 순서 제어·오류 분류 세부·설정값·토픽 구성·보관 기간·재처리 API는 미정이다. 코드 구현·실행 테스트는 수행하지 않았다.

추가로 DLT 보관 후 실패한 소비 그룹의 해당 토픽·파티션을 보류하고 실패 원본을 건너뛰는 오프셋을 커밋하지 않기로 합의했다. 이미 읽은 같은 파티션의 후속 메시지도 보류하며 다른 파티션은 진행 가능하다. 중단 사유·원본 위치를 영속 기록해 재시작·재할당 시 다시 적용한다. 원인 수정 후 기존 식별자로 실패 건을 재처리하고 해당 소비 단계의 DB 반영을 확인한 뒤 후속 처리를 재개한다. 같은 파티션의 다른 업무도 대기한다. 정상 재처리가 어려운 무효 원본의 운영 종결 예외는 8.15절을 따른다. 구체적인 저장·오프셋·운영 API는 미정이며 코드 구현·실행 테스트는 수행하지 않았다.

2026-10-28에는 무효 원본에 한정한 운영 종결 예외를 합의했다. 정상 재처리를 기본으로 하며 무효성과 필요한 업무 누락이 없음을 확인한 경우에만 별도 종결 기록을 커밋하고 해당 원본만 넘긴다. 사람·시각·사유·근거·원본 위치와 DLT 이력을 보존하고, 종결 기록 커밋 후 오프셋 통지 전 중단은 같은 원본의 종결 적용을 이어간다. 업무 영향이나 실제 승인·환불 결과가 불명확하면 보류한다. 정상 처리 성공·결제 실패·환불 완료로 간주하거나 확보 수량을 임의 해제하지 않는다. 운영 요청의 접수·실행과 동시 조작 제어 원칙은 8.16절을 따른다. 실행권 인수·단계별 복구 원칙은 8.17절을 따른다. 운영 실행권의 시간 기준·갱신·반영 시 권한 재검사는 8.18절을 따른다. 정확한 기한·단계별 제한시간과 구체적인 저장·권한·API는 미정이며 코드 구현·실행 테스트는 수행하지 않았다.

이어서 운영 요청을 DB에 접수하고 현재 파티션 담당 소비자가 실행하며, 요청 ID·실패 원본·보류 버전을 확인하고 충돌 작업을 동시에 실행하지 않기로 합의했다. 접수·실행 중·완료·실패를 구분하고, 재시작·재할당 시 저장된 진행을 이어가며 이전 담당자의 늦은 갱신을 제한한다. 추가로 실행 ID·기한을 원자적으로 확보하고 안전한 해제 또는 만료 후 현재 담당자에게 새 실행 ID로 인수하기로 합의했다. 권한 확인과 업무·진행 저장을 같은 짧은 DB 트랜잭션에서 제어하고, DB 반영 전·오프셋 커밋 전·재개 완료 전을 구분해 남은 단계를 복구한다. 만료만으로 결제 실패·원본 종결·확보 해제를 확정하지 않는다. 운영 실행권의 시간은 해당 RDB를 기준으로 하고 단계 경계에서 필요할 때 미만료·현재 실행 ID·담당 여부·보류 버전을 확인해 갱신하기로 합의했다. 업무 반영 시에도 권한을 다시 검사하며 갱신 실패·불명 시 새 단계를 중단한다. 운영 요청별 한도 내 자동 복구와 원인 수정 필요·반복 실패·장시간 무진행 시 영속 중단·운영 알림으로 전환하고, 요청 ID에 연결한 이력을 재시작·인수로 초기화하지 않기로 합의했다. 공통 장애는 일시 중단 후 복구하며 원인 수정 후 같은 요청을 수동 재개한다. 수동 재개 때 같은 요청 안에 새 복구 회차와 한도·수정 근거를 기록하고 전체 이력을 보존하기로 합의했다. 재개 중복은 같은 회차를 반환하고 재시작·실행권 인수는 같은 회차의 이력·한도를 유지한다. 정확한 수치·DB 제어는 해당 구현 설계에서 구체화한다. 코드 구현·실행 테스트는 수행하지 않았다.

**이번 세션은 구현 범위 3개 합의와 문서 인계로 마무리했다.** 별도 HTTP PG Mock, 초기 알림 테스트 대역, 각 서비스 내부의 주기적인 미완료 업무 복구, API·테스트 클라이언트 중심 범위를 채택했다. 다음 세션은 RDB 구성·핵심 테이블과 트랜잭션·동시성 제어 3개를 함께 검토한다. 남은 큰 결정은 약 15개·5묶음이며 데이터와 동시성의 새 제안은 아직 선택하지 않았다. 관련 항목 3개씩 검토하는 진행 방식을 유지하고 실제 구현은 별도 요청을 따른다.

합의한 핵심 사항:

- 수동 재개는 같은 운영 요청 안에 새 복구 회차와 한도·수정 근거를 기록한다. 전체 이력·원본 식별자·완료 단계는 보존하며, 재시작·실행권 인수는 같은 회차를 이어간다. 중복 재개로 회차·한도가 중복 생성되지 않도록 제어하고 남은 단계만 수행한다.

- 운영 요청은 요청 ID 기준의 한도 내에서 자동 복구하고 원인 수정 필요·반복 실패·장시간 무진행 시 영속 중단·운영 알림으로 전환한다. 재시작·실행권 인수로 이력을 초기화하지 않는다. 공통 장애는 일시 중단 후 복구한다. 원본·진행·업무 결과 확인을 보존하고 원인 수정 후 같은 요청을 사람·시각·사유와 함께 수동 재개한다. 정확한 한도·시간과 재개 후 한도 관리는 미정이다.

- 운영 실행권의 시간 기준은 해당 소비 서비스 RDB로 통일한다. 단계 경계에서 현재 담당·실행 ID·보류 버전·미만료 조건을 확인해 필요한 경우에만 갱신하고 업무·진행 반영 시에도 권한을 검사한다. 갱신 실패·불명 시 새 단계를 시작하지 않고 저장된 권한·진행을 확인한다. 정확한 기한·단계별 제한시간·DB 제어는 미정이다.

- 운영 실행권은 실행 ID·기한으로 원자적으로 확보하고 안전한 해제 또는 만료 후 현재 파티션 담당자가 새 ID로 인수한다. 업무·진행 기록은 실행권을 확인하는 같은 짧은 DB 트랜잭션에서 저장한다. DB 반영·Kafka 위치 정리·후속 재개의 저장 근거에 따라 남은 단계를 이어가며, 실행권 만료만으로 결제 실패·원본 종결·확보 해제를 확정하지 않는다.

- 운영 요청을 DB에 영속 접수하고 현재 담당 소비자가 실행한다. 요청 ID·실패 원본·보류 상태 버전을 확인하고 같은 파티션의 충돌 작업은 동시에 실행하지 않는다. 동일 요청은 기존 진행을 반환한다. 접수·실행 중·완료·실패를 구분하고 재할당 후 저장된 진행을 이어가며 이전 담당자의 늦은 갱신을 제한한다. 실행 ID·기한에 따른 인수와 단계별 복구는 8.17절을 따른다. 운영 실행권의 시간·갱신 원칙은 8.18절을 따른다. 정확한 기한·단계별 제한시간·DB 제어의 상세 조건은 미정이다.

- 정상 재처리를 기본으로 하되, 무효성과 필요한 업무 누락이 없음을 확인한 원본만 별도 운영 종결 기록을 커밋한 뒤 넘길 수 있다. 실제 승인·환불 결과나 업무 영향이 불명확하면 보류한다. 종결 근거·조작 이력·원본을 보존하고 정상 처리 성공·결제 실패·환불 완료·확보 해제로 간주하지 않는다. 동시 조작 제어 원칙은 8.16절을 따르며 구체적인 저장·권한·API는 미정이다.

- DLT 보관 후 실패한 소비 그룹의 해당 토픽·파티션 후속 처리를 보류하고 실패 원본을 건너뛰는 오프셋을 커밋하지 않는다. 이미 읽은 후속 메시지도 보류하며 다른 파티션은 진행할 수 있다. 중단 기록을 영속화해 재시작·재할당 시 다시 적용하고, 원인 수정 후 실패 건의 DB 반영을 확인한 뒤 후속 처리를 재개한다. 8.15절의 무효 원본 운영 종결 예외 외에는 임의로 원본을 넘기지 않는다. 실제 저장·오프셋·운영 API는 미정이다.

- 소비 측 정상 중복·업무 거절, 일시 오류, 처리 불가·한도 초과 메시지와 공통 장애를 구분한다. 일시 오류는 한도 내 재시도하고 처리 불가·한도 초과 메시지는 DLT 보관·운영 알림 대상으로 관리한다. 공통 DB 장애는 영향받는 소비를 일시 중단한다. DLT 저장 확인 전 원본 소비 위치를 넘기지 않으며 보관을 업무 완료·결제 실패 확정으로 취급하지 않는다. 격리 후 후속 소비는 8.14절의 파티션 보류·재개 원칙을 따르며 구체적인 재시도·오프셋·보관·재처리 설정은 미정이다.

- 각 소비 서비스는 자신의 업무 RDB에 별도 처리 기록 테이블을 두고 소비 처리 역할 + 메시지 ID에 중복 저장 방지 제약을 둔다. 처리 기록·해당 단계 업무 변경·필요한 Outbox를 한 로컬 트랜잭션으로 커밋하거나 롤백하고, DB 커밋 후 Kafka에 소비 완료를 알린다. 실제 외부 승인·환불 완료는 별도 진행으로 추적한다. 상세 모델·보관 기간·구체적인 오프셋 설정은 미정이다.

- 메시지 ID는 최초 Outbox 저장 시 부여하고 재발행 시 유지한다. 소비 중복 기록은 소비 처리 역할 + 메시지 ID를 기준으로 관리한다. 승인·중단은 시도 ID와 업무 종류로 구분하고 원승인당 전액 환불 업무·환불 ID를 재사용한다. 같은 업무 식별자의 금액·대상 불일치는 충돌로 기록하며 외부 멱등성 키는 승인·환불 업무별로 고정한다. 실제 ID 형식·알림 대상 단위·저장·API·연동 계약은 미정이다.

- 소비 멱등성은 메시지 ID와 업무 식별자·현재 상태를 함께 확인한다. DB의 중복 처리 기록·업무 변경·필요한 Outbox를 같은 로컬 트랜잭션으로 저장하고 동시 중복도 제어한다. 외부 승인·환불은 같은 업무의 재요청에 같은 멱등성 키와 기존 결과 확인을 적용한다. 미완료 복구와 새 시도를 구분하고 중복·늦은 결과로 상태를 되돌리지 않는다. 구체적인 ID 형식·상세 저장 모델·보관 기간·DB·API·외부 연동 계약은 미정이다.

- 자동 재시도 상태와 운영 확인 상태를 구분한다. 중단 기록 저장 후 즉시 알리고 장기 일시 장애는 최초 실패 이후 경과 시간으로 판단한다. 원인 수정 후 같은 메시지를 정상 선점 대상으로 돌리고 재개한 사람·시각·사유를 기록한다. 알림 확인·재개 요청만으로 발행 완료나 문제 해결로 처리하지 않는다. 도구·채널·운영 임계값·권한·API는 미정이다.

- 초기 업무 서비스는 공동구매(상품·참여 포함)·결제·회원·알림의 4개다. 별도 상품 서비스는 두지 않는다.
- 초기 폴링 간격은 길게 잡는 방향으로 합의했다. 정확한 초 단위 값은 구현 전에 정하고, 발행 대기와 DB 조회 부하·전체 업무 완료 시간을 검증해 조정한다. 결제 기한은 폴링 지연으로 연장하지 않는다.
- 초기 폴링 발행기는 각 서비스 내부에 구성한다. 공동구매·결제 서비스가 각각 자신의 Outbox를 조회하고 발행한다. 발행 대상은 처리 중 상태·선점 ID·기한을 원자적으로 기록해 선점하고 커밋 후 Kafka로 전송한다. 현재 처리 중인 선점 ID에만 결과 갱신을 허용하며, 미완료 작업은 기한 만료 후 새 ID로 재선점한다. 구체적인 DB 제어·설정값은 미정이며 중복 전달에 대한 소비 멱등성 원칙은 8.10절을 따르며 구체적인 구현은 미정이다.
- 같은 결제 시도·같은 전달 방향의 메시지는 순번을 저장하고 가장 앞선 미완료 메시지만 선점한다. 순번 갱신·업무 변경·Outbox 저장을 함께 커밋하며, 앞 메시지의 Kafka 전송 성공 확인과 현재 선점 ID에 따른 Outbox 완료 기록 후 다음 메시지를 허용한다. 실제 승인·환불 완료를 기다리지 않는다. 재시도 시 메시지 ID·순번은 유지하고 재선점 시 새 선점 ID를 부여한다. 서로 다른 시도는 병렬 전달할 수 있으며 공동구매 경합과 역순·중복 도착에는 기존 업무 규칙을 적용한다. 재시도 원칙은 8.8절을 따르며 구체적인 DB·Kafka·소비 계약과 오류 분류·시간 설정·운영 임계값·권한·API는 미정이다.
- Transactional Outbox를 도입한다. 각 서비스의 업무 RDB와 같은 DB에 Outbox 테이블을 두고 업무 변경과 발행할 메시지를 같은 로컬 트랜잭션으로 영속화한다. 커밋 후 폴링 발행기가 Kafka로 전달하고 발행 결과를 기록한다. 재시작 후 미발행·미확인 발행을 추적하며, 중복 전달에 대한 소비 멱등성 원칙은 8.10절을 따르며 구체적인 구현은 미정이다. 폴링의 구체적인 간격·상세 동작과 구체적인 DB 모델은 미정이다.
- 참여 상태는 기존 구성을 유지하고, 결제 시도별로 진행 중·결과 확인 중·반영 완료와 확인된 승인 결과를 구분한다. 마감 결과 확인 중은 별도 공동구매 상태로 둔다. 접수 정보를 영속화한 뒤 202와 시도 ID·조회 경로를 반환하고 결과를 조회한다. 미완료 시도는 기존 시도를 추적하며, 미승인 확정·업무 반영·확보 해제 후 조건이 유효한 재시도는 새 시도로 기록한다. 환불은 별도 진행으로 추적한다.
- 공동구매 서비스가 승인 전에 참여 한 건의 전체 수량을 원자적으로 확보하고, 취소되지 않은 결제 완료 수량 + 확보 수량이 기준 수량을 넘지 않도록 한다. 유효 승인 성공이면 결제 완료로 전환하고, 미승인·중단 확정이면 해제한다. 취소·기한 외 성공은 제외와 환불 필요성·요청을 기록한 뒤 해제한다. 결과 불명이면 확보를 유지하며 시간 경과만으로 해제하지 않는다.
- 공동구매 서비스가 결제 흐름의 Saga Orchestration을 맡는다. 승인 요청·업무 결과 반영·필요한 환불 요청과 전체 진행을 조정하고, 결제 서비스는 실제 승인·환불 실행과 처리 결과 확인·기록·전달을 맡는다. 진행을 영속화하고 재시작 후 이어가야 하며, 상세 모델·복구 구현은 후속 설계에서 정한다.
- 기준 수량은 최소 10개, 최초 모집 목표는 기준 수량의 120%를 올림한다. 재모집은 실제 부족분만 모집한다. 구매자별 유효 참여금액 합계는 목표금액의 10% 이하다.
- 기준 수량을 정확히 채운 유효 결제로 구매를 확정한다. 초과 결제는 참여 건 전체를 거절한다. 구매자 취소는 구매 확정 전 참여 한 건 전체에 대해서만 허용하고 실제 결제 금액 전액을 환불한다.
- 구매자 취소가 먼저 수락된 참여의 늦은 승인 성공은 성립 판단에 반영하지 않고 환불한다. 참여 취소 → 환불 대기 → 환불 완료로 추적한다.
- 안내 시점은 회차 공통 결제 개시 시각이다. 결제 기한은 개시 후 168시간과 최종 마감 중 빠른 시각이며, 알림 지연·실패·재시도로 자동 연장하지 않는다. 새 회차는 새 기한을 갖되 이전 시도의 기한은 유지한다.
- 실제 승인 완료 시각이 해당 기한 미만인 유효 결제만 반영한다. 마감에는 새 접수를 닫고 미확정 결과를 확인한 뒤 성사·재모집·무산을 판정한다. 기한 외 승인 성공은 참여 신청 → 환불 대기로 전환해 전액 환불한다.
- 상품명·설명·단가·기준 수량·최종 마감은 임시 저장 중 소유 판매자만 수정하고 최초 게시 후에는 고정한다. 참여가 없거나 모두 취소되어도, 공동구매가 재모집으로 돌아와도 유지하며, 오탈자 수정 예외와 게시 후 임시 저장 복귀는 두지 않는다. 시스템의 상태·수량 집계·회차별 기한 변경은 계속 허용한다.

### 설계 진행 현황과 다음 검토

업무 규칙·서비스 경계·Saga·수량 확보·메시지 안정성·운영 복구·데이터 제어·API와 메시지 계약·인증과 권한·실행 환경·관측과 검증의 주요 방향을 합의했다. 다음은 구현 순서와 단계별 완료 기준을 검토하고, 요청받은 단계의 상세 설계·구현·검증으로 이어가는 것이다.

관측과 검증 3개 항목까지 합의해 아래 큰 설계 결정 6묶음의 주요 방향을 정리했다. 이는 세부 컬럼·쿼리·설정값의 확정이나 구현 완료를 뜻하지 않는다. DB 물리 구성은 단일 PostgreSQL 서버의 서비스별 DB·계정으로 유지한다. 구현 계획의 새 제안은 사용자 선택 전까지 확정하지 않으며 실제 구현은 별도 요청을 따른다.

| 묶음 | 함께 검토할 3개 항목 | 현재 상태 |
|---|---|---|
| 1. 구현 범위 | 외부 PG·알림 연동 범위 / 미완료 승인·환불·Saga 복구 구성 / 사용자·운영 화면과 API 범위 | 합의 완료 |
| 2. 데이터와 동시성 | RDB 제품·서비스별 소유권과 물리 구성 / 핵심 테이블·로컬 트랜잭션 / 수량·취소·마감·상품 게시의 경합 제어 | 주요 방향 합의. 물리 구성은 실행 환경 묶음에서 단일 서버·서비스별 DB로 확정 |
| 3. API와 메시지 계약 | 외부 API·요청 멱등성·오류·결과 조회 / 명령·결과 메시지와 식별자·버전 / Kafka 토픽·키·파티션·발행 확인·소비 완료 설정 | 주요 방향 합의. 세부 경로·필드·보관·설정은 구현 설계에서 구체화 |

관련 항목 3개마다 문제·선택지·추천과 영향을 함께 제시하고 전체 동의 또는 번호별 수정으로 검토한다. 필드·쿼리·수치 설정을 매번 별도의 승인 주제로 추가하지 않고 해당 기능의 구현 설계에 포함한다. 전체 값을 미리 정할 때까지 프로젝트 생성을 미루지 않되, 프로젝트 생성 전 버전 호환·빌드·최소 환경을 확인하고 기능 구현 전 필요한 데이터·계약·인증·검증 조건을 정한다. 구현 계획과 일정은 범위·핵심 구조를 정리한 뒤 수립하며, 실제 구현은 별도 요청을 따른다.

2026-10-28 최신 합의: 참여·시도·확보 및 Saga 진행과 환불을 구분하고, 공동구매 집계와 상세 기록을 로컬 트랜잭션으로 갱신한다. 공동구매 행 비관적 잠금을 초기 경합 제어로 채택하며 잠금 후 상태·수량·기한을 확인한다. 성사·무산 결정과 후속 작업을 영속화하고 참여 정리·환불은 나누어 수행한다. 상세 범위는 [핵심 결제 흐름 설계](design/%ED%95%B5%EC%8B%AC%20%EA%B2%B0%EC%A0%9C%20%ED%9D%90%EB%A6%84%20%EC%84%A4%EA%B3%84.md) 11절을 따른다. 앞선 인계의 데이터 구조·제어 미정 표기는 이번 합의 범위만큼 갱신된다. 업무 RDB는 PostgreSQL로 확정했다. 버전·물리 구성은 미정이다.

초기 선택은 MVP 구현·검증을 위한 기준으로 두며 [MVP 설계 재검토 목록](decisions/MVP%20%EC%84%A4%EA%B3%84%20%EC%9E%AC%EA%B2%80%ED%86%A0%20%EB%AA%A9%EB%A1%9D.md)에 목적·재검토 조건·대안·트레이드오프·검증 방법을 관리한다. 구현 후 관측한 문제를 근거로 대안 구현 여부를 결정한다.

API와 메시지 계약도 합의했다. 변경 요청에 사용자·작업 종류·Idempotency-Key를 적용하고 같은 키의 내용 충돌은 409로 처리한다. 공통 정보와 업무별 본문을 구분한 JSON을 사용하며 초기에는 계약 문서와 호환성 테스트로 관리한다. Kafka는 결제 명령·결제 결과·알림 의뢰를 분리하고 키는 각각 원승인 시도·공동구매 ID를 사용한다. acks=all·프로듀서 멱등성·자동 커밋 해제·DB 반영 후 연속 처리 완료 위치까지 커밋을 적용한다. 기존 Outbox·소비 멱등성·실패 파티션 보류를 유지한다. 상세 범위는 [API와 메시지 계약](design/API%EC%99%80%20%EB%A9%94%EC%8B%9C%EC%A7%80%20%EA%B3%84%EC%95%BD.md)과 핵심 결제 흐름 설계 12절을 따른다. 코드 구현·실행 검증은 수행하지 않았다.

인증과 권한도 합의했다. 회원 서비스 PostgreSQL의 Spring Session JDBC로 시작하고 Redis는 재검토 목록 R-11에 후속 후보로 관리한다. Gateway는 보호된 요청마다 회원 서비스로 세션·현재 역할·계정 상태를 확인하며 외부 신원 헤더 제거·서비스별 내부 호출자 확인·인증 확인 장애 시 거절을 적용한다. 쿠키·CSRF와 소유 서비스의 역할·소유권·업무 상태 검사, 운영 권한의 제한·이력을 적용한다. 상세 합의는 [인증과 권한 설계](design/%EC%9D%B8%EC%A6%9D%EA%B3%BC%20%EA%B6%8C%ED%95%9C%20%EC%84%A4%EA%B3%84.md)를 따른다. 다음은 실행 환경과 초기 설정의 3개 항목이며 코드 구현·실행 검증은 수행하지 않았다.

실행 환경과 초기 설정도 합의했다. Java 21·Maven Wrapper·단일 저장소의 개별 실행 모듈, Boot 4.0.x + Cloud 2025.1.x 후보의 연동 검증 후 패치 고정, 로컬 Compose·단일 DB 및 Kafka 브로커·Config 파일·비밀값 별도 주입·빌드/테스트/이미지 CI를 채택했다. 세션 유휴 30분·HTTP 연결 1초/응답 5초·Outbox 10초/최대 50건·복구 30초·Outbox 일시 재시도 최대 60초와 무작위 차이·업무 기록 초기 자동 삭제 없음으로 시작한다. 상세 범위는 [실행 환경과 초기 설정](design/%EC%8B%A4%ED%96%89%20%ED%99%98%EA%B2%BD%EA%B3%BC%20%EC%B4%88%EA%B8%B0%20%EC%84%A4%EC%A0%95.md), 재검토는 목록 R-14~R-19를 따른다. 앞선 인계의 물리 구성·초기값 미정 표기는 이번 합의 범위만큼 갱신한다. 프로젝트 생성·기동·성능 검증은 아직 수행하지 않았다.

관측과 검증도 합의했다. JSON 로그에 요청·공동구매·결제 시도·메시지 ID를 연결하고 개별 ID를 메트릭 라벨로 사용하지 않는다. Actuator·Micrometer·Prometheus·Grafana로 시스템·업무 지표를 관측하며 운영 알림은 Kafka를 거치지 않는 Prometheus → Alertmanager → 로컬 테스트 수신기로 구성한다. 별도 로그 수집·분산 추적 서버는 분석의 어려움이 확인되면 비교한다. 업무 규칙·실제 PostgreSQL/Kafka·PG Mock 전체 흐름·인증 검증을 나누고 DB·집계·거래 기록으로 판정한다. k6는 결제 접수 유입 초당 2건·준비 2분/측정 5분, 5/10건 증가와 분산/집중 비교로 시작한다. 기준 부하의 접수 p95 500ms 미만·예상 밖 오류율 1% 미만·정상 결제 최종 반영 p95 120초 이내는 측정 전 목표다. 접수·완료·미완료 건수와 정합성 위반 0건·종료 후 대사를 함께 확인한다. 상세 합의는 [관측과 검증 설계](design/%EA%B4%80%EC%B8%A1%EA%B3%BC%20%EA%B2%80%EC%A6%9D%20%EC%84%A4%EA%B3%84.md), 재검토 조건은 목록 R-20~R-22를 따른다. 프로젝트 생성·실행 테스트·성능 측정은 아직 수행하지 않았다.

2026-10-28 후속 사용자 요청으로 구현 순서 제안의 전체 승인을 기다리는 대신 단일 Spring Boot 초기 프로젝트 생성만 진행했다. 다음 작업은 MSA 공통사항을 사용자와 정해 단계별 커밋으로 추가하는 것이다.
